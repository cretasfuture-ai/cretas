# 白垩纪对外合同：起草流程、条款原则、文字标准

> 2026-09 六膳门项目两轮工作沉淀，全部是实际用过并验证的做法。客户专有的数字、底线、让步阶梯不在本文件，
> 在各项目的 `docs/private/<客户>/`（gitignored）里。本文件是内部文件，用「」和——是为了好读，不受第三节约束。

## 一、工作流

1. **先定商务，再写条款。** 口头条件（价格、维护、免费功能、股权、退出）逐条判断写成决策备忘，创始人拍板后才起草。拍板记录是唯一商务依据，任何文件与它冲突以它为准。
2. **拍板记录逐条编号、只增不改。** 每条写：谁拍的、原话、落到哪一条、作废了哪一条。价格改多少次都不会乱。
3. **对抗审计多轮、换模型。** 自审 → Codex → Claude → Codex 再几轮；每轮出「拍板表」让创始人逐项决定，不让审计意见直接改稿。审计会把稿子推向法律中立，**审完再做一轮「谈判姿态」修正**，把开局就让完的位置收回当筹码。
4. **先核对方主体，再定交易结构。** 统一社会信用代码、注册资本、法人、股东穿透（签约主体与持股主体可能不是同一家）、融资历史、被执行 / 欠税 / 质押。签约与持股都对有厂有证的实体；上层 VC 主体作承诺方，不直接进股权关系。
5. **专业意见先用 AI 模拟、再找执业人士复核。** 税务师视角用 subagent 出初步意见，能提前发现结构性问题；数字、文号、税目必须执业人士确认。给律师 / 税务师的问题清单是活文件，每条标「已答 / 作废 / 待问」。
6. **改前必备份、改后必核验。** 批量改动先拷到 `_archive/日期-改前/`；改完跑 `tools/audit.py`，再核金额五处（正文、分期表、交付清单、税务列价、合作方案）一致。
7. **每处替换只许命中一次。** 脚本 `assert count == 1`；命中 0 或 2 都停下看。替换串要和**当前**文本一致（去加粗、去空格后旧串会失效），先 grep 现状再写。
8. **镜像条款逐字比对。** 同一段文字在两份文件里，改一处必改另一处并 diff 为空。
9. **一个目录、固定编号、四类子目录。** `00–NN-<名>.md` 与 docx 成对；`_outbound/` 发送稿、`_build/` 合并稿、`_archive/日期-改前/` 快照、`_sent-日期/` 已发出版。**发出后存快照，之后所有改动与它比。**
10. **对外与内部分离。** 让步清单、底线价、税务分析、审计报告全部内部；对外只有合作方案、合同、附件、独立协议。
11. **发 Word 不发 PDF**（对方要用修订模式），PDF 自己看排版。**不单独发送审函**——「几份文件、哪些是空、只签其一、请几天内回复」写在微信或邮件正文里，更不写进合同。
12. **发出后不改价、不改定义。** 能改的窗口是对方回修订稿那一轮，把要加的条款当成正常往返塞进去。

## 二、条款设计原则

1. **能拆就拆成独立文件。** 排他、股权这类有独立对价的安排单独成协议：独立对价、独立期限、独立退出，不与主合同价款或股权互锁。理由是税务（非货币对价按公允价值计税）也是谈判（对方律师改附件不牵动主合同）。
2. **对价必须是现金、有发票。** 「用股权换排他」两头吃亏；「A 元现金买 N 个月」对方能税前列支，反而好谈。
3. **价格从成本账推，折让有名义。** 开发费 = 许可 + 工日 × 单价 + 实施，每项对到模块表；折让名义是「创始客户价 / 股东价」，⛔ 不写成股权的对价（隐含估值 = 折让 ÷ 股比，会成为融资锚、并把「置换」的税务核定风险请回来）。低于成本的报价在内部标明「有意让利、终点不是开局」。
4. **三分列价保留但不为税。** 许可 / 技术开发 / 实施分列是让对方入账清楚。小规模纳税人不申请即征即退、不申请技术开发免税、不拆委托开发合同。合同税务句只写「不含税价；甲方现为小规模纳税人，按届时征收率开专票；身份变更按新税率、不含税价不变」。
5. **不写自我限制。** 「甲方不得仅以项目名称主张免税」这类对方没提、我方先写的句子一律删。
6. **不写自认。** 「主合同为关联交易」会被税务机关直接引用；删定性、留治理安排（回避表决）。
7. **每条正向承诺配边界。** 「新功能不收费」配：业务域内、每月 N 工日、我方排期、维护费在付、成果归我方。
8. **触发条件客观可核对。** 验收写「连续 5 个工作日线上录入、差异不超过 2%」，不写「稳定」「满意」；排他判定交第三方会计师匿名核验。
9. **限制只锁一个动作。** 排他只锁「为受限企业新实施正式生产部署」，演示、报价、签约、其他品类全放开；受限企业用许可证 + 公开 SKU 占比两个客观条件定义。
10. **时间锚点用验收日不用签约日。** 保护期、维护期、股权分期都从核心模块最终验收次日起算；验收前不承担排他。「起算日前已签署的项目不受限」是存量客户的保护——要抢在起算日前签的，就抢。
11. **给自己留退路，退路要定价。** 买断 = 剩余月数比例 × 对价 × 1.5；源码托管释放事件只列四项（破产 / 停服 30 日 / 停营 / 核心人员全无），不含「严重违约」。
12. **有股权才有长期承诺。** 三年领先期只随共创方式；采购方式一年。
13. **两版方案平等摆出，不引导。** 价格可以差，对外不写「建议选 X」，不列专门让某一版显得便宜的对比行；对比表每一行都问「这行是让谁显得便宜」。
14. **责任上限 + 例外 + 不重复。** 累计已付款 2 倍、各自独立限额、同一损害不重复、故意与重大过失除外。固定违约金作免举证保底、计入限额、实际损失更大可另行主张。
15. **不对称条款要有理由。** 泄密违约金我方高、对方低——数据在我方手里，不对称是信心信号，理由说得出口才写。
16. **关联方与上翻。** 乙方定义含其关联方（承诺方签字）；我方股权的知情权仅限持股主体本人行使、不得转让 / 质押给关联方、不得为关联方利益表决——防止查账权沿股权链上翻到对方的 VC。

## 三、文字标准（对外文件）

### 结构
- 按科技部《技术开发（委托）合同》示范文本：封面四要素（项目名称、签订时间、签订地点、有效期限）；导语「……经平等协商，在真实、充分地表达各自意愿的基础上，根据《中华人民共和国民法典》的规定，达成如下协议，并由双方共同恪守」；条款名用「名词和术语的解释」「验收标准和方法」「技术成果的归属与使用权」「有效期限、解除与终止」「其他约定」。
- 不用英式「鉴于：1. 2. 3.」，不用「一般条款」，不用「以资共同遵守」「本着……原则」。
- 保密协议作为附件一全文并入主合同；签署时仍同日单独签。
- 两份平行合同正文逐字相同，差异列成对照表。
- 对外文件里不出现内部编号（「04 号」「Q-10」）、版本号（v8）、日期以外的任何起草痕迹。

### 不写什么
- **不写关于文件本身的说明**：「本稿所列」「供审阅稿」「只签其一」「【待明确】」「以完全相同的文字列示」「本句不构成……」「（本条内容略）」。
- **不留占位标记**：「【　】」「【待定】」「【版本/日期】」「◆」。真正要填的用「＿＿」空线；带括号的默认值（【2】%）直接写实。
- **不写同义反复的防御句**：「本款不承诺无限期免费」「双方均确认该限额公平合理」——已有条款覆盖的不再重复。
- **不写「不承担任何责任」这类绝对句**，写成「在实际阻碍……且非甲方可归责的范围内」。

### 用词
- 常规中文合同词，不用英文直译或行业黑话：买断（不用「释放」）、核验（不用「清关」）、服务费减免（不用「服务积分」）、开发额度（不用「容量」）、责任限额规则（不用「统一责任结构」）、需求清单 / 产品规划 / 更新 / 整合（不用需求池 / 路线图 / 迭代 / 打通）、全流程（不用「闭环」）、缺陷（不用 Bug）。
- 缩写全部中文，**不加英文括注**：首笔款到账日（T0）、严重 / 重要 / 一般故障（P0 / P1 / P2 / Critical）、服务等级（SLA）、恢复时间 / 数据恢复点（RTO / RPO）、工日（人日）、回购权 / 卖出权（Call / Put）、端应用（App）、多因素认证（MFA）、接口（API）。保留 ERP / MES / AI / BOM / SKU / NFC 这类行业通用名和系统菜单原名。
- 金额写「人民币80,000元（不含税）」；不写大写、不写「¥」、不写「捌万元整」，不写「三（3）人日」这种中英双写。
- 单字母变量不进正文（A、n、H、M、r、q），改用文字。
- 「甲方」「乙方」直呼，不写「以下简称」。

### 排版
- 引号“”，不用「」。
- 汉字与数字、字母之间不留空格（「逾期30日」）；条款号后保留一个空格。
- 括号编号全角（a）（i），不用半角 (a)；同一层级用一种编号。
- 数字区间用「至」不用「–」；比较用「不超过」不用「≤」；清单用顿号不用「·」「→」。
- 只有条款小标题加粗，句中不加粗。
- 零破折号「——」、零比喻、第三人称、无「不是X是Y」式标题（依据：Anthropic Fable 5.1 文档 Writing density：有直白说法可用时就用它）。
- 黑白、宋体正文、黑体标题；目录只给长文件；附件各起一页。

### 句式
- 平均句长 35–43 字；超过 120 字只允许列举句；一句里「不」不超过 3 个。
- 长段拆成带编号的子款（11.2.1–11.2.5），对方律师只能逐款谈、不能整段划。

## 四、审计判据（每次改完跑 `tools/audit.py`，再人工看）

| 项 | 判据 |
|---|---|
| 解释性 / 占位 / 黑话 / 缩写 / 符号 / 内部痕迹 | 词表扫，发送稿为 0；命中逐条看上下文（「AI建议」「按比例折算」「取代此前草案」是合法用法） |
| 排版 | 汉字-数字空格、半角括号、句中加粗、「」、—— 均为 0 |
| 交叉引用 | 每个「第X.Y条」「附件N」在本文或指明的另一文件里落到实处 |
| 金额 | 正文、分期表、交付清单、税务列价、合作方案五处一致；分列之和等于总额 |
| 两版一致 | 平行合同 diff，差异全部落在对照表内 |
| 页数 | 与上一版比，页数变化能逐节解释 |
| 镜像 | 共同条款逐字相同 |
| 发出后 | `_sent-日期/` 快照，所有改动与它比 |

## 五、踩过的坑

- 重编号附件先改单个附件名、最后改「附件一至附件N」总称（反了会串）。
- 「折算」「释放」「建议」「草案」在别处有合法用法，残留检查要看上下文。
- 一次改多个文件、半途断言失败 → 从备份还原再重跑，或摘掉已完成段只跑剩余；⛔ 不要直接重跑。
- 编辑工具拒绝直接改主目录时用脚本落盘，⛔ 不要拷进 worktree 再拷回——两份副本一定漂。
- 拆独立协议后，主合同里所有指向旧附件的引用（第十条、责任限额、送达、承诺义务表、股权文件的折算与退出）一次清完。
- 法条引用是 AI 凭记忆核的，多处标「需核实」（税法文号、2025 年反法新条号、公司法配套解释）；签前律师过一遍。
- 示范文本以委托方为甲方；本包沿用客户自己保密协议的「白垩纪 = 甲方」，对方提了再谈，不主动改（牵涉数百处）。
- 税务意见是 AI 模拟的：方向可信，数字、文号、税目要执业税务师复核。
