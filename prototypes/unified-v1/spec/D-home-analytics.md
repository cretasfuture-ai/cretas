# 第一部分 · 跨页 AI 协议（A/B/C/D 四线共用）

本协议是实现线的约束，不是愿景。每条都写了「代码怎么判定」，实现与验收都按它对表。

## P1 唯一入口：悬浮窗

1. 全站只有一个 AI 容器：共享悬浮窗（现有实现见 DESIGN.md「计划/配置解读采用 UCard、UTextarea 和单一悬浮窗」，组件库第 15 类 ai-contextual）。不再新建页内聊天框、右栏 AI 卡片或第二个对话层。
   - 可拖动（标题栏拖柄 + 键盘方向键移动）、可调宽（左边缘拖柄，最小 360px，最大视口宽 60%）。
   - 位置与宽度按「账号 + 工作区」记在浏览器，刷新恢复；视口变小时夹回可见区域，不允许整窗跑出屏幕。
   - 覆盖式浮层，不占主内容列；打开/关闭前后主表宽度不变（现有验收：1288px 不变，ai-domains-floating-delivery.md）。
   - 原业务弹窗/抽屉打开时自动收起，关闭后不自动重开（DESIGN.md「原业务弹窗打开时收起生产 AI 面板」）。
2. 页面里只放「触发按钮」，不放 AI 内容本身。每页同一对象最多一个触发按钮，按对象分两类：
   - 列表/筛选范围：放在标题右侧主操作旁，次要按钮样式，文案「〈目的〉分析」，如「执行分析」「采购分析」「预警归因」。
   - 单条记录：放在该行「更多」或详情头部，文案「解读〈对象〉」，如「解读计划」「解读这张单」。
   - 创建草稿是另一类任务（描述建单、生成工序），沿用原创建权限，不和解读合并、不算作重复。
   - 一个页面出现第三个 AI 触发按钮即视为重复，必须合并（原则 4）。
3. 文案规则：
   - 按钮说目的，不说技术：用「核对缺料」「解读计划」，禁止「AI 分析」「智能洞察」「问 AI」「AI 初筛」作按钮名或区块标题。
   - 旁边一个问号（`CretasUI.help`），回答三件事：分析谁（对象/范围）、能解决什么、不会做什么（不改单据、写操作需确认）。
   - 界面不出现设备名、主机名、模型名（Mac mini、qwen3:8b、canada-mini 等）；来源统一写「本机规则」或「解读服务」。
4. 悬浮窗固定结构（自上而下）：当前对象条 → 问题输入（独占一行，按钮下一行右对齐）→ 状态条 → 结论 → 依据 → 建议动作 → 历史。

## P2 统一动线

```
遇到异常 → 就地点触发按钮 → 自动带入当前对象 → 结论与依据 → 建议动作 → 预览 → 确认执行 → 回读结果
```

1. 自动带入当前对象：触发时由页面传入结构化上下文 `{workspace, objectType, objectId|filter, version, sourceHash}`，悬浮窗顶部显示为可读文字，例：「计划 PLAN-0012 · 工序 v3 · 配方 v4」「采购单 · 当前筛选 12 条（关键词“鸡腿”，10/01–10/31）」。用户可点「改用当前筛选/当前选中」切换，不自动改。对象类型：计划、工序节点、BOM 版本、工单、批次、单据、筛选范围、报表文件+工作表。
2. 结论与依据：依据逐条可点，点后在主页面定位原单/节点（打开详情侧栏或滚动高亮行），悬浮窗不关。依据最多展示 20 条，汇总用全部匹配记录（沿用 ai-domains-floating-delivery.md 口径）。
3. 建议动作：只能是该页面已有的操作（含原处理器），以按钮出现，点后进入预览，不直接执行。
4. 预览：显示对象、字段「改前 → 改后」、影响范围、恢复方式（组件库第 9 类 diff-unsaved、第 16 类 ai-preview-confirm）。
5. 确认执行：调用原领域接口，不走通用分析接口。
6. 回读结果：执行后独立 GET 一次，用回读值渲染结果，不用请求体回显。
7. 三种状态分开显示（同一时刻可并存，各有独立标记，不合并成一个「完成」）：

| 状态 | 何时出现 | 标记文案 | 代码判定 |
|---|---|---|---|
| 回答完成 | 解读任务结束且通过 P3 校验 | 「解读已完成 · 未改动业务数据」 | 任务 status=DONE 且 proof 校验通过 |
| 草稿已保存 | 用户保存解读或备注草稿 | 「草稿已保存 · 尚未执行」 | 草稿写入接口 2xx 且回读一致 |
| 业务已完成 | 用户确认执行且回读一致 | 「已执行 · 回读一致」+「查看记录」 | 领域接口 2xx 且独立回读字段与预览改后值一致；不一致显示「已提交，回读不一致」并给原单入口 |

## P3 分工边界：代码定口径，模型写解释

1. 代码负责（事实层，按领域一个 facts 模块，参照 `tools/ledger-facts.cjs`）：
   - 口径与计算：合计、差额、比例、待发/待收、超期、单位换算禁止跨单位相加。
   - 值的类型：每个数值标 `zero`（已记录 0）/ `missing`（未填/缺字段）/ `invalid`（格式错）/ `value`；渲染时 missing 显示「—」并写「未填写」，绝不显示 0。
   - 状态：取消单排除待执行但保留历史；关单不再算待发；未识别状态不给完整结论。
   - 数量与金额分列，币种分列；零分母（零产出、零人时、零样本）不做除法，显示「无法计算：〈原因〉」。
2. 模型负责（只写这些）：解释、归因线索、下一步核对方向、「找谁补」（岗位或单据责任人）。
3. 模型数字绑定校验（每次输出都跑）：
   - 严格模式（数量/金额/状态类领域，领料已采用）：模型只返回核对代码数组 `reviewCodes`，正文由代码按代码表渲染；额外文本、未知代码、不适用代码 → 整次拒绝。
   - 解释模式（经营、图表、预警归因等需要自然语言的领域）：正文按段落切分，每段抽出所有数字（含百分比、日期、带单位数）→ 与事实表做「值+单位+对象」匹配；任一数字不在事实表或单位不符 → 该段标为「未通过校验」，折叠在「未核实内容」下，不作为结论展示。
4. 校验通过 ≠ 判断全对，再做矛盾检查（规则表，代码执行）：
   - 事实为 `zero` 而正文称「缺失/未填」，或事实为 `missing` 而正文称「为 0」→ 段落拒绝。
   - 事实差额为负而正文写「上升/增加」，或反之 → 段落拒绝。
   - 状态为 CANCELLED/CLOSED 而正文建议「补发/继续执行」→ 段落拒绝。
   - 同一回答内两段对同一对象给出相反结论 → 两段都标「互相矛盾，待人工判断」。
   - 现有已知问题：本地模型会把已记录 0 说成可能缺失（reports-typeset-delivery.md「已知限制」），本条就是为它设的拦截。
5. 段落级标记：结论区每段右上角显示来源「系统计算」或「解读（已核对数字）」；被拒段落不显示为结论。

## P4 异常态模板

| 状态 | 判定 | 悬浮窗显示 | 用户能做什么 |
|---|---|---|---|
| 缺数据 | 事实层返回所需字段 missing 或记录数 0 | 「缺少：〈字段/单据〉，来源：〈页面〉」；不给结论，只列缺口 | 「去补录」跳到对应页面；「仍按已有数据解读」（结论带缺口标注） |
| 无权限 | 当前账号对对象或建议动作无读/写权 | 「当前账号不能〈查看/执行〉此项」，不显示对象内容 | 可看自己有权的部分；写建议显示为只读文本 + 「找谁处理」 |
| 依据过期 | 对象 sourceHash 与缓存不一致，或规则版本升级 | 旧结论置灰，标「依据已变化（〈时间〉后有修改）」 | 「按当前数据重新解读」；旧结论保留在历史 |
| 模型不可用 | 解读服务连接失败/超时 | 「解读服务暂不可用」；规则分析照常输出（系统计算部分完整显示） | 「稍后重试」；规则部分可直接用 |
| 排队中 | 提交后未开始执行 | 「排队中，前面还有 N 个」+ 实时位置；可离开页面 | 「取消排队」（未开始的才可撤）；已开始的只能「停止等待」，不伪装为撤回 |
| 来源接口报错 | 报表/能力接口返回 404/502/503 等 | 显示真实状态码与接口名，例「经营报表来源返回 503（未开放）」 | 「重试」；不得用演示数据或 0 顶替 |

## P5 权限原则

1. AI 能做的 = 该账号在界面里本来就能做的。建议动作在渲染前用同一前端权限判断 + 执行时由领域接口服务端鉴权；菜单隐藏不代替服务端鉴权（权限梳理与界面蓝本-V4）。
2. 写操作一律「预览 → 确认」，没有「自动执行」开关。Workflow 生成/发布仍受原生成权限约束，不能借解读接口绕过（DESIGN.md「AI 与权限」）。
3. 关闭模块的数据不进入 AI 上下文；工作区之间（味美/六膳门）上下文不串。六膳门只读黑湖来源，任何建议动作在六膳门工作区只能写本机核对资料，不回写黑湖。
4. 抄送、已处理等「知悉」关系不产生处理权，AI 也不产生。

## P6 历史与复用、排队与用量

1. 缓存键：`workspace + objectType + objectId|filterHash + sourceHash + ruleVersion + question`。命中则直接显示，不再调用模型（六膳门已实现「查看保存答案不会再次提交模型」）。刷新恢复最近一次结论与窗口状态；对象变化后只默认展示匹配当前对象的结论，其它进历史。
2. 历史：按对象分组，列「时间 / 问题 / 状态（有效 / 依据已变化 / 未通过校验）」，旧未校验解读保留但不作有效答案（ledger-truth-delivery.md）。
3. 取消人为限流，改为排队：现状 `tools/online-bridge.cjs:1` 同时 4 个、队列满 64 返回 429「在线请求队列已满，请稍后重试」。改为：并发数按解读服务实际能力配置；超出即排队，不拒绝；队列持久化（刷新/离开页面后仍在排、结果按缓存键落地）；同一缓存键重复提交合并为一个任务。是否设最长等待时间待裁定（见第三部分）。
4. 用量记录：每个任务记 `promptTokens / completionTokens / 耗时 / 排队时长 / 是否命中缓存 / 校验结果`；仅管理员可见（建议放「系统组件/原型与来源」之外的管理员设置页），普通用户界面不显示。
5. 页面打开不自动调用模型。现状岗位工作台一打开就自动发默认问题（见 D2），改为显示上次缓存结论 + 「更新」按钮。

### 5 AI 处理点
- 触发位置与文案：右栏待办下方，「核对计划」+ 问号（分析当前工作区全部计划的状态、交期与数量口径；不改计划）。
- 当前对象：当前工作区、全部未取消计划；首页状态筛选生效时带入筛选（例「已超期 1 条」）。
- 输入依据：计划编号、成品、计划量与单位、交期、状态、绑定工序/配方版本、领料待办；来自首页只读投影 `tools/home-overview.cjs`。
- 代码确定：状态计数、超期天数、取消/草稿/暂停排除规则、单位分列、缺失显示「—」。
- 模型生成：先核对哪几条、为什么、找谁（计划员/仓库/采购）。
- 输出形态：结论 → 依据（计划编号可点，跳计划页并定位该行）→ 建议动作（只有导航类：去计划页、去领料）→ 无写操作，不需要预览。
- 三种状态：本页只有「回答完成」；「草稿已保存」指保存解读；不会出现「业务已完成」。
- 异常态：无计划 → 「当前工作区没有计划」不调用模型；解读服务不可用 → 规则部分（超期清单、缺版本清单）照常显示。
- 模型路由：本地解读服务优先，不可用时规则输出；不显示设备/模型名。
- ⛔ 不做：不改计划状态、不改交期、不代替计划页「执行分析」另算一套口径（同一缓存键、同一事实模块）。

### 6 不该用 AI 的地方
状态计数、超期判定、待办数量、常用入口排序、最近保存列表，全部由只读投影代码计算；排序用拖柄与前后按钮。

### 7 验收用例
1. 打开 `/dashboard?acceptanceSession=spec-d` → 点「已超期」格 → 列表只剩超期计划 → 点行内「查看」进入计划页 → 返回首页，状态筛选仍是「已超期」。
2. 「调整常用」→ 用拖柄把第 1 个入口拖到最后 → 松开自动保存（Toast「已保存常用入口」带「撤销」）→ 刷新 → 顺序保持 → 换另一浏览器登录同账号回读（若裁定按账号保存）。
3. 编辑态拖动时按 Esc → 顺序不变、影子清除；尝试添加第 13 个入口 → 明确提示上限，旧入口不被挤掉。
4. 点「核对计划」→ 悬浮窗显示对象「当前工作区 · 全部计划 N 条」→ 完成后点依据中的计划编号 → 主页面跳到计划页并高亮该行 → 刷新首页再开悬浮窗 → 显示缓存结论，未再次调用模型（用量记录无新增）。
5. 首页「原料批次」与分析概览、进销存、数据完整度四处同一工作区计数一致（阴性对照：现状 3 / 0 不一致应判失败）。
6. 阴性：在空工作区打开首页 → 计数显示 0（已收录 0 张），业务概况缺来源的项显示「—」而非 0；「核对计划」显示「没有计划」不提交任务。
7. 顶栏「搜索菜单」可搜到全部入口，页头不再有「全部应用」。

### 8 依赖与数据缺口
- 依赖：`tools/home-overview.cjs` 只读投影、`public/home-workspace.js`、生产计划页（A 线）执行分析缓存键、领料/采购/销售列表筛选参数（A/C 线）、统一外壳工作区头。
- 缺口：当前味美工作区仅 1 条计划，采购单 0、销售单 0，待办 3 项全 0，无法验证列表分页与多状态；分析概览计数不一致根因未查明；六膳门工作区是否有首页（其菜单只有成本等少数页面）未实测。

## D2 岗位工作台（销售跟进 / 生产安排 / 仓库任务 / 采购安排）

所属线：D 首页与分析
使用的角色：销售负责人、生产经理、仓管员、采购员；每天开工时看本岗位要跟进的事项。

### 1 一句话目的
按岗位视角列出今天要跟进的单据清单，并给出一份可回看的跟进建议，点任一条进入原单处理。

### 2 现状问题（带证据）
1. 打开即自动调用模型：`/workdesk/production-manager` 打开后立即显示「正在核对当前记录、状态与数量口径…」，约 8 秒后生成「排产建议清单 19:35:02 生成」。问题：每次进入都消耗解读服务，违反 P6.5；页面主体被等待状态占据。
2. AI 内容在主列：页内「起产建议」输入框 + 「发送」，结果直接排在主内容区。问题：违反 P1 单一悬浮窗。
3. 标题与内容不符：区块标题「排产建议清单」，内容实际是「生产计划 · 记录核对」与字段原样列举。问题：承诺了排产建议，给的是记录核对。
4. 技术用语外泄：输出含「IN_PROGRESS」「0是已记录零值；空白/null是未填写」「状态分布：IN_PROGRESS 1条」；销售视角空态写「请联系销售员录入 sales_orders」。问题：用户看到枚举和表名。
5. 命名三套：侧栏「岗位工作台 → 销售跟进/生产安排/仓库任务/采购安排」；页面标题「销售老板工作台/生产经理工作台」；页签同旧名。证据：`/workdesk/*` 截图。
6. 销售视角重复标题：「B2B 销售实时数据」「B2B 销售真业务数据」「实时统计」三层抬头 + 一段「并非示例」说明。
7. 仓库任务、采购安排视角本轮未打开（未查明其现状）。

### 3 目标信息层级
首屏回答：今天本岗位要跟进几件？哪几件最急？点哪里去处理？
- 导航与任务：侧栏「岗位工作台」下 4 个视角，页内顶部用分段切换（同一路由族，切换保留各自筛选），页面标题与侧栏一致。
- 当前对象：视角名 + 范围（例「生产安排 · 今天 · 全厂」）。
- 主操作与筛选：日期（今天/本周）、状态；右侧「起产建议」触发按钮（各视角文案不同）+「刷新」。
- 业务内容：紧凑任务列表（单号、对象、数量+单位、截止、状态、行内「处理」→ 原单）。销售：待发清单、待跟进订单；生产：待起产/受阻计划；仓库：待收/待发；采购：缺口与待下单请购。
- 详情与 AI：悬浮窗显示建议；首屏不展示长文本。
- 不放：页内聊天输入框、默认问题自动发送、原始字段逐条罗列。

| 按钮名 | 作用对象 | 点击结果 | 区 | 处置 |

| 视角切换 ×4 | 岗位视角 | 切换列表与建议对象 | 导航 | 保留（新增页内分段，与侧栏同步） |

### 5 AI 处理点
- 触发：主操作区按钮，文案按视角：「跟进建议」（销售）、「起产建议」（生产）、「收发安排」（仓库）、「采购安排」（采购）；问号说明范围与「不下单、不审批、不改计划」。
- 当前对象：本视角当前筛选（日期、状态）下全部匹配单据。
- 输入依据：销售订单/发运（C）、生产计划/批次/领料（A）、入库/出库任务（C）、请购与缺料（C/A）；缺哪个来源就列为缺数据。
- 代码确定：待发=订购−已发（取消/短交关闭除外）、待起产与受阻判定（缺版本、缺料）、待收、缺口数量；单位分列。
- 模型生成：先后顺序理由、核对方向、找谁。
- 输出形态：结论（3 条以内）→ 依据（单号可点定位）→ 建议动作（只导航到原单）→ 无写操作。
- 三种状态：回答完成 / 草稿已保存（保存建议）分开；无业务执行。
- 异常态：销售来源无记录 → 「暂无销售订单」，不调模型；解读服务不可用 → 列表与规则排序照常。
- 模型路由：同 P1/P4；不显示设备与模型名。
- ⛔ 不做：打开页面自动调用；在输出中显示英文枚举、字段名或表名（由代码翻译为中文状态）；替用户下单、审批、改计划。

### 6 不该用 AI 的地方
待办清单本身、紧急程度排序（按截止日与状态的确定规则）、状态翻译、空态判断，全部代码完成。

### 7 验收用例
1. 打开 `/workdesk/production-manager?acceptanceSession=spec-d` → 网络面板无模型请求；显示上次缓存的「起产建议」或「尚未生成」。
2. 点「起产建议」→ 排队/生成 → 结论中无 `IN_PROGRESS`、`null`、表名 → 点依据中的计划号 → 跳计划页定位 → 返回后视角与筛选保持。
3. 切到「仓库任务」再切回「生产安排」→ 生产视角筛选保持，悬浮窗对象随视角切换，旧结论进历史。
4. 刷新页面 → 悬浮窗位置、宽度和上次结论恢复，用量记录无新增。
5. 阴性：销售视角无订单 → 列表空态「暂无销售订单」，「跟进建议」按钮可点但直接返回「缺数据」，不提交模型任务。
6. 阴性：用只读账号（若有）打开采购视角 → 建议中不出现「去下单」按钮。

### 8 依赖与数据缺口
- 依赖：A 线计划/批次/缺料事实；C 线销售/采购/库存事实；`list-analysis.js` 现有列表分析事实层。
- 缺口：味美工作区销售订单 0、采购单 0，销售/采购视角只能验证空态；仓库、采购视角本轮未打开；生产视角「受阻」所需缺料事件数据未核对。

## D3 个人 OA（审批中心：待我处理 / 我发起的 / 已处理 / 抄送我的）

所属线：D 首页与分析
使用的角色：所有有审批或发起审批的人；处理自己的待办、追踪自己发起的申请、复查历史与知悉抄送。

### 1 一句话目的
在一处按「与我的关系」切换查看审批单，处理我有权处理的那一张，其余只读。

### 2 现状问题（带证据）
1. 四个视图头部不一致：`/workflow/pending` 标题「OA 审批中心」、无记录数无刷新；`/workflow/my-created` 标题「我发起的审批 · 0 条记录 · 刷新」；`/workflow/copied`「抄送我的 · 0 条记录 · 刷新 · ?」。问题：同一模块四种头部，不像一个中心。
2. 名称不一致：侧栏子项「待我处理」，页面/页签「待我审批」。
3. 空表也出现横向滚动条：待我审批表 9 列（业务类型、业务单据、金额、往来单位、修正内容、当前节点、申请人、提交时间、操作），无数据时仍有横向滚动条。证据：800px 截图。

5. 与其它审批入口关系不清：「待审批请购」（采购）、「报工审批」（生产）各自独立，本轮未查明是否同时进入「待我处理」。菜单搜索「审批」命中三处。
6. 无任何审批依据解读入口（是否需要，见第 5 项）。

### 3 目标信息层级
首屏回答：有几张等我处理？最早的是哪张？我发起的卡在哪个节点？
- 导航与任务：侧栏「个人 OA → 审批中心」；页内四个分段（待我处理 N / 我发起的 / 已处理 / 抄送我的），切换保留各自筛选。
- 当前对象：分段名即关系；进入详情时显示单据号。
- 主操作与筛选：业务类型、时间范围、关键词；「刷新」。待我处理分段支持勾选批量「同意」（仅当原流程支持批量）。
- 业务内容：紧凑列表，统一列（单据、类型、金额+币种、往来单位、当前节点、申请人、时间、操作），修正内容进详情；空表不出横向滚动。
- 详情与 AI：右侧详情抽屉显示单据、修正前后差异、审批记录、原单入口；「解读审批依据」触发按钮只在待我处理的详情里出现。

### 5 AI 处理点
- 触发：仅「待我处理」详情头部，「解读审批依据」+ 问号（说明这张单改了什么、与历史同类单差异；不替你审批）。
- 当前对象：单张审批单及其关联业务单据当前版本。
- 输入依据：修正内容前后值、金额、往来单位历史同类单（未查明接口是否提供，缺则明说）。
- 代码确定：差异字段、金额变化额与比例、是否超过已有阈值。
- 模型生成：可能原因、需要向申请人确认什么。
- 输出形态：结论 → 依据（差异行可点）→ 建议动作只有「同意/驳回」两个原按钮的定位，不预填意见、不代点。
- 三种状态：只有「回答完成」；审批结果属于用户操作，由原流程显示。
- 异常态：抄送/已处理/我发起的分段不显示该入口（无处理权）；关联单无权查看 → 「无权限」。
- 模型路由：同协议。
- ⛔ 不做：代替审批决定、批量审批建议、在抄送视图出现任何处理动作。

### 6 不该用 AI 的地方
审批流转、节点判断、可处理权限、列表计数与筛选全部代码；差异计算由代码。

### 7 验收用例
1. 在隔离会话 `?acceptanceSession=spec-d` 造一张待审单 → 「待我处理」显示计数 1 → 打开详情 → 「原单」跳转 → 返回列表筛选保持。
2. 同意（确认弹窗）→ Toast「已同意」带「查看记录」→ 刷新 → 该单出现在「已处理」，不在「待我处理」。
3. 切换四个分段，头部、刷新、筛选位置一致；空表无横向滚动。
4. 阴性：「抄送我的」中同一单据详情无同意/驳回、无解读按钮。
5. 阴性：「已处理」分段打开历史单，不出现「重新审批」。
6. 「解读审批依据」（若实现）→ 依据中差异行可点定位 → 刷新后结论从缓存恢复。

### 8 依赖与数据缺口
- 依赖：原 workflow 接口；请购（C）与报工撤回（A）的原生审批是否汇入「待我处理」需确认。
- 缺口：味美四个视图当前均为 0 条，无法验证列表与详情；审批「修正内容」字段结构未查明；同类单历史接口未查明。

### 5 AI 处理点

- 异常态：识别服务不可用 → 照片照常进入待审核，标「未识别，请人工全检」。

### 5 AI 处理点

- 异常态：切换工作表 → 旧结论标「范围已变化」，提示「改用当前工作表」；解析失败 → 显示真实错误，不保存。
- ⛔ 不做：在保存前用模型改值或猜映射。

### 6 不该用 AI 的地方
