## 0.2 共用规则（本线所有页面）

- **AI 落点（DECISIONS A3，20:45 后修订）**：本线不自带悬浮窗。下文各页「悬浮窗」均指 D 维护的统一 AiFloat；本线只提供不画界面的适配器 `src/collab/e-ai-adapter.ts`（对象 `inspection` / `task` 的标签、事实、解读、草稿与确认写入）。AiFloat 接入前，页面内只显示规则算出的「核对方向」（标「系统计算」），任务草稿只用系统规则整理；模型解读与模型草稿在 AiFloat 接入后启用。检验标准页、不良分析页不需要 AI。
- 来源标记与格式改用 D 共享件（`sourceTagHTML`：黑湖 / Cretas 补充 / 味美 / 系统计算；`fmtQty` / `fmtNumber`），不另写。

- 工作区隔离：味美与六膳门各自一份保存文件；切换工作区不串数据。六膳门的对象选择器只列黑湖快照对象；味美的对象选择器只列味美接口返回对象，接口返回 0 条时显示「味美当前无该类单据」并允许手填编号（标「未核实引用」）。
- 会话：`?acceptanceSession=test-*` 写入独立会话文件；名称不合规时接口返回 400「会话名称必须以 test- 开头」，不回落默认区。不带参数时写本机原型默认区。
- 格式：数量两位小数 + 单位；缺失显示「未填写」，不显示 0；日期 `YYYY-MM-DD HH:mm`。
- 写入一律：填写 → 保存 → 接口返回后**独立 GET 回读**，页面用回读值渲染并提示「已保存 · 回读一致」；不一致提示「已提交，回读不一致」。
- 并发：每次写入带 `expectedVersion`，版本冲突返回 409「数据已被更新，请重新读取」。
- 设计：`--cs-*` 变量、frame.css 共享类（card / table / state / uni-ai-*），表格行高 32–33px，行内按钮两个字。

## E1 质量检验列表（按阶段）
所属线：E 质量与协同任务
使用的角色：质量经理、品控员；每天看「哪些检验还没做完、哪些不合格还没处置」。

### 1 一句话目的
按阶段（来料、生产、入库、发货、其他）查看并处理检验单，先看不合格与未完成。

### 2 现状问题（带证据）
1. 两个工作区都没有阶段化检验入口：味美「质量管理」只有包装标签拍检（`menu-map.json` 中质量组唯一页面 `/quality/label-qc`）；六膳门菜单目录同样只有该项（`liushanmen-v1/public/menu-catalog.json:323`）。问题：来料、过程、入库、发货的检验无处记录。
2. 味美首页 `reports/dashboard/quality` 返回 `qualityGrade:"D"`、`defectRate:100`，但 totalInspections=0（`factory-baseline.json`）。问题：0 样本时给出等级和不良率是错误口径；本模块统计在 0 样本时显示「无检验记录，无法计算」。
3. 黑湖快照没有检验资源（见第 0 节）。问题：不能假装「读黑湖检验数据」，必须明示是 Cretas 补充。

### 3 目标信息层级
首屏回答：每个阶段各有多少张未完成 / 不合格待处置？哪张最急？新检验从哪里开？
- 导航与任务：侧栏「质量管理 → 质量检验」；面包屑显示工作区。
- 当前对象：无（列表页不强加当前记录）；选中一行时该行成为悬浮窗对象。
- 主操作与筛选：标题右侧主按钮「新建检验」；阶段页签「全部 / 来料 / 生产 / 入库 / 发货 / 其他」，页签上带计数；状态下拉（全部 / 草稿（未提交）/ 不合格 / 合格 / 已作废）；提交时必须选处置，所以不存在「不合格未处置」的已提交单；关键词（单号、对象编码/名称）。
- 业务内容：紧凑表格列：检验单号、阶段、检验对象（编码 · 名称）、关联单据、标准（名称 + 版本）、判定（代码算）、处置、检验人、检验时间、来源标签、行内「详情」。
- 详情与 AI：详情抽屉（E2）；悬浮窗对象 = 选中检验单。
- 不放：图表、合格率大卡（样本 0 时无意义；有样本后在页签计数旁给「合格率 xx.xx%（n 张）」小字）。
- 阶段说明折叠在每个页签的问号里：来料 = 供应商到货验收（证件、外观、温度）；生产 = 工序过程检验（对象为工单/工序）；入库 = 原材料入库前检验（存储条件、包装、保质期）；发货 = 成品出厂检验；其他 = 不属于以上的专项（如留样复检）。

## E2 检验单详情与录入
所属线：E 质量与协同任务
使用的角色：品控员录入结果；质量经理确认处置。

### 1 一句话目的
按该阶段的检验标准逐项录入结果，由代码判定合格与否，再由人选择处置。

### 2 现状问题（带证据）
1. 无既有录入页（同 E1-1）。
2. 风险：如果由模型给出「合格/不合格」，会把解读当真值（D 协议 P3）。本页判定只由代码按标准上下限计算。

### 3 目标信息层级
首屏（抽屉顶部）回答：检的是什么？结论是什么（哪几项不合格）？下一步谁处理？
- 当前对象条：检验单号 · 阶段 · 对象（编码/名称/来源标签）· 关联单据。
- 主操作：草稿态「保存草稿」「提交结果」；已提交「作废」（需原因）；不合格时「生成任务」。
- 业务内容（三段）：
  1. 基本信息：阶段（新建时可选，提交后锁定）、对象类型由阶段决定（来料/入库 = 原材料；生产 = 工单；发货 = 成品；其他 = 任意并手填）、对象（选择器）、关联单据、抽样数量 + 单位、检验人、检验时间。
  2. 检验项结果：取自所选标准的当前版本，逐行：项目、方法、标准（下限–上限 单位 或「判定项」）、实测值 / 判定、单项结果（代码算：合格 / 不合格 / 未填写）。
  3. 判定与处置：总判定（代码算：任一不合格 → 不合格；必检项有缺 → 未完成；否则合格）；处置（人选：放行 / 让步接收 / 拒收 / 返工 / 复检），不合格时不能选「放行」，选「让步接收」必须写原因。
- 留痕：底部折叠「修改记录」（谁、何时、改了什么、原因）。
- 不放：模型生成的判定、业务单据的冻结/放行开关。

### 4 按钮与入口清单
| 按钮名 | 作用对象 | 点击结果 | 区 | 处置 |
|---|---|---|---|---|
| 保存草稿 | 本检验单 | 写入草稿 → 回读 | 主操作 | 新增 |
| 提交结果 | 本检验单 | 校验必填 → 预览判定与处置 → 确认 → 写入 → 回读；提交后阶段、对象、标准版本锁定 | 主操作 | 新增 |
| 作废 | 本检验单 | 填原因 → 确认 → 状态改「已作废」，原记录保留 | 主操作（危险） | 新增 |
| 生成任务 | 本检验单（不合格） | 悬浮窗进入「整理成任务草稿」，带入不合格项 | 判定区 | 新增；与 E6 同一流程 |
| 解读 | 本检验单 | 悬浮窗「解读这张检验单」 | 悬浮窗 | 唯一 AI 入口 |

### 5 AI 处理点
**解读这张检验单**（严格模式）
- 触发：悬浮窗；对象 = 当前检验单（已提交或草稿均可）。
- 输入依据：阶段、对象、标准名称与版本、逐项实测值与上下限、单项结果、缺项、处置、关联单据。全部来自本地保存区。
- 代码确定：单项结果、总判定、偏离量（实测 − 上限 或 下限 − 实测，两位小数，单位同标准）、缺项列表、按阶段 + 判定得出的「允许核对代码」集合。
- 模型生成：只从允许的核对代码里选最多 3 个（例：RECHECK_SAMPLE 复检留样、ISOLATE_LOT 隔离该批、CHECK_SUPPLIER_CERT 核对供应商证件、NOTIFY_PURCHASE 通知采购、CHECK_PROCESS_PARAM 核对工序参数、CHECK_STORAGE 核对存储条件、HOLD_SHIPMENT 暂缓发货、CONFIRM_STANDARD 确认标准是否适用、FILL_MISSING 补录缺项）。正文由代码按代码表渲染，含「找谁」（采购 / 生产主管 / 仓库 / 质量经理）。
- 输出：结论（代码判定 + 偏离项）→ 依据（逐项，可点击在抽屉中高亮该行）→ 建议动作（核对代码对应文字；其中可执行的只有「整理成任务草稿」）→ 预览 → 确认 → 回读。
- 三种状态：「解读已完成 · 未改动业务数据」/「任务草稿已生成 · 尚未保存」/「任务已创建 · 回读一致」分开标记。
- 异常态：模型不可用 → 显示「解读服务暂不可用」，规则建议（按判定取默认核对代码）照常显示并标「系统计算」；未提交草稿缺项多 → 只列缺项，不给结论。依据过期（检验单 version 与解读时不同）→ 旧解读置灰「依据已变化」。
- ⛔ 不做：不改判定、不改实测值、不替用户选处置、不改业务单据状态。

### 6 不该用 AI 的地方
单项与总判定、偏离量、必填校验、处置约束（不合格不能放行）、状态流转、作废。

### 7 验收用例
1. 六膳门工作区（`?acceptanceSession=test-e-20261111`）：新建「来料」检验，对象选一条黑湖物料，选来料标准，填 3 项（其中温度超上限）→ 保存草稿 → 刷新 → 打开详情，值回读一致，单项结果「不合格」。
2. 提交结果：处置下拉中「放行」不可选；选「让步接收」不写原因 → 被拦；写原因后提交 → 刷新 → 状态「不合格 · 让步接收」，阶段与标准版本锁定。
3. 作废：填原因 → 列表状态「已作废」，详情仍可看原值与修改记录。
4. 阴性：标准为空（该阶段没有启用标准）时「新建检验」抽屉提示「该阶段还没有检验标准，先去配置」并给链接，不允许提交空检验。
5. 悬浮窗「解读这张检验单」：结论里的偏离量与表中一致；模型不可用时显示规则建议并标「系统计算」。

### 8 依赖与数据缺口
- 依赖：E3 标准；六膳门黑湖快照（物料、工单、产品）；味美对象接口（批次、计划、出货、成品类型——当前返回 0 条）。
- 缺口：味美没有可选对象时只能手填对象编号，标「未核实引用」；附件/照片上传本轮不做（拍检仍在 label-qc）。

## E3 检验标准（按阶段）
所属线：E 质量与协同任务
使用的角色：质量经理维护；品控员只读。

### 1 一句话目的
为每个阶段、每类对象配置检验项与合格范围，检验单按它判定。

### 2 现状问题（带证据）
1. 黑湖快照无检验标准资源（第 0 节）；DECISIONS「四之前」明确 E 线检验标准属于 Cretas 补充。
2. N7 要求标准跟着阶段走，不做通用检验项库：标准必须先选阶段，再选对象。

### 3 目标信息层级
首屏回答：每个阶段有哪些标准？覆盖了哪些对象、还缺哪些？最近谁改过？

## E5 任务详情（指派、截止、状态、评论、关联单据）
所属线：E 质量与协同任务
使用的角色：负责人更新进展；发起人跟进与关闭。

### 1 一句话目的
在一个地方完成任务的指派、改截止、推进状态、评论与查看关联单据。

### 2 现状问题（带证据）
新模块，无既有页面（同 E4-1）。

### 3 目标信息层级
首屏回答：要做什么、谁做、什么时候前？现在到哪一步？卡在哪里？
- 当前对象条：任务号 · 状态 · 截止（超期标红）· 来源。
- 主区：标题与说明；指派（负责人：岗位 + 姓名；「指派给 Agent」选项显示为禁用并带问号说明「预留：以后可由智能代理按任务说明执行只读核对；本轮不接执行，不会自动改任何数据」）；截止日期；优先级；状态按钮组（开始 → 完成；任意未结状态可取消，需原因；已完成可重新打开，需原因）。

- 评论：时间线（人、时间、内容）；输入框独占一行，「发表」在下一行右侧。
- 修改记录折叠：每次指派、截止、状态变化留痕（改前 → 改后、人、时间、原因）。

### 4 按钮与入口清单
| 按钮名 | 作用对象 | 点击结果 | 区 | 处置 |
|---|---|---|---|---|
| 保存修改 | 本任务字段（标题、说明、负责人、截止、优先级、关联） | 预览改前→改后 → 确认 → 写入 → 回读 | 主区 | 新增 |

### 5 AI 处理点
**概括任务进展**（解释模式 + 数字绑定）
- 触发：悬浮窗；对象 = 当前任务。
- 输入：标题、说明、状态、截止、超期天数（代码算）、评论时间线、关联单据清单、修改记录。
- 代码确定：状态、超期天数、评论条数、最近更新时间、未结关联单据。规则摘要（不需要模型）：「状态 · 截止 · 超期 n 天 · 最近一条评论（人、时间）」。
- 模型生成：2–4 句进展概括 + 卡点 + 建议下一步找谁。校验：正文里出现的每个数字必须在输入事实中出现，否则该句标「未通过校验」折叠；正文提到「已完成」而状态不是已完成 → 整段拒绝。
- 输出：规则摘要（系统计算）→ 模型概括（解读，已核对数字）→ 建议动作（可选「把概括发表为评论」：预览 → 确认 → 回读）。
- 三种状态分开：「解读已完成 · 未改动业务数据」/「评论草稿 · 尚未发表」/「已发表 · 回读一致」。
- 异常态：模型不可用 → 只显示规则摘要；评论为 0 条 → 提示「还没有进展记录，无法概括」，只给规则摘要。
- ⛔ 不做：不改状态、不改截止、不替人指派、不自动发表评论。

### 6 不该用 AI 的地方
状态流转与合法下一步、超期、留痕、关联跳转。

### 7 验收用例
1. 打开任务 → 负责人改为「采购」，截止改为后天 → 预览显示改前改后 → 确认 → 刷新 → 回读一致，修改记录 1 条。
2. 开始 → 发表评论「供应商已回复，周五补发证件」→ 刷新 → 评论在时间线 → 完成 → 状态已完成，列表不再计入超期。
3. 阴性：取消不填原因 → 被拦；「指派给 Agent」不可选，点击问号看到占位说明。
4. 关联单据点击六膳门工单编号 → 跳到生产工单页并打开该工单详情；返回协同任务仍在原筛选。
5. 「概括任务进展」：模型不可用时只显示规则摘要并标「系统计算」。

### 8 依赖与数据缺口
- 依赖：A 线生产工单详情的地址参数（当前统一入口 `#/production/plans` 支持；按单号打开详情需要 A 线支持 `?project=<id>`，暂未提供时只跳列表并提示单号）。
- 缺口：人员名单（同 E4）；Agent 执行不在本轮。

## E6 从异常或 AI 回答生成任务草稿
所属线：E 质量与协同任务
使用的角色：发现异常的人（品控、生产主管等）。

### 1 一句话目的
把一段异常说明（或一张不合格检验单、一条解读结论）整理成任务草稿，人确认后才创建。

### 2 现状问题（带证据）
异常说明目前只能停留在解读回答里（例：六膳门悬浮窗「核对记录」只存说明，不派给人，`src/frame/AiFloat.vue` 的 followup），没有截止和负责人。

### 3 目标信息层级
- 入口两处、同一流程：检验详情的「生成任务」（带入不合格项）；悬浮窗「整理成任务草稿」（任意页，粘贴或输入一段异常说明；若当前对象是检验单，自动带入）。
- 流程：输入说明 → 生成草稿（模型或规则）→ **预览**（标题、说明、负责人岗位、截止、优先级、关联单据，全部可改；每个字段标「解读建议」或「系统」）→ 确认创建 → 独立回读任务 → 「查看任务」。
- 不放：一键创建（跳过预览）、自动指派到具体人名。

### 4 按钮与入口清单
| 按钮名 | 作用对象 | 点击结果 | 区 | 处置 |
|---|---|---|---|---|
| 生成任务 | 当前不合格检验单 | 悬浮窗进入草稿流程并带入事实 | E2 判定区 | 新增 |
| 整理成任务草稿 | 输入的异常说明 / 当前对象 | 生成草稿 | 悬浮窗 | 新增（创建类，不与「解读」合并） |
| 确认创建 | 草稿 | 写入 → 回读 → 显示「已创建 · 回读一致」+「查看任务」 | 悬浮窗预览 | 新增 |
| 返回修改 | 草稿 | 回到输入 | 悬浮窗预览 | 新增 |

### 5 AI 处理点
**整理成任务草稿**（创建类，结构化输出 + 校验）
- 当前对象：输入文字 +（若有）当前检验单事实。
- 代码确定：关联单据候选集合（只能是当前对象及输入中出现、且在本工作区可核实的单号）；截止选项（今天 / 明天 / 3 天内 / 7 天内，代码换算成日期）；负责人岗位枚举；优先级枚举；检验单来源的不合格项清单。
- 模型生成：JSON `{title, description, role, dueOption, priority, relatedIds}`，枚举外的值整次拒绝；title ≤ 40 字；title/description 中出现的数字必须在输入或事实中出现，否则拒绝该字段并用规则值。
- 规则草稿（模型不可用或被拒时）：标题 = 「处理：」+ 输入第一句（≤ 40 字）；说明 = 原文；岗位按阶段（来料/入库 → 采购；生产 → 生产主管；发货 → 仓库；其他 → 质量经理）；截止 = 不合格 → 明天，否则 3 天内；优先级 = 不合格 → 高，否则中。标「系统规则草稿」。
- 输出：草稿预览（字段来源标记）→ 确认创建 → 回读。
- 三种状态：「草稿已生成 · 尚未创建」/「已创建 · 回读一致」分开；解读完成不等于任务已创建。
- 异常态：输入为空 → 按钮禁用；模型超时 → 自动给规则草稿并说明；关联单号在本工作区查不到 → 不放入关联，提示「单号 xx 未核实，未关联」。
- ⛔ 不做：不跳过预览、不指派具体人名（只到岗位，姓名由人填）、不跨工作区关联。

### 6 不该用 AI 的地方
截止日期换算、关联单号核实、枚举校验、任务创建与回读。

### 7 验收用例
1. 不合格检验单 → 生成任务 → 预览中关联单据 = 该检验单，岗位 = 采购（来料）→ 改截止为 7 天内 → 确认创建 → 回读 → 「查看任务」→ 协同任务列表出现，来源「检验异常」；刷新后仍在。
2. 悬浮窗输入「工单 S20260005-001-001 出料偏少，请生产主管核对报工」→ 整理 → 预览关联单据中出现该工单（六膳门可核实）→ 确认 → 回读。
3. 阴性：输入一个不存在的单号 → 预览提示「未核实，未关联」，不出现在关联里。
4. 阴性：模型不可用（或超时）→ 显示「系统规则草稿」，仍需确认才能创建；取消预览后列表无新任务。

### 8 依赖与数据缺口
- 依赖：本地解读服务；六膳门黑湖快照用于单号核实；味美对象接口（当前 0 条，味美单号只能标「未核实」）。
- 缺口：Agent 执行（占位）。

## E7 不良分析：不良品项字典 + 工序不良分布（BL-borrow 第 7 条，B7）
所属线：E 质量与协同任务（报工采集不良项由 A 线配合）
使用的角色：质量经理、生产主管；看不良集中在哪道工序、哪类问题。

### 1 一句话目的
维护不良品项字典，并按工序看报工记录里的不良数和不良率。

### 2 现状问题（带证据）

2. 黑湖报工 `output` 只有 `numberofGoodProducts` / `numberofDefectives`（2026-11-11 快照 428 条，非零不良 7 条，全部在「砍排修油」，合计 1,057.00 KG），没有不良项明细，也没有人员字段。
3. 味美工作区报工记录没有不良数量字段（统一入口会话文件里只有工序画布端口的 `defective:null` 标志）。

### 3 目标信息层级

- 主操作与筛选：报工日期范围、「只看有不良的工序」，写入地址。
- 业务内容：①按单位汇总（报工条数、良品、不良、不良率），不同单位不相加；②按工序明细（工序、单位、报工条数、含不良的报工条数、良品、不良、不良率），不良数降序；③按不良项：读 A 线 `GET /__unified/a/api/defect-captures`（报工详情「补录不良项」，Cretas 补充，合计不超过黑湖不良数），只算未撤销、且属于日期范围内含不良报工的记录，按「工序 × 不良项」汇总数量与占本工序黑湖不良比例，剩余单列「未分项」不估算（与 A 的 unallocated 同名）；无补录时显示「未采集 · 含不良报工 n 条 / 已补录 0 条」；A 接口不通时显式提示；④不良品项字典表（编码、名称、类别、适用工序、状态、来源「Cretas 补充」、最后修改）。
- 不放：按人员排名（BL-borrow 第 7 条「不该照搬」②）、AI 入口。

### 4 按钮与入口清单

### 5 AI 处理点
本页不需要 AI：比率是固定公式，字典值由质量人员填写（四之前原则：AI 不生成补充值）。

### 6 不该用 AI 的地方
不良率 = 不良数 ÷（良品数 + 不良数），同单位内计算；分母为 0 显示「无法计算：报工数量为 0」；报工不良数记为 0 时显示「0.00%（报工不良数记为 0）」，不当作「无不良」的结论；缺数量的报工不纳入并计数。

### 7 验收用例
1. 六膳门：不良分析显示 KG 单位不良 1,057.00 KG，「砍排修油」1.41%；勾「只看有不良的工序」→ 只剩 1 行 → 刷新保持。
2. 新建不良项「XG-01 碎骨残留 · 异物 · 适用工序 砍排修油」→ 预览 → 确认 → 回读 → 刷新仍在。
3. 修改不填原因 → 被拦；停用不填原因 → 被拦。
4. 阴性：味美工作区显示「报工记录没有不良数量字段，未采集不良数据」，不显示 0%。
5. 阴性：工序编码不在黑湖工序目录 → 接口拒绝。

### 8 依赖与数据缺口
- 依赖：黑湖报工与工序目录（只读）；A 线 `defect-captures` 只读接口（21:00 A 已交付，待 D 挂载）。
- 缺口：班组（黑湖无字段）；味美报工无不良数字段。
