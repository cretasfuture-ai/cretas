## 1. 做了什么
- **八块结构都有页面**（管理端一套 + 375 宽手机端一套）：
  1. 班组首页 `/crew`：五张卡（今天办成 / 等确认 / 发现问题、权限状态、形象占位四状态），全厂汇总，本厂启用哪几位（改动要写原因，回读）。
  2. 工作台 `/crew/worker?id=…`：左对话（按 ai-chat-standard：助手全宽无气泡、用户浅色气泡、16px、澄清选项同一样式、追问芯片只用代码给的、加载骨架带文字、新对话），右任务（等你确认 / 办理中 / 已办成 / 没办成 / 结果不明 + 原型演示未执行）。
  3. 等我确认 `/crew/inbox`：所有写操作先预览、每行都显示；按登录人权限只显示有权确认的，其余写「另有 N 件需要别的岗位确认」。
  4. 工作记录与额度 `/crew/ledger`：只记回读核实过的已办成；额度口径默认每件 1 个，没办成 / 结果不明 / 原型演示 / 班组配置不扣；可导出 CSV。
  5. 班组入职 `/crew/onboard`：口述 → 按黑湖工序目录整理工序与记录要求（对照这款产品真实报过的工序）→ 确认规则（历史范围给出，标准由人填）→ 每位员工上岗条件（具备 / 缺什么）→ 确认上岗。
  6. 嵌入现有页面：共享入口 `crew-entry.ts`「交给数字 X」（带上下文、回到原页面）；工作台一侧已可用；A–E 页面按 `F-crew-embed.md` 第六批合并后接。
  7. 主动汇报 `/crew/reports`：出成下降（成本会计）、原料库存为 0 但在生产（仓管）、工序超时「暂不能判断」说明；看依据、转成待办、忽略（写原因）、恢复。
  8. 一线手机端 `/crew/mobile`：按岗位只给一个入口（操作员→计划员、仓管→仓管、质检员→质检员），语音优先大按钮、今天要办的（真实工单 / 待核实项）、大字输入、确认卡。
- **能力跟权限走**：员工 = 权限模块组（`crew-config.ts`）；当前账号读 `permissions/current`，其他岗位是标明「演示」的假设权限。
- **写操作**：确认后经 E 线 `tasks/save` 真写 `test-f-20261112`，F 后端回读 E 保存区核实后才记「已办成」；称重报工（A 第六批未合并）只记「原型演示，未执行」。
- **对话是规则分析，不调模型**；数字全部由代码从黑湖快照算出。

F 线手上没有 BP 原文，下面按任务原文里的示例写成「改成这样」的成句。原句措辞以 BP 为准，只替换数字和结论。所有数字都来自六膳门黑湖快照（revision e4d77bafb5c9，2026-11-12 22:42），路演现场点开 19063 看到的是同一组数。

**第 7 页（急单）**

- 物料的结论不写「齐套」，改为：「物料：不能判断，交仓库核实。这款产品的 7 项原料在黑湖库存里都是 0，可近 14 天有 11 天都在生产，说明入库没登记全，系统不倒推库存。」

**第 8 页（费料）**
- 产品写实：叮咚好食光轻卤门腔（猪舌）120g。
- 82% → 78% 改为：「同一款产品『出料 → 熟制』的出成从 81.41%（工单 GD202611020005）掉到 77.65%（工单 GD202611040003），降了 3.76 个百分点。」
