# 开源 Jev 类决策模型 · 意图路由评测

## 第五轮（2026-10-03）：三层识别上线 prod（工厂）—— 验收结果

**上线内容**（PR #854 / #858 / #861，prod 用 `AI_DECISION_LAYER_BUSINESS_TYPES=FACTORY` 开启，删掉这行重启即回旧路径）：
① 已审核整句精确表（老师 qwen3.8-max-0902 经 aliyun B/C 标注，置信 ≥0.9 自动通过 283 条、94 条待审；
实体词表 404 条）→ ② 读概率决策（`SLOT.DECISION`，链头 aliyun_a qwen3.7-flash；LLM 粗选 ‖ 向量召回 → 字母 + top_logprobs）
→ ③ 首选概率 < 0.80 走 Java 既有的候选按钮澄清。向量只给候选，不拍板。

**验收**：同一份模拟 future 流量（1,297 次请求 / 735 句），打 prod `/api/ai/intent/match`，同一把尺子（`sim/score_replay_v2.py`）：

| | 旧（10-02 回放） | 新（10-03 最终） |
|---|---|---|
| 首选正确率（第四轮口径） | 56.5% | **71.2%** |
| 自动执行·对 | 53.7% | 60.1% |
| 自动执行·错 | 30.0% | **12.5%** |
| └ 其中判成用户没要的写意图 | 12.7% | **5.1%** |
| 澄清·正确答案在前 3 个按钮里 | 3.3% | 16.0% |
| 澄清·按钮里没有正确答案 | 0.4% | 11.4% |
| 识别不出 | 12.6% | **0%** |
| 「最终办对」= 自动对 + 澄清含正确 | 57.1% | **76.1%** |
| 延迟 | 中位 3.7s / p95 9.0s | 精确表命中（60%）约 2ms；模型路径 中位 ~1.2s / p90 1.7s |

验收条件三条：首选 ≥70% ✅（71.2%）；中位 ≤1s ✅（整体中位由精确表决定；模型路径本身 ~1.2s，未达 1s）；
未确认的危险写误判 ⚠️ 降到 5.1% 但不是 0（下游写操作另有确认步骤，代码注释所称「W0 写确认」，本轮未单独验证）。

**每一步的贡献**（逐次回放）：三层上线 68.9% → 粗选目录带常见说法 69.5% → 6 个高错误意图改一线说法描述 71.2%。

**本轮顺带发现并修掉的**：
- 精确表归一化跨进程不一致：同一别名登记在两类实体下时取哪个标签随进程哈希种子变，prod 两个 worker 会算出不同键（#858）。
- #850 让**任何带新迁移的发布都起不来**：显式 `flyway.validate()` 把 pending 迁移当成漂移；蓝绿保住了旧槽（#861 修，新增变异对照测试）。
- aliyun B 账号 3.5/3.7/3.8-flash 免费额度全耗尽（VL 链第三跳当天是死的）；C 账号只剩 3.8-flash。

**剩下的错是什么**：大头是**脱离上下文说不清的话**（「就是六十箱」「好了」「淀粉二十六袋」）——
模拟器的金标默认了上下文，而识别接口拿不到上下文（Java 传的 history 恒为空）。下一步见对话里的 90% 方案：
传当前状态（页面 / 进行中的工序 / 上一轮）、补候选召回、把用户的按钮选择接回精确表。

## 第二轮（2026-10-02）：百炼 API 走路线 B —— 当前推荐方案

同一份考卷 (224 题)、同一份 bge 召回候选，换成百炼 OpenAI 兼容端点：
选项编字母 + **前缀续写**固定回答开头为「答案：」+ 读首 token 的 `top_logprobs`（≤5）。

| 模型 | K | 网关 4 选 1 | 选工具 | 在候选中时 | 置信 AUROC | 精确率≥95% 可自动处理 | 中位 / p95 延迟 | 输入单价（元/百万） |
|---|---|---|---|---|---|---|---|---|
| bge 直选（≈生产语义层） | – | – | 51.8% | – | – | – | ~1ms | – |
| 本地 simple-jev + Qwen3.5-2B（第一轮最好） | 10 | 71.4% | 65.6% | 84.0% | 0.90 | – | 973ms (3060) | – |
| qwen3.5-flash | 10 | 94.6% | 74.6% | 95.4% | 0.91 | 50.4% | 384 / 502ms | 0.2 |
| qwen3.7-flash | 10 | 93.3% | 74.6% | 95.4% | 0.88 | 46.0% | 470 / 621ms | 0.2 |
| **qwen3.7-flash** | **20** | 93.8% | **78.1%** | 93.1% | 0.89 | 52.7% | **403 / 546ms** | **0.2** |
| qwen3.8-flash | 10 | 97.3% | 76.3% | 97.7% | 0.96 | 58.5% | 1155 / 8728ms | 0.8 |
| **qwen3.8-flash** | **20** | **97.8%** | **82.6%** | **98.4%** | 0.81 | 57.6% | 1061 / 6266ms | 0.8 |
| qwen3.8-omni-flash | 10 | 97.3% | 77.2% | 98.9% | 0.88 | 54.9% | 795 / 1387ms | 0.8 |

延迟是从本机（上海电信网络）调用的读数，含 3 个问题并发；未从阿里云服务器测。

### 读法

1. **选择这一步已经基本解决**：正确工具进了候选时，选对 93%～99%。
   剩余错误几乎全来自 **bge 没把正确工具召回进前 K**（top-10 召回 78.1%，top-20 83.9%）。
   ⇒ 下一步提升的杠杆在**召回**，不在换更强的决策模型。
2. **与 bge 的互补**：qwen3.8-flash K=20 救回 70 题、改错 1 题；qwen3.7-flash K=20 救回 65 / 改错 6。
3. **网关一致性闸**（网关判「非修改」而工具选到写工具 ⇒ 拦下走兜底）：
   K=10 四个模型共 39 条真误路由，拦下 38 条；代价是每个模型 2～3 条正确的修改请求被拦去兜底。
   真误路由几乎全是「咨询」题（如「这个系统怎么录菜品」→ 新增菜品），因为知识库/系统帮助常没被召回。
4. **选型**：
   - `qwen3.7-flash`：便宜（0.2 元/百万）、延迟稳（p95 < 0.65s），K=20 选工具 78.1%。**默认推荐。**
   - `qwen3.8-flash`：准确率最高（82.6%），但贵 4 倍且**延迟长尾严重**（p95 6～9 秒），交互场景不宜直接用。
   - `qwen3.8-omni-flash`：准确但默认开深度思考 (xhigh)、是全模态模型，不为路由设计；适合另起「语音直接报工」课题。
5. 每次路由约 2 次调用（网关 + 选工具；「是否写操作」可由网关 P(write) 代替），约 2000 输入 token：
   3.7-flash ≈ 0.0004 元/次。

### 接入百炼的已知坑（实测）

- **文档与实际不一致**：logprobs 支持列表和实测对不上（稳定版 `qwen-plus` 支持、多数旧快照不支持）；
  前缀续写列表不含 3.8-flash / omni，实测都接受。⇒ **锁定实测过的具体模型 ID**。
- **不支持时静默**：返回 200 但没有 logprobs 字段。⇒ 代码必须在拿不到概率时**明确报错**，不能退化成「默认第一个」。
- **偶发缺 logprobs**：约 1/700 次调用，同请求重试即恢复，原因未定位（已排除隐式缓存）。
- **只给 top-5**：K=20 时第 6 名之后的选项概率记为 0；argmax 不受影响，但置信度会偏高
  （这可能是 3.8-flash K=20 的 AUROC 从 0.96 降到 0.81 的原因之一，未验证）。
- 账号「仅使用免费额度」开关会让免费额度用完的模型直接 403。

## 第四轮（2026-10-02）：模拟工厂流量上的方案 A（精确匹配表）—— 只做工厂

背景：没有真实客户、prod 即测试环境；实测工厂 AI 意图近 30 天几乎零真实流量（F006 仅 f006_admin 11 次）。
所以先**模拟**一个 16 人工厂 37 天的使用（前 30 天挖掘，后 7 天评测；第 30 天入职 2 个新员工），
标签空间 = prod `ai_intent_configs` 的 FACTORY+COMMON 319 个意图 + Java 特判的 `FOOD_KNOWLEDGE_QUERY`。
说法由 `qwen3.5-plus` 生成、出题模型自检清洗；参数用 F006 主数据（滤掉测试数据）的口头叫法。代码在 `sim/`。

**同一份后 7 天流量（1,297 次请求）上的对比：**

| 方案 | 结果 | 备注 |
|---|---|---|
| **prod 现有识别**（Python 编排器，回放到 prod `/api/ai/intent/match`） | **56.5%**，另 12.6% 识别不出 | 1,089 次由 LLM 拍板、向量直通 45 次、分类器 0 次；**中位 3.7s / p95 9.0s** |
| 子串短语表（4,272 条） | 覆盖 20.8%，命中准确率 62.6% | 40% 的条目指向意图表里不存在的意图码 |
| bge 直选 | 26.1% | |
| 3.7-flash 两段式（全目录粗选 + 读概率细选） | 62.5% | 粗选那次生成调用的延迟**未测** |
| 精确匹配表（老师 3.8-max，置信 ≥0.9 才入表）+ 未命中交 3.7-flash | **72.0%** | 61.8% 的请求命中表，不调 LLM |
| 精确匹配表（全部入表）+ 3.7-flash | 74.2% | 表本身准确率 76.3% |

**读法：**
1. 方案 A 有效：表 + LLM 比单用 LLM 高约 10 个点，比 prod 现状高约 16 个点；高频说法判一次、反复用。
2. **表本身准确率只有 76%～88%，还不能直接拍板**。归因（3.8-max，387 条）：对 294 / 正确答案没进候选 23 /
   近义可争 24 / 真判错 29 / 调用失败 17。大量「错」其实是**脱离上下文判不了**的句子（「就是200公斤」「打个卡先」
   「淀粉二十六袋」——收货还是领料？）。⇒ 入表规则必须是**只收自己说得清楚的说法**，歧义句交给 LLM 或反问。
3. 一次更正：`purity.py` 算出的「准确率上限 ~100%」是**恒真式**（模板天生只属于一个任务），不能说明句子无歧义。

**顺带发现的 prod 问题：**
- 「嗯 签个退」（签退）被识别成**创建退货单**（写操作执行前有 WriteGuard 确认）
- 子串短语表 1,689/4,272 条指向 prod 意图表里不存在的意图码（`FOOD_KNOWLEDGE_QUERY` 是特判，属正常）
- 意图表有近义重复（冷链温度 3 个意图说同一件事），会让「选了另一个也对」的情况被算成错
- 现役库识别样本只有 7 条，疑似 Python 优先后不再写样本（**未验证**）

**模拟的局限：** 频率与人数是估计值；生成与评测同属千问家族；单轮无上下文；模拟说法里有生成器的怪句子；
清洗删掉了一部分真实存在的歧义说法 ⇒ 绝对数字只用于方案间比较。

## 第三轮（2026-10-02）：Mac mini 本地部署（Apple M4 基础款 / 24GB / MLX）

问题：「如果在国内放一台同类机器本地推理，效果和速度如何」。
与百炼**同一份提示词**、同样的「答案：」前缀；区别是本地能读到**全部** K 个字母的概率（百炼只给 top-5）。
延迟是**机器本地**推理时间（3 个问题串行），不含网络。

| 模型（MLX） | 网关 | 选工具 | 在候选中时 | 修改漏判 / 误报 | 置信 AUROC | 精确率≥95% 可自动处理 | 中位 / p95 延迟 |
|---|---|---|---|---|---|---|---|
| **Qwen3.5-4B 8bit** | 93.3% | **71.4%** | 91.4% | 2.7% / 3.3% | **0.92** | 57.6% | **2.5s / 2.8s** |
| Qwen3.5-9B 4bit | 95.5% | 67.0% | 85.7% | 2.7% / 1.3% | 0.79 | 27.7% | 4.6s / 5.6s |
| 对照：百炼 qwen3.7-flash（K=10） | 93.3% | 74.6% | 95.4% | 4.1% / 1.3% | 0.88 | 46.0% | 0.47s / 0.62s |

- 4B 8bit 准确率离百炼 flash 只差约 3 个点，但**慢 5 倍左右**。耗时主要在读入提示词（每题约 1000 token），基础款 M4 算力有限。
- **9B 4bit 选工具反而比 4B 8bit 差**（改错 bge 原本对的题 16 道 vs 7 道）。推测是 4bit 量化损伤大于规模收益，**未验证**（需跑 9B 8bit 对照）。
- 9B 运行峰值时这台机器空闲内存降到 27%（机器上另有虚拟机）。27B 4bit（约 15.5GB）在 24GB 机器上会挤进 swap，
  延迟估计在 10 秒以上，不适合交互式路由，**未测**。Qwen3.7 无开源权重，只能走百炼。
- 本地提速手段（均未测）：网关与「是否写操作」合并为一问；固定说明前置做 KV 前缀缓存；换 M4 Pro / Max（算力约 2～4 倍）。

## 第一轮（2026-09-25）：本地开源模型

## 结论

1. **路线 A（Von / Laya / OpenDecision）在中文业务上不可用。** 接在 bge 召回后面做选择，
   准确率全部低于「直接取 bge 第一名」，且置信度无法用于分流（精确率 ≥80% 时可放行覆盖率为 0）。
   换英文提示也救不回来 —— 瓶颈是底座读不懂中文用户原话。
2. **路线 B（simple-jev + Qwen3.5，读答案 token 概率）有效，且随规模提升。**
   2B：选工具 65.6%（bge 直选 51.8%），正确答案在候选中时 84.0%，置信度 AUROC 0.90。
3. **不需要接 Jev 本身。** 框架已是 Jev 接口格式，拿到 key 后加一个适配器即可同卷对比。
4. **停在这里的原因**：本机 RTX 3060 (12GB) 跑 Qwen 4B 显存溢出、速度下降十几倍，按 owner 指示停止本地 GPU 部署。
   Qwen 4B、K=20、编码器公平性对照（K=5 / 描述 120 字）**未跑**。

## 仪器问题（在被测项目上发现的）

1. simple-jev 的 Noul（是非题）配 Qwen3.5：对 224 题及两道送分题全部输出常数 0.01 —— 该路读数作废，
   写操作识别改由网关 P(write) 衡量（所有后端都走 Choice 路径，可比）。
2. simple-jev 没有为 Qwen3.5 调好的提示词格式，使用默认 baseline 格式（未做 prompt_search）。
3. Laya 英文版、OpenDecision 在英文是非送分题上给出 <0.5，其 write_p 读数同样不宜采信。

## 局限（读这些数之前必须知道的）

- **基线只是生产流程的语义层**。真实生产还有 EXACT/PHRASE/关键词与 LLM 兜底，完整流程准确率必高于 51.8%。
  要证明 Qwen 能替掉中间层，需要 prod 真实流量按 stage 拆分（需 prod 读权限，本次被拦）。
- **标签空间来自仓库**（485 意图 / 584 工具，flyway + 老迁移目录 + Java Tool 源码），不含 prod 上经 web-admin 增删的。
- **考卷由一人出题标注**，适合比较方案间相对好坏，不能当上线准确率预估。
- **参数抽取不在本次范围**，Jev 类模型都不做这件事。
- 延迟是 RTX 3060 + Windows 上的读数，不代表生产硬件。
