# AI 意图 -> 能力 棘轮基线
#
# 这份文件被 AiCapabilityHonestyGateTest 读取。它的作用是让
# 「意图库里又多了一条指向不存在能力的短语」这件事在 review 时必须被显式承认，
# 而不是悄悄长出来。
#
# ⚠️ 关于口径，先把话说清楚（不说清楚这份文件就会被误读）:
#
#   意图 -> 能力 的**权威绑定在数据库里** (ai_intent_configs.tool_name)，
#   而那张表不在仓库里。所以本文件用的是一个**代理判据**:
#     有能力证据 = 存在同名 Tool (INTENT_CODE 小写 == getToolName())
#                  或 意图码出现在 flyway seed / 其它 Java / resources / Python 里
#
#   ⛔ [NO_EVIDENCE] 里的意图**不等于**「确认没有能力」——
#      多数是命名对不上 (例: SCALE_WEIGHT_DIAGNOSIS 很可能绑到 scale_troubleshoot)。
#      要判定某一条真的没有能力，必须去查 DB 那一行。
#      本文件只保证一件事: **这个数不许变大**。
#
# 怎么改这份文件:
#   · 新增意图码 -> 必须加进下面某一节, 否则闸红。加进 [HAS_CAPABILITY] 等于
#     你声明「我查过, 它有真实实现」。
#   · 查清楚某条 [NO_EVIDENCE] 其实有能力 -> 挪到 [HAS_CAPABILITY], 计数自然下降。
#   · 确认某条真的做不到 -> 按 UnsupportedCapabilityRegistry 的做法改成明确拒答。
#
# 生成于 2026-08-26。
#
# 关于 189 这个数是怎么来的（口径要写出来, 否则下次没法比）:
#   它是**运行时那三张 Map 里去重后的短语数**, 不是源码里 put 的行数。
#   源码字面数是 193 —— 差的 4 条是同一短语被 put 了两次, LinkedHashMap 后写覆盖前写。
#   闸量的是运行时的表, 所以基线也用运行时的数; 用 193 会白留 4 条的松动。
