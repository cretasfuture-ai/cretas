# 已确认能复现

## 🔴🔴 缺陷 A31｜报工审批把接口 403 渲染成「待审批 0」，而真实待办有 26 条

**现象**：`lsm008`（六膳门质量经理）打开 `/production/approval`，看到
「**待审批 0**」+「暂无数据」，**没有任何错误提示**。

### 决定性对照（同一页、同一 URL、几分钟内，两个角色）

| 角色 | `GET /api/mobile/LIUSHANMEN/process-work-reporting/pending-approval?page=1&size=500` | 页面显示 | 表格行 |
|---|---|---|---|
| `lsm008` 质量经理 | **403** | **待审批 0** + 暂无数据 + toasts `[]` | 0 |
| `lsm015` 生产经理 | **200** | **待审批 26** | 20 |

⇒ 那个 0 **不是空列表**，是**挡在 26 条真实待办前面的伪造读数**。

### 同页阳性对照 —— 本条最硬的地方

`/production/reversals`（撤回审批）**同样 403**，却弹出准确提示：

> 操作无法完成 / 您的角色 [质量经理] 在 [生产管理] 模块无 [读写] 权限
> 请联系工厂管理员在 Canvas → 模块权限 矩阵为角色 [质量经理] 开通 [读写] 权限，或切换到有权限的账号重试

⇒ **平台会正确报这个错，是「报工审批」这一页把它吞了。** 排除了「缺全局错误处理」。

### 其它阳性对照（排除「全都 403」）

同一次页面加载里：

```
GET canvas/role-module-override        => 200
GET canvas/user-module-access/1646     => 200
GET config/disabled-modules            => 200
GET notifications/unread-count         => 200
GET process-work-reporting/pending-approval => 403   ← 只有这一个
```

### 结论：后端是对的，缺陷在前端，且是两条

**⛔ 不要改后端** —— 它放行了本该审报工的角色（生产经理 200）、拒绝了质量经理（403）。
「质量经理该不该审报工」这个问题**后端已经用行为回答了：不该**。
（该答案是否符合业务意图，仍是 owner 的判断，本文件不代拍。）

- **(A)** 菜单/路由把「报工审批」给了不该有的角色 —— 见下方「疑似」栏，**层级未定位**。
- **(B) 🔴 优先级更高**：页面把 403 渲染成一个**肯定的数字**。与 (A) **独立**——
  即使 (A) 修好、质量经理再也进不去这页，**任何**将来因权限收紧而 403 的角色
  仍会看到一个假的 0。

  ▎(A) 是「看到了不该看的入口」，(B) 是「**被告知了一个假事实**」。

## 排除 2｜4 个仓储页「内容空白」—— **我的仪器错，不是产品问题**

第一版判空用的是 `document.body.innerText.length`，**把侧边栏菜单的文字也算了进去**
（菜单本身约 400 字），于是「len≈440」被读成「内容区空白」。

换成只量内容区（`.app-main` / `.el-main`）重测后**全是假警报**：

| 页面 | 真实内容 |
|---|---|
| `/inventory/by-warehouse` | 正常渲染；默认选中的「外仓 (WH-LOG)」本身就是 0 批次 |
| `/warehouse/storage-locations` | 正常渲染；6 个区域 / 3 个位置 |
| `/warehouse/wastage-reports` | 正常渲染；诚实的「暂无数据」 |
| `/warehouse/materials` | 正常渲染；1 项待收货 + 61 个已入库批次 |

⇒ **已撤回。** 教训与本仓「287 屏报 280 干净，实际大量是启动闪屏」同族：
**判空的仪器必须量对对象**。

## 排除 3｜`lsm015` 两次登录失败停在 `/login` 且无提示 —— **我的仪器错**

看起来像「登录静默失败」这种像样的缺陷。先查网络层：**登录 POST 根本没发出去**
⇒ 是 Playwright 的 refs 过期 / `fill` 没落进 v-model，不是产品问题。
换成显式设值 + 触发 `input` 事件 + 点按钮后一次就过。

⇒ **没有报出去。** 判据：**界面「没反应」时，先证明请求发出去了，再谈是不是缺陷。**

## 方法学备注

- **只读的读数优先用无障碍树 / DOM 文本，不用截图** —— 截图正是「加载中被判成干净」的来源。
- **接口状态直接从网络层取，不从界面反推。**
  ⚠️ 中途踩过一次：钩 `window.fetch` 读到空，因为这个应用走 **axios(XHR)**。
  三个页面全是 `api: []`（包括明显有数据的生产计划）⇒ 一眼看出是仪器坏了，不是没有请求。改钩 `XMLHttpRequest`。
- **每个角色独立登录、独立上下文**，⛔ 不在 `*:*` 会话里量角色可达性。
- **顺着菜单走**，路径取自 `menuConfig.ts` 的对应组 —— 保证只访问「菜单里真有的」页面，
  不靠敲 URL 制造假可达（那正是缺陷 30 那一族被掩盖的方式）。
