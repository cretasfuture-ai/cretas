## 🔴 订正：PR #436 对「画布丢边」的根因判断是**错的**（2026-09-01 部署后实测）

PR #436（已合、已部署，merge `5ebd0eaaec`）声称根因是
「`deserializeGraph` 在同一个 tick 里先写 nodes 再写 edges，VueFlow 把边判成悬空丢弃」。
**该判断不成立。**

**证伪证据（部署后行为验证）**：
- 线上 `index.html` 哈希 = 回执 `index_sha256` `6c4dd2fa…` ✓
- 审批编辑器 chunk `assets/index-DUxIsahk.js` 线上可取，含本次改动的中文标记
  `已阻止保存` ✓（`loadedEdgeCount` 被压缩改名，中文串才是可靠标记）
- **而画布状态栏仍读作 `4 个 Cell · 0 条连线`** ❌

⇒ 代码上线了，行为没变。**「回执全绿 + 制品里 grep 到标记」不等于「功能修好了」** ——
本仓硬约束 2 的补充条款（找到标记 ≠ 它能跑）的又一个实例。

**为什么原判断是错的**：工序 Workflow 编辑器（能正常显示连线、真实用户每天在用）的
`hydrate()` **同样在一个 tick 里先设 `flowNodes` 再设 `flowEdges`**，没有任何 `nextTick`。
同一个写法在那边能跑 ⇒ 顺序不是病因。

**已排除的三个假设**（逐个证伪，记下来免得后面的人重猜）：

| # | 假设 | 证伪方式 |
|---|---|---|
| 1 | 同 tick 写 nodes/edges 导致边被丢 | 工序编辑器同样写法能跑；部署后行为未变 |
| 2 | 节点缺 source/target handle 导致边悬空 | `StartNode` 有 source、`EndNode` 有 target、`ApprovalNode` 两者都有、`ConditionNode` 两个具名 source —— 全都齐 |
| 3 | （未证伪，仅存疑）VueFlow 挂载时机 | 工序是 `<VueFlow v-else>`，**数据装好后才挂载**；审批是无条件渲染，画布从第一帧就挂着且为空，之后才推数据进去 |

⚠️ **PR #436 仍有价值，不要回滚**：它加的 `handleSave` 破坏性写入闸
（载入时有边、写回 0 条 ⇒ 硬拒绝）**已上线并生效**，
其余 4 条已启用审批链从此不会再被同样的操作清空。
被否掉的只是「顺序」这一条因果解释，以及那个多余但无害的 `await nextTick()`。

**补料 3 — 缺陷 13 有个会让修复空转的坑。**
element-plus 2.13.0 的 emptyText 逻辑：

```

options.size === 0                                                    → noDataText
```

## 待核 11｜PO 金额三个数对不上（差 1 分，需用大数量复核）

`PO-20260830-0004`：

```
含税单价 10 元/kg × 数量 0.03 kg = 0.30
总金额 ¥0.27  +  税额 ¥0.04     = 0.31
明细小计 ¥0.27                   税率 13%
```

0.27 × 13% = 0.0351 → 0.04 ⇒ 系统是**先定未税再乘税率**；
而含税单价口径应当是**先算含税 0.30 再拆**（未税 0.2655→0.27，税 0.0345→0.03，合计 0.30）。

⇒ 两种口径差 1 分。**金额太小，四舍五入无法排除**，
必须用一个大数量的单子复核（例如 100kg，差额应放大到元级）才能定性。
⛔ 在复核之前不下结论。

## 🔴 缺陷 18｜报错指路让去配主数据，配完不回填草稿单，用户照做仍然失败

**生产实证**（2026-09-01，最硬的一条）：
1. `PO-20260901-0001` 提交审批 → 报 `采购物料未配置有效采购价…请在供应商—物料关系或采购包装规格中维护大于0的未税采购价`
2. owner 照提示去 `DEMO235005 → 供应原料 → 13.9kg海天草菇老抽 → 编辑`，填 `8.85`，保存成功
   （列表回读：默认采购价 `CNY 8.85/kg` ✅）
3. 回 `PO-20260901-0001` 重新「提交」→ **报一模一样的错**

**根因**：价格在**转 PO 那一刻**从请购行 JSONB 取
（`PurchaseRequisitionServiceImpl:245` `dto.setUnitPrice(toBigDecimal(item.get("unitPrice")))`），
而请购单创建弹窗**根本没有单价字段** ⇒ 必为 null。
提交审批时 `validateOrderLinesBeforeApproval`（`PurchaseServiceImpl:858-866`）
只**读** `item.getUnitPrice()` 做判空，**不重新解析主数据**。

⇒ 于是形成闭环死结：**转 PO 时主数据还没配 → 价为空；主数据配好了 → 已存在的草稿单不会更新。**

🔴 **这比"没有提示"更糟**（本仓形态 D′：一个会误报的提示比没有提示更糟）——
提示是准确的、用户是照做的、做完没用，而且**没有任何一句话告诉他还要去「编辑草稿」**。

**建议**（三选一，需 owner 定）：
- (a) 提交审批时若行价为空，**回解一次**供应商—物料关系／采购规格，解得到就落价
- (b) 转 PO 时就解析主数据（而不是从请购行抄一个必为 null 的值）
- (c) 至少把报错 hint 改成「…维护后需回到本单点『编辑草稿』重新填价」

⛔ (c) 是下策：它承认了这个死结而不解开。

**两边语义并不一致：**

## 🔴🔴 缺陷 27｜改已发布审批定义后，在途实例进入「看得见、点不动」的死状态，且前端不显示原因

**本轮最重的一条。生产实证链完整，浏览器网络面板取证。**

### 发生了什么

1. `PO-20260901-0001` 提交审批，实例 `851d0845-da48-4349-a6e5-1c8664e67e34`
   创建时绑定的节点是 `LIUSHANMEN admin approval`
2. 用画布的「**仍然直接改**」修改了**已发布的 v1**：显示名改中文、审批人角色 `工厂总监 → 财务主管`、清空指定审批人
3. **显示层立刻跟着新定义走了** —— 该单从 `liushanmen_admin` 的待办**转移到** `lsm009`（财务主管）的
   「待我审批」，当前节点列显示「采购订单财务审批 · 财务主管」
4. `lsm009` 点「通过」→ **界面毫无反应**，反复点仍然毫无反应
5. 浏览器 Network 取证：

```
POST /api/mobile/LIUSHANMEN/workflow/instances/851d0845-.../actions  → 409  (×2)
{"code":409,"message":"WORKFLOW_BOUND_DEFINITION_CHANGED","success":false,
 "severity":"warning","actionHint":null,"hintTarget":null}
```

### 三条缺陷叠在一起

**A. 🔴 前端把 409 完全吞掉。** 后端明确回了 `WORKFLOW_BOUND_DEFINITION_CHANGED`，
`severity: warning`，而**用户看到的是"点了没反应"**。
`pending.vue` 的 `act()` 里，`catch { return; }`（用于处理"用户点取消"）与
后续的 `handleCatchError` 之间，这个 409 没有走到任何可见提示。
⇒ 典型的**把故障变成静默**：用户唯一能做的就是反复点，而每次都同样无声。

**B. 🔴 「在途审批不会被修改」这句话是假的 —— 显示层用新定义，执行层认旧定义。**
画布顶部原话：「当前业务使用独立画布；**在途审批不会被修改**（无在途实例时可直接改已发布版本）」。
实测：**待办归属、当前节点标签、审批角色全部跟着新定义变了**（单子真的跑到财务主管待办里去了），
只有**执行**被 409 拦住。
⇒ 两层用了不同的定义版本 ⇒ 单据进入「看得见、点不动」的状态。
后端那道 409 本身是**对的**（不许在定义被改动过的实例上执行动作），
错的是**显示层没有一起守住** —— 它把一张事实上不可操作的单，摆进了一个新审批人的待办里。

**C. 错误码 `WORKFLOW_BOUND_DEFINITION_CHANGED` 是英文常量直接下发**，未中文化。
与缺陷 23 同族。

### 后果

该 PO 目前**卡死**：`lsm009` 点不动（409）；`liushanmen_admin` 的待办里也不再有它
（节点已按新定义指向财务主管）。⇒ 在真客户生产租户上产生了一张**任何人都推不动的在途单**。

### 建议

1. **A 必修**：`act()` 收到非 2xx 一律显示后端 message + actionHint；
   ⛔ `catch { return }` 只能吃 ElMessageBox 的 cancel，不能吃网络异常。
   本仓形态：「收窄告警时别把『没能做决定』一起收掉」。
2. **B 必修**：定义变更后，在途实例的**显示**必须与**执行**用同一个版本判定 ——
   要么显示层继续按实例绑定的旧定义（与那句声明一致），
   要么在待办行上明确标注「该单据绑定的审批流已变更，需重新提交」并禁用操作按钮。
   ⛔ 不能出现"摆进你的待办、但你点不动、也不告诉你为什么"。
### 🔴🔴 升级：产品内**没有任何**解卡路径 —— 已实测

- **驳回也是 409**，同一个错误码（`POST .../actions → 409` ×3，最后一次是 REJECT）
  ⇒ 通过、驳回**两条路都堵死**。
- **强制取消不存在**。全仓 `grep -niE "forcecancel|force-cancel|cancelInstance|terminateInstance"`
  只命中**两处注释**：
  `WorkflowInstanceController.java:553`「(W4+ 加 force-cancel / delegate)」、
  `WorkflowEngineService.java:246`「Sprint 6 W4+ 加 force-cancel / delegate」——**都是"将来要加"，没有实现**。
- 守卫在 `WorkflowEngineServiceImpl.verifyBoundDefinition:349-364`：拿实例上存的 digest
  与当前定义 digest 比对，不等即 409。⇒ **只有把定义改回到 digest 完全相同才能解开。**
- ⚠️ 而我们用的是「**仍然直接改**」——**原地覆盖了已发布的 v1，没有留下旧版本**，
  原「指定审批人」是谁已不可考 ⇒ 精确复原不可行。

### ⇒ 结论（本条严重度按此评）

> **在这个产品里，改一次已发布的审批流定义，就会让该流程下所有在途单据永久卡死，
> 且没有任何产品内的恢复入口。**

而 UI **主动引导**用户走这条路：有在途实例时提供「仍然直接改」按钮，
旁边还写着一句让人放心的「**在途审批不会被修改**」——那句话在"显示"层是假的（待办真的转移了），
在"执行"层是真的（409），**两层的真假相反，正是它把用户送进死局的方式**。

**必须补的**：
1. 有在途实例时，「仍然直接改」要么禁用，要么明确警告「本操作将使 N 条在途单据无法继续处理」
   （N 就是它已经算出来的 `running-instances/count`，界面上已经显示成「有 1 条在途审批」了 ——
   **它知道有 1 条，却没告诉用户改下去这 1 条会死**）
2. 补 force-cancel / 重新绑定定义 的管理员入口（注释里已规划两个 Sprint 未做）
3. 缺陷 A（前端吞 409）必须同批修 —— 否则用户连"为什么点不动"都看不到

**当前这张 `PO-20260901-0001` 的处置**：建议**保留不动**，它是本缺陷的活体复现证据。
业务上无害（¥0.09、演示供应商）。走查继续时另起一条新的 PR→PO 链
（新实例会绑定新定义，可顺带验证财务审批节点端到端可用）。

## 缺陷 28｜采购数量校验：真实门槛是 ≥0.01，提示却说「必须大于0」，照提示改不对

**生产实证**（2026-09-01）：新建采购订单，采购数量填 `0.001`，前端正常接受并算出
「折合入库量 0.001 kg」「未税金额 0.01」「含税金额 0.01」，提交后报：

```
操作无法完成
第1行：采购数量必须大于0 请检查「items[0].quantity」字段
```

**根因**：`backend/java/.../dto/inventory/CreatePurchaseOrderRequest.java:98`

```java
@DecimalMin(value = "0.01", message = "采购数量必须大于0")
```

**约束值是 0.01，文案说的是「大于 0」**。`0.001` 确实大于 0，所以用户照着这句提示
**永远改不对** —— 他会以为自己填的不是正数，而真实规则是"不得小于 0.01"。
（该 DTO 内 `@DecimalMin/@Min/@Positive` 全文只此一处，问题是孤立的。）

**次生**：前端**没有对应的 min 校验** —— 让人填了 0.001，还替他算出了折合入库量和三个金额，
一路到提交才被后端拒。⇒ 问题没有前移。

**建议**：
1. 文案改成与约束一致：「采购数量不得小于 0.01」（或把约束改成真正的 `@Positive`，二选一，
   **但要先确认下游能不能承受 0.001 这种精度** —— 折合入库量、单价换算、库存流水都会跟着走）
2. 前端补同值 min 校验，在输入框就拦住
⛔ 不要只改文案不改前端 —— 那只是把"看不懂的拒绝"变成"看得懂的拒绝"，人还是白填一遍。

## 🔴🔴 缺陷 29｜从唯一有菜单入口的路径配不了审批分支条件 ⇒ 这样配出来的审批链「通过」会走到「拒绝」

**两个事实叠加，后果是致命的：**

**① 引擎里空条件 = 永真，取第一条命中的**
`WorkflowEngineServiceImpl.evaluateOutgoingEdges:1256-1262`：

```java
String cond = e.getCondition();
if (cond == null || cond.isBlank()) {
    // 空 condition = always true.
    return List.of(e.getTarget());   // 第一条无条件边直接命中并返回
}
```

出边按 `priority` 升序稳定排序；若两条分支边 priority 相同，**数组顺序决定结果**，
且**与用户点的是"通过"还是"驳回"无关**（`decisionOverride` 根本没被用上）。

**② 而条件输入框在业务模式下被隐藏**

```vue
<el-form-item v-else-if="!isSalesOrderDecision && !props.businessMode" label="条件 (SpEL)">
```

`businessMode = props.lockDecisionType`（`approval-workflow-editor/index.vue:272,310`），
而 `canvas-editor/index.vue:247-250`：

```js
approvalBusinessLocked = initialApprovalDecisionType !== undefined
                      && route.query.source === 'approval-chains'
```

⇒ **从「系统管理 → 审批链配置 → 配置审批」进入时 `source=approval-chains`**，
条件框被替换成一句 `此连线包含高级判断条件…请由平台管理员在高级模式处理`。

### ⇒ 合起来的后果

**「审批链配置」是唯一有菜单入口的路径**，而从它进去**配不出带条件的分支边**
⇒ 任何人用正常入口新建/重建一条审批链，得到的必然是

`admin_approval → approved` 之前 ⇒ 该链当时处于"通过即拒绝"状态。

