# 没做的三刀：④ 繁体洞 / ⑤ 死代码 / ⑥ 裸单字「菜」

**日期**: 2026-08-20
**口径**: prod **MOCK_REST 评测题库**（`smartbi.scripts._veto_fix_probe`），⛔ 非真实流量；
静态读数为**本地 AST**，⛔ 不是 grep。

⛔ **这三条都写「没做」并给解冻条件，⛔ 不硬做一个会误报的版本。**

---

## ⑥ 裸单字「菜」当维度判据 —— **没做**（交接件描述的伤害没能复现）

### 交接件说的

> 端到端实测（3/3 + 阴性对照 3/3）：
> `韭菜园店最近30天营收多少` → 23 字反问「没给名单」；
> 阴性对照 `王府井店…`（同样不存在、只是不含「菜」）→ 直接拿到 225 字好答案；
> 短路裸「菜」后，韭菜园店也拿到那 225 字。

### 我量到的

**先证明词表真的开火了**（短路前后 `dims` 逐条对照，同一棵基线树、同一窗口、各 3 轮）：

| 问句 | 裸「菜」在 | 短路之后 |
|---|---|---|
| 韭菜园店最近30天营收多少 | `['store','dish']` | `['store']` |
| 这个月买菜花了多少钱 | `['dish']` | `[]` |
| 点菜高峰在几点 | `['hour','dish']` | `['hour']` |
| 王府井店…（阴性） | `['store']` | `['store']` |
| 这个月采购花了多少钱（阴性） | `[]` | `[]` |

⇒ **词表确实在开火，而且只打在含「菜」的那三句上。** 仪器是活的。

**但老板看到的东西 15 轮里 14 轮逐字相同**（唯一那 1 轮差异落在短路侧**自己**
3 轮内就不稳的 `X1`，⛔ 不可归因）：

```
X1-韭菜园店   2/3 轮相同   A 23 字 || C 23 字
X2-王府井店   3/3 轮相同   A 225 字 || C 225 字
X3-买菜       3/3 轮相同   A 253 字 || C 253 字
X4-点菜       3/3 轮相同   A 10 字 || C 10 字
X5-采购(阴性) 3/3 轮相同   A 947 字 || C 947 字
```

### 交接件那个对比是**抖动**

在**不短路**的基线上跑 3 轮，`王府井店` 自己就在 **23 字 ↔ 225 字**之间摆动
（`md5` `730bf8c44c` / `70626d552a`，第二轮翻面）。
▎**「韭菜园店 23 字 / 王府井店 225 字」这个对比两侧都在基线树上，
▎与裸「菜」无关 —— 它是同一个问句在不同轮次的两种结果。**

⚠️ 这正是本仓 2026-08-19 记过的那条：
**在低抖动窗口里做 A/B，任何改动都会显示成「修好了」**；反过来，
在一个抖动的样本上做单轮对照，抖动会显示成「改动的效果」。

### 而且删掉它会弄红一条**合理**的既有断言

```
tests/test_restaurant_intent.py:
    assert _detect_dimensions("这道菜的食材成本是多少") == ("dish",)
```

「这道菜」**不在** `_DISH_TOKENS`（`菜品/菜系/菜价/哪道菜/哪个菜/单品`）里，
撑着它的正是那个裸单字。⇒ 要删就得先把 `_DISH_TOKENS` 补全，
而那是在**没有已复现伤害**的情况下动一张实体词表 —— ⛔ 不做。

### 解冻条件

1. 拿到一条**真实流量**里裸「菜」造成的误答（⛔ 不是评测题库、⛔ 不是单轮），且
2. 该问句在基线树上 **3 轮零抖动**（否则读到的是抖动）。

到那时的改法**不是删裸单字**，而是：
`_DISH_TOKENS` 补齐指代式说法（这道菜/那道菜/这个菜/该菜…）→ 再撤裸单字 →
重跑 `test_detect_dimensions` 那一组。

### 顺带（⛔ 不改，登记）

`_detect_dimensions` 里 store 那半边写着
`"店" in text and "点" not in text` —— 那个 `"点"` 否决是**硬编码巧合**
（为了不让「点菜/几点」误判成门店）。
SQL 实测单字「店」命中 10/10 个真实店名，⇒ 它当前**没有已复现的伤害**，
与裸「菜」同一条解冻条件。

## ⑤ 生产不可达的死代码 —— **没做**（比交接件说的多一处，且它在测试里是活的）

### 我自己复核出来的可达性（AST，⛔ 不是 grep）

判据：`if semantic_first:` 块内**每条路径**都 `return`/`raise`（递归看
`If`/`Try`/`With` 的最后一条），且它**没有** `else` ⇒ 其后的语句在
`semantic_first=True` 时到不了。

| 函数 | `if semantic_first:` | 其后不可达区间 | 行数 |
|---|---|---|---|
| `_parse_restaurant_query_impl` | 7994 | **8167–8495** | **329** |
| `_parse_continuation` | 8784 | **8717–8985** | **269** |

⇒ 合计 **598 行**，⛔ 不是交接件说的一处 330 行。**第二处交接件没提。**

只在这两段里被调用、别处一次都没有的符号（候选可删）：

```
_approved_exact_route                      _cache_get / _cache_put
_explicit_read_only_action_ranking_spec    _explicit_sales_period_comparison_spec
_explicit_store_dish_ranking_spec          _is_pure_store_scope_answer
_sales_metric_phrase                       _t2_vector_match
capability_clarification_question          optimization_clarification_question
```

⚠️ `match_restaurant_ops` 在死区里被调 2 次、**在别处也被调 2 次** ——
交接件提醒过这一点，核对属实，**它名下的词表仍然是活的**。

### ⛔ 为什么不删 —— 量过了

**「生产不可达」≠「没人执行」。** `parse_restaurant_query` 的
`semantic_first` 默认是 `False`，而 `tests/test_restaurant_intent.py` 里大量用例
是 `parse_restaurant_query(query, pool, factory_id="QHJ01")` —— **不传这个参数**。

📏 **绊线实测**（在 detached 基线树上，两段区间各插一句
`raise AssertionError("DEAD_REGION_REACHED")`，
⚠️ 先证明绊线真的落进了那两个函数体：`inspect.getsource` 里各出现 1 次）：

```
装绊线前 tests/ 基线失败          24
装绊线后 tests/ + gold 失败      106
                       差额  ≈  82 条用例会走进这两段
```

⇒ 这 598 行**是测试套件里 ~82 条用例唯一在跑的那条路**。
删掉它 = 同时要删/迁移那 82 条，那是一次跨目录的重构，
⛔ 不是「顺带清理」，也超出本轮「只碰 `restaurant_intent.py`」的范围。

▎更值得记一笔的是这件事本身的形状：
▎**一大批断言跑在一条生产永远不走的路上** —— 与本仓反复记的
▎「闸编译进 CI 但从没被执行」是同一个病的**镜像**（这次是「测试执行了，
▎但执行的不是生产那条路」）。

### 解冻条件（两步，⛔ 不许只做第一步）

1. 先把 `parse_restaurant_query` / `_parse_continuation` 的
   `semantic_first` 默认值改成 `True`，跑全量，**逐条**处理红掉的用例
   （要么改成显式传 `False` 并说明为什么要测那条路，要么迁到语义路径上）。
2. 确认没有任何生产入口能走到 `semantic_first=False` 之后，再整段删除，
   并把 `capability_clarification_question` /
   `optimization_clarification_question` 一并删掉
   （它们的唯一调用点在死区里）。

⛔ 判据仍是交接件写的那条：**要么删干净，要么把调用点挪进 `semantic_first` 块**，
⛔ 不许留着一段「看起来在守、实际生产一次没执行」的代码。

## ④ `_REQUEST_TEXT_TOKENS` 的繁体洞 —— **不在我的文件里**

交接件写：

> 位置 `restaurant_intent_service.py:1182` ⚠️ 那个文件不归你。
> 但它读的 `_REQUEST_TEXT_TOKENS` 如果定义在**你这个文件**里，那个繁体洞归你。

**它不在。** 实测：

```
_REQUEST_TEXT_TOKENS  定义在  smartbi/gold/restaurant/answer_contract.py:61
answer_contract.py 里 `with_traditional` 出现次数 = 0
```

⇒ 按交接件自己给的条件，这一条不归本轮。

⚠️ 而且它不是「一张词表忘了包 wrapper」：**那个模块整体没有繁体处理**。
`_PROFIT_VERDICT_TOKENS` / `_EXPLICIT_GAP_TOKENS` / `_MARGIN_TOKENS` /
`_REQUEST_TEXT_TOKENS` 四张表都是简体字面量。
⇒ 修法应该是给 `answer_contract` 整体加一层，⛔ 不是单点补一张表
（单点补会造出「这张包了、那张没包」的第二种漂）。

### 解冻条件

1. 先量一次「繁体输入在真实流量里占多少」——
   `answer_contract` 的四张表**都**只判产品自己的输出或用户问句关键词，
   繁体面为 0 的话这件事不值得做（形态 A¹¹：先问这里的空是不是合法状态）。
2. 要做就在 `answer_contract` 模块级统一包，并配一条闸钉住
   「本模块的中文词表元组一律经 `with_traditional`」。
