## 实测（prod，MOCK_REST，探针每轮独立 `session_key` + 传 `history`）

### 伤害侧

模型对第二轮「哪几家店」的**原始输出**（逐字，探针包 `_semantic_spec_from_t3` 抓的入参）：

```json
{"intent": "RESTAURANT_OPS_STORE_MARGIN", "dimensions": ["store"],
 "requested_metrics": ["gross_profit"], "wants_margin": true,
 "asks_profitability": true, "aggregation": "bottom", "store_scope": "all",
 "time_range": {"type":"relative","unit":"day","count":30},
 "clarification_needed": false, "confidence": 0.9}
```

**完全正确。** 而老板看到的是：

```
当前账号共有 **10 家门店**
1. 模拟·宝山大场社区店
2. 模拟·徐汇美罗城店
...
10. 模拟·静安嘉里中心店
```

（154 字，md5 `84a5fff5e9`）

### 立身之本侧 —— 它宣称守的那件事，一次都没发生

4 个标准名录问句（「我们一共有几家门店」/「有哪些门店」/「门店名单」/「现在有几家店」）
的模型输出全是

```json
{"intent": "RESTAURANT_OPS_STORE_DIRECTORY", "requested_metrics": [],
 "wants_margin": false, "clarification_needed": false, "confidence": 0.99}
```

`authority=llm`（⛔ 不是 `llm_contract_repair`）——
▎**模型自己就答对了，那条正则短路与否，输出逐字相同（同一个 md5 `84a5fff5e9`）。**

它的 docstring 写的立身之本是「a complete model response may not turn an explicit
directory object into an unrelated metric clarification」——
在这 4 条上 `clarification_needed` 全是 `false`，**那件事一次都没发生**。

## 改法

判据从「这句话长得像名录问句」换成「**模型这一轮到底确不确定**」：

```python
explicit_store_directory = (
    _is_explicit_store_directory_query(query)
    and bool(parsed.get("clarification_needed"))      # ← 新增
)
```

- `clarification_needed=True` 模型说不准 ⇒ 正则接管（**它的立身之本原封不动**）
- 模型给出完整计划 ⇒ ⛔ 不许覆盖

⚠️ 契约**形状**不完整那一类够不着这里 —— `contract_complete` 在本函数开头就早退了。
⇒ 收窄之后只剩「形状完整、但模型自己说不准」这一种，正是原设计要救的那一种。

### 硬约束 8（改共享结构前先数）

| | 数 |

| `explicit_store_directory` 赋值点 | 1（改这一处） |

## 这道闸（`test_a_wordlist_alone_cannot_veto_an_llm_slot`）为什么还在数它

普查仍把 ③ 计为一个「词表单独否决」决策点，**这是代理判据的盲点，不是漏改**：

判据认的「查」是 `EVIDENCE_SOURCES`（能力表 / 目录 / 指标登记表），
而 `parsed["clarification_needed"]` 是**模型自己的声明**，既不是词表也不是查。

⛔ **不把它塞进 `EVIDENCE_SOURCES` 来消音** —— 那个登记表的含义是「它真的去查了数据」，
塞一个非查的东西进去，就是那条闸自己 docstring 里写的「最大可被规避点」。
⇒ 宁可让计数偏保守（多算一个），也不动登记表的含义。
