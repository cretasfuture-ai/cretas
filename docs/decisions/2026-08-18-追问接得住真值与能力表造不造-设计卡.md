### 三条读数改变了判断

**① (a) 类只有 2 条，而且两条都是 resolver→【维度】，不是【指标】。**
那张维度表 `_RESOLVER_DIMENSIONS` **已经存在，而且这两次判对了** ——
第 7 条的拒答文案甚至完整满足交付定义第 5 条（缺什么 / 怎么拿到 / 他要干什么）。
⇒ **因 resolver→指标能力表缺失而接不住 = 0 条。**

**② (d) 类 4 条，全是同一个形态：实体消解 fallthrough，槽位里装着问句片段。**
`'按门店'` / `'分别看'` / `'那最低'` / `'按菜品看'` / `'最低的那道'` ——
这正是 #2872「**归一 ≠ 核对**」修的那个形态（`兜底把「我不知道这是不是门店」
翻译成「它就是门店」`），但那次只接了**门店**槽。
📏 实测：**菜品槽同形未修**（3 条），且**门店槽在「按门店」这种输入上仍然存活**
（`store_slot='按门店'` 3/3）。
⚠️ 这也与 `audit_restaurant_wordlists.py` 头部记的 2026-08-17 实测同源
（老板追问「那最差的呢」，产品把「最差」当菜名）。**一天之后仍在发生。**

**③ 第 8 条里，指标兼容判据【正确地】阻止了一次错误的 repair。**
`STORE_MARGIN` 登记不出 `revenue` ⇒ `_default_metrics_for_code` 那道 guard 不放行
⇒ 没有把「拒答」换成「用毛利顶营收」。**能力判据在做对的事**，
卡点在 planner 为什么给 revenue×store 挑了 STORE_MARGIN。

### 🔑 这同时推翻了上一轮登记的一条结论

上一轮写：

> 🔑 **真正的形态是「这些维度组合根本没有 resolver 服务」—— 能力表的事，
> 不是给 resolver 加 `dimensions` 形参。**

📏 本轮实测：(a) 类 **2/8**，且都是**维度**表（已存在、已判对）；

## 三 · Q3：造不造 —— 三个选项

### 选项 A：造一张新的 resolver → metric 能力表（19 个 resolver × N 个 metric）

**代价**：
1. **仓里已经有两份，再造就是第三份。** `restaurant_intent.py:2660` 白纸黑字：
   「判据读**既有**的 `_default_metrics_for_code`, ⛔ 不新造第二张
   「哪个 resolver 出哪些指标」的表(形态 D)。」
2. 「能力表写宽了下游会拿它当承诺」（`_RESOLVER_DIMENSIONS` 注释里反复写着
   「声明的是**真能出**的粒度，不是希望它能出的」「宁可窄而真」）。
3. **影响面 = 0**（见 Q2）。为没有受害者的缺口开工程。

⛔ 否决。

### 选项 B（选中）：不造，用已有的两份 + 补一道钉住它们不漂的闸

📏 **实测（跑出来的，⛔ 不是读注释）**：

```
_DEFAULT_METRICS_BY_CODE   restaurant_intent.py:2136   19 个 resolver, 全覆盖
MARGIN_CAPABLE_INTENTS     answer_contract.py:369      毛利族 3 个
```

`answer_contract.py:359` 对第二份的原话就是「**resolver 能力表** —— 契约只要求
resolver 真正能满足的元素……只有下面三个能产出毛利金额与盈亏判断」，
且 `required_elements` 的 docstring 写着「the contract is a regression guard for
**what the resolver CAN honor, not a wish list**」——
与设计卡要求的纪律**逐字同义**。

### 选项 C：造一张区分「能算」与「默认出」的完整二维表

**它指向一个真实的缺口**：`_DEFAULT_METRICS_BY_CODE` 比真实能力**窄** ——
`SALES_SUMMARY` 声明 `revenue/orders/avg_ticket`，而它的实现在 `wants_margin`
为真时**也会**出「已覆盖毛利」（`restaurant_ops_router.py:8668/8674`）。

**代价**：那一格恰好已被 `MARGIN_CAPABLE_INTENTS` 盖住，且**本轮 0 条接不住卡在
这里**。⇒ 为一个**没有受害者**的缺口做 19×N 的工程。

⛔ 本轮否决，登记为「有缺口、无受害者」。解冻条件写在第五节。

## 四 · 裁定与理由：**做 B**

1. **影响面 = 0**：resolver→指标能力表缺失导致的接不住 **0/8**（Q2 实测）。
2. **表已存在**，且第一份**早在设计卡之前 14 小时**就被 contract-repair
   自己当判据用了（`restaurant_intent.py:2678`，`eabd408f4d` 2026-08-18 06:27 #2806；
   设计卡是同日 20:52 `3c268dc1d0`）。
   ⇒ 设计卡里那句「📏 但仓里**没有** resolver → metric 的能力表」是**事实错误**。
3. **解冻条件 1 已满足**：把它写的判据原样跑在亏损句实测到的 spec 格上 ——

   ```
   LLM 选的 resolver = RESTAURANT_OPS_STORE_MARGIN   登记指标 = {gross_margin, gross_profit}
   planner 推出要的  = {gross_margin}
   ⇒ 「已能满足全部指标」= True ⇒ ⛔ 不该 repair（保留 STORE_MARGIN）   ← 正确
   阴性对照 WASTAGE_TOP / INVENTORY_WARNING / SUPPLIER_PRICE / STOCK_SHORTAGE 全 False
   ```

4. **解冻条件 2 也已满足**（见第五节）—— 所以设计卡 ④ 现在可以动手了，
   **而且不需要造表**。

### 🔴 本轮最值钱的那条：真正的坑不是「没有表」，是「取数口会撒谎」

```python
_default_metrics_for_code("RESTAURANT_OPS_OUT_OF_DOMAIN", True)  ->  ('gross_margin',)
_default_metrics_for_code("RESTAURANT_OPS_WASTAGE_TOP",   True)  ->  (..., 'gross_margin')
```

`wants_margin=True` 时它给**任何** code 追加 `gross_margin` ——
它是「这次要拉哪些指标」，**不是**「这个 resolver 能算什么」。

⇒ 谁要是照解冻条件 1 的字面意思、用这个函数去实现
「LLM 选的 resolver 已能满足全部指标 ⇒ 不 repair」，
**在毛利问句上判据恒真，改动静默地什么都不做，而单测照样绿。**

▎**我自己第一版就是这么写的**，是阴性对照当场把它打红的（4 条一起红）。
⇒ 能力判据一律读**原表** `_DEFAULT_METRICS_BY_CODE`，⛔ 不经过那个 accessor。
这条已经钉成闸，⛔ 不写成注释（注释拦不住 —— 本仓形态 B⁶ 记过前科）。

## 五 · 📏 解冻条件 2 已满足：第二个同形受害问句

设计卡写死的三条子句，**逐条核对**（「是哪几家」，3/3 轮稳定）：

| 子句 | 实测 |
|---|---|
| `dims == ()` | ✅ `dimensions=()` |
| LLM 与 planner 挑了**不同** resolver | ✅ `intent=STORE_MARGIN` ∉ `plan=('GROSS_MARGIN',)` |
| **两者都能算那个指标** | ✅ `req=('gross_margin',)`；两个 resolver 的登记指标**逐字相同** `('gross_profit','gross_margin')` |

而它的上一轮是「有没有店是亏钱的」—— 产品**答得很好**
（「10 家门店中没有毛利为负的门店」）。老板顺口问一句
**「是哪几家」**，拿到的是：

> 我不确定你要看的是哪一层的数，所以这次我没敢算。
> 你是想看某道菜、某家门店，还是全店合计？

▎他刚刚才说的就是门店，产品自己上一轮也是按门店算的。

⚠️ 另有一条**部分同形**：「那最低的呢」2/3 轮 `dims=()` 且
`intent=STORE_MARGIN ∉ plan=(SALES_SUMMARY,)`，但 `req=('revenue',)`
而 STORE_MARGIN 登记不出 revenue ⇒ **第三条子句不成立**，
它该走的是「repair 应该发生却没发生」那一支。

### 🔴 ④ 的成因比设计卡写的更宽

设计卡说 `dims == ()` 时「repair **无条件执行**」。
📏 实测「是哪几家」那次 **repair 根本没开火**（日志里只有 `执行前拦截`）——
`if repair_candidate and dimensions:` 把**整段**跳过了，于是
2636 那条 realign 也够不着，矛盾被原样留给 `_execution_mismatch` 拒答。

▎**同一个外层闸，两种相反的坏法**：
▎`dims==()` 时它既可能让 repair 无条件覆盖（亏损句），
▎也可能让 realign 无法开火（本条）。⛔ 修的时候两条都要有对照。

⚠️ 我自己的探针第一版扫描判据就写错了（扫「repair 开火了」而不是
「`code ∉ plan` 且 `dims==()`」），两头都错：**假阳性**把第一轮的日志算给第二轮，
**假阴性**漏掉了「是哪几家」—— 恰恰是最重要的那条。已修（`648950abb3`）。
▎形态 A：我想知道的是 X，实际在量 Y。
