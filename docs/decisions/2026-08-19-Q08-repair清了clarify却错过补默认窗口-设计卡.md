## 二 · 执行证据（`sys.settrace`，⛔ 不是读码）

外部审计提了两种可能，各自修法完全不同：

    A  repair 根本没走到 `clarification_needed = False` 那一行（被 guard 挡了）
    B  走到了，但清得**太晚**

`_q08_trace` 盯 `restaurant_intent.py` 的这几行，记**执行顺序**
（行号自检 3/3 ✅ / 阴性对照 0 命中 ✅ / 阳性对照 3/3 ✅）：

```
米饭（3 轮）:
  命中 2942（repair 清 clarify）      = 3/3    ⇒ ⛔ 不是 A
  命中 2373（补默认窗口）             = 0/3
  2942 之后又命中 3025（时间反问闸）  = 3/3
```

### 完整因果链

```
2361 补默认窗口的条件链里有 `and not clarification_needed`
   LLM 说要澄清 ⇒ 不补 ⇒ time_range_defaulted=False, window='全部历史'
2385 date_range / window_label **已经按「全部历史」算完**
2942 contract-repair 把 RECIPE_COST 改回 GROSS_MARGIN，并清 clarification_needed=False
     （authority 加上 `_contract_repair` 后缀 —— 这就是它执行了的证据）
3025 时间反问闸的条件链现在**全部成立**（无 time_phrase / 无 clarify / 无 defaulted）
     ⇒ 又把 clarify 设回 True
```

▎**同一个 `clarification_needed=False`：在 2373 那里会让「补默认」开火，
▎在 2942 之后却只让「时间反问」开火 —— 因为 2373 已经走过去了。**

对照：水煮牛肉在 `_semantic_spec_from_t3` 里（`_build_spec` **之前**）就被清成
False ⇒ 传进去时 `clarification_needed=False` ⇒ 2373 开火 ⇒ 最近30天 ⇒ 答上。

⇒ **同一个状态，只因清的时机不同而结果不同。这是确定性代码的顺序缺陷。**

## 三 · 为什么「repair 之后补一下 time_phrase」不行

`date_range` / `window_label` 在 **2385** 就从 `sales_spec` 算完了，
而 repair 在 **2942**。此时补 `time_phrase` 只改一个局部变量，
下游仍按「全部历史」出数，披露却说「最近30天」。

那段代码的注释自己写着这条（2344）：

> ⛔ 为什么必须在**这里**补而不是在闸那里放行：闸放行只是不问，而
> `_resolve_sales_date_range(query)` 仍是「全部历史」—— 下游会按全历史算，
> 披露却说「最近 30 天」。**那才是真正的降级处理**（数字与说明不符）。

⇒ 唯一干净的修法是**用修好的 code 重编译一次**。
