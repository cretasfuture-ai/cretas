## 2. 写入范围与端点

- **只写 L1**。一格一次：`(role_code, module_code) → level ∈ {rw,r,w,-}`，UNIQUE(role_code,module_code) 已在表上。
- **端点二选一（owner 拍 ③ 时顺带）**：
  - (a) 复用 F1 的 PUT —— 但 F2 说明它只给平台管理员；六膳门的 `permission_admin` 走不到。
  - (b) **推荐**：新开 `PUT /api/mobile/{factoryId}/permissions/matrix/{role}/{module}`，与 #646 的只读端点同前缀、同 interceptor 链；门禁 `@RequirePermission("system:read_write")` **或** 一个专用码 `permission:l1:write`（白名单角色 `platform_admin` / `factory_super_admin` / `permission_admin`），⛔ 不新造 permission 模块（#646 的理由：又一份清单）。服务层把 F1 的校验与守卫抽成共用 `PlatformRolePermissionWriter`，两个入口都调它 —— ⛔ 不复制第二份守卫（形态 D）。
- **模块轴**：编辑态复用 #646 的侧边栏轴 `sidebarModuleAxis()`；轴上不在写白名单里的列（今天只有 `restaurantProcurement`）**渲染成禁用并标注「后端白名单不认」**，⛔ 不悄悄放宽白名单（那是 owner 拍 ① 的事）。
- **角色轴**：`FactoryUserRole` 全量（30 个），`unactivated` 只读。

## 4. 缓存失效点

- 写后调 `invalidateCache()`（F4）—— 今天是全清，30 角色 × 22 模块的量级下全清没有代价，⛔ 不做按 key 精准失效（多一份逻辑）。
- 契约（真跑，不 mock）：**一次写入 ⇒ 后端下一次 `@RequirePermission` 判定立即变化**。测试形状：真实 `PermissionServiceImpl` + 假 repo；先 `hasPermission(u, "sales:read")` 命中缓存为 true；写 L1 `sales='-'` 并 `invalidateCache()`；再判 ⇒ false。变异「去掉 invalidateCache」⇒ 5 分钟内仍 true ⇒ 红。
- 登录响应侧不用管（每次登录现算，F8）。

## 5. `permission_admin system=r` 的 Flyway

- 一条 `UPDATE platform_role_permissions SET permission_level='r', updated_at=NOW() WHERE role_code='permission_admin' AND module_code='system' AND deleted_at IS NULL;` 加 `INSERT … ON CONFLICT DO NOTHING` 兜没有行的库。编号开工那天重数（F7）。
- 后果要写清：`r` 只让 `lsm001` **看得见**只读页与矩阵；要**写**还得走第 2 节的门禁。⚠️ `system:read` 在别的 controller 上还守着什么，开工前 `grep -rn '"system:read"'` 数一遍贴进 PR（今天没数，不假装数过）。
- 同时把硬编码 `PERMISSION_MATRIX.permission_admin`（= superAdminPerms 全 rw）**留着不动**：L1 有行时兜底到不了（#646 的 override 语义），改它只会制造第二处真相。
