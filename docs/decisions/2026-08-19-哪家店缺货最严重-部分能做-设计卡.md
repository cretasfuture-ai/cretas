# 设计卡 · 「哪家店缺货最严重」—— 一半能做，却整句作废

**日期**: 2026-08-19
**租户/口径**: MOCK_REST，prod（`smartbi_prod_db`），全景重测 24 问句 × 2 轮
**探针**: `_panorama24` / `_inventory_followthrough` / `_inventory_claim_check`

---

## 一 · 老板看到的（prod，2/2 轮逐字相同）

```
我不确定你要看的是哪一层的数，所以这次我没敢算。按食材我能算，但你这句还要求
再按门店拆一层，这次选中的算法拆不出这一层。想看的话分开问：先只按食材问同一件事。
我不会拿别的数据凑。
```

三处逐字撞在 owner 写死的规范上：

| 违规 | 规范原文 |
|---|---|
| 「所以这次**我没敢算**」 | 交付定义① 就是「答得上 —— 给答案，**不是「我没敢算」**」 |
| 「这次**选中的算法**拆不出这一层」 | ⛔ 技术话不给老板 |
| **整句作废** | 「部分能做：能做的先给 → 为什么另一半不能 → 老板要做什么 → 还能看什么。⛔ **不因为一半不行就整句作废**」 |

## 二 · 「按食材我能算」是**真的**（实测，⛔ 不是读码）

照产品自己给的出路走一遍（`_inventory_followthrough`，2/2 轮）：

```
**库存预警（2026-08-19）:**
- 需要立即补货 **4 项**, 关注 0 项, 正常 21 项
| 状态 | 食材 | 分类 | 剩余 | 安全库存 | 缺口 |
| 需立即补货 | 鲈鱼 | 水产 | 1689.4 kg | 4826.8 kg | 3137.4 kg |
| 需立即补货 | 罗氏虾 | 水产 | 0.0 kg | 2288.4 kg | 2288.4 kg |
...
```

⇒ ▎**产品手里有一份完整的答案，却因为老板多问了一层「按门店」而整份扣下不发。**

⚠️ 我在查证过程中一度把这句判成假话（拿 smartbi 池去查 `raw_material_types`，
读出「表不存在」）——**那两张表在 Java 侧 `cretas_db`**（实测 483 / 101 行）。
留痕见 `_inventory_claim_check` 顶部的作废说明。

## 三 · 断点（读码 + 实测）

`_drop_unanswerable_mislabeled_dimensions`（`restaurant_intent_service.py:974`）
本来就是干这件事的 —— 「去掉误标且无 resolver 支持的维度」。它的两个条件对 Q09
**都成立**：store 粒度上一个实体都没点名（`store_slot=∅`）、
计划里没有 resolver 支持 store（`INVENTORY_WARNING = {ingredient}`）。

**但它没开火**，因为：

```python
namers = {"ingredient": _query_names_an_ingredient}     # ← 只登记了 ingredient
...
if namer is not None and dim not in supported and not namer(query or ""):
```

`store` 不在 `namers` 里 ⇒ `namer is None` ⇒ 直接保留 ⇒ 撞维度闸。

⚠️ 那个函数的 docstring 写着「只登记**能判**的粒度；判不了的粒度一律不动」——
**store 是能判的**：执行入口在同一个函数里、早 46 行就算好了
`store_mention`（且已经过 `_mentions_backed_by_catalogue` 用租户门店目录核对）。
⇒ 不是「判不了」，是**没接上**。

### 第二个断点：剥掉之后**不告诉老板**

`_drop_unanswerable_mislabeled_dimensions` 剥掉维度时**只写 log**：

```python
logger.info("[restaurant-intent] 去掉误标且无 resolver 支持的维度: dropped=%s ...")
```

▎**形态 B 第 7 例（投影丢失）：产出端有了，消费端收不到。**
与 `_dimension_gap_advice` 自己 docstring 里记的成因**逐字相同**
（「差是算出来的，只是没有投影到用户侧」）。

⇒ 只补 `namers` 而不投影，就变成了**替老板做决定且不告诉他** ——
他问按店，拿到按食材，不知道为什么。那违反「⛔ 不替他做判断」。

## 四 · 三个选项

### 选项 1 · 只改措辞，仍然整句拒答
- **好处**：改动最小，零执行路径风险。
- **代价**：老板**还是拿不到那个数**。而产品手里那份答案是完整的。
  owner 规范明说 ⛔ 不因为一半不行就整句作废。
- ⛔ **不采纳**。它把一个「能给却不给」粉饰成了「说得更好听的不给」。

### 选项 2 · 补 `namers` 剥掉 store，直接按食材答
- **好处**：老板拿到数了，改动也小（一行登记）。
- **代价**：**替他做了决定且不告诉他**。他问「哪家店缺货最严重」，
  拿到一张按食材的表，**没有任何一句话解释门店那一层去哪了**。
  下一次他会以为这就是按门店的答案。
- ⛔ **不采纳**。它把「整句作废」换成了「静默降级」，后者更贵 ——
  静默降级不报错、不变红、看起来像正常答案。

### 选项 3 · 剥掉 + **把差投影出去** ✅ 采纳

```
① 你问的那一层给不了 + 为什么   ← 必须是第一句
② 下面是能给的那一层            ← 完整答案原样附在后面
```

顺序是**硬性**的，逐字沿用 `partial_coverage_answer` 的 docstring：

> ⛔ 反过来写（先甩数再解释）用户读到的就是「赚了这么多」——
> **那是「相邻指标顶替」换个位置重演**。

- **判据是「查」不是「猜」**：剥不剥由 `_RESOLVER_DIMENSIONS`（能力表）
  与「那个粒度上有没有点名实体」共同决定，两者都是确定性的。
- **措辞由实际值算出来**：说「按食材」还是「按门店」，取 `Dimension.label`，
  ⛔ 不硬编码（同 `_dimension_gap_advice` 已有的两次订正）。
- **零新增口径**：「差在哪一层」抽成**一份** `_dimension_gap(spec, plan)`，
  拒答文案（`_dimension_gap_advice`）与部分能做的说明**共用它** ——
  ⛔ 不写第二份 subset 计算（形态 D）。

**代价（诚实登记）**：
它把一部分原来「拒答」的问句变成「作答」，⇒ 答上率会涨，
但**涨的那部分不是新能力，是本来就算得出来的东西终于发出去了**。
⛔ 报数时必须说清这一点。

## 五 · 能让判据红的对照（⛔ 不是「测试通过」）

| # | 变异 | 该红的断言 | 守的是什么 |
|---|---|---|---|
| M1 | 从 `namers` 里摘掉 `store` | 承重：Q09 形态不再被剥 ⇒ 撞维度闸 | 接线在 |
| M2 | 剥掉但**不投影**（说明返回空串） | 阴性1：答案里必须有「门店那一层给不了」 | ⛔ 不静默降级 |
| M3 | 把说明**挪到答案后面** | 阴性2：说明必须在第一句 | 顺序是硬性的 |
| M4 | 让「有没有点名门店」恒为 False（即使点了名也剥） | 阴性3：点了名的门店**不许**被剥 | ⛔ 不把用户说的东西扔掉 |
| M5 | 让能力表对 store 恒为「支持」 | 阴性4：resolver 真能按店出时**不许**剥 | ⛔ 不降级本来能答的 |

⚠️ M1 单独不够 —— 它只证明「改动生效了」。M2–M5 证明**没有改过头**。
🔴 **本判据是 AND 链**：⇒ 每加一条条件，把 M1–M5 **全部重跑一遍**
（本仓刚实测过：加第三个 AND 条件后两条阴性对照变红 0 条，
而变异三层都证过生效 —— 它们的输入被新条件短路了）。

## 六 · 登记：这次**不做**的

- **给 `INVENTORY_WARNING` 补 `store` 能力** —— ⛔ 不做。
  实测 `resolve_inventory_warning` 读的是 Java 侧库存底账
  （`raw_material_types` + `material_batches`），那是**工厂级**的物料账，
  **没有餐饮门店维度**。⇒ 「它真能出」这条依据不成立，
  ⛔ 不许往能力表里写一个它出不来的粒度。
  🔴 解冻条件：库存底账接入门店维度（或 `fact_inventory_snapshot` 有真实数据
  —— 实测当前全表 0 行，它是 2026-08-09 起**已弃用**的旧账）。
- **`namers` 只补 `store`，⛔ 不顺手补别的粒度**。
  其余粒度（channel / meal_period / customer …）没有「能不能判点名」的实测，
  按那个函数自己的纪律「判不了的粒度一律不动」。
  🔴 解冻条件：出现一句实测被那个粒度卡住、且该粒度的「点名判定」有现成实现。
