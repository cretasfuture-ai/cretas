# 设计卡 · 三条能力缺口：读数、裁定，与**为什么其中两条不做**

**日期**: 2026-08-19
**口径**: MOCK_REST / prod。⚠️ 评测题库，⛔ 不是真实流量。

---

## ① 契约闸的子串判据 —— ⛔ **裁定：不收紧**

`answer_contract._request_coverage_present` 判的是
`_contains_any(answer_text, tokens)`（「提到了这个词」），
实测被一句**建议**满足（「往下可以拆开看…毛利分别是多少」）。

**⛔ 不收紧的理由是可检验的**：

```
`request_coverage` 是**契约元素** ⇒ 闸红 ⇒ contract.missing 非空
⇒ 老板拿到**兜底拒答**，而不是「营收表 + 一句说明」
```

▎收紧它 = 把「答案 + 说明」换成「拒答」= **退步**。

### 🔴 2026-08-19 晚：**理由变了，结论没变**

同日做完「产出被驳回时手边的数也给他」之后，上面那条理由**已经不成立** ——
闸红now也能拿到数了。⇒ 重新判了一次：

| 路径 | 老板拿到 |
|---|---|
| 闸放行 + `_metric_gap_note` | **完整的表格**（渠道 × 营收 × 单量 × 各门店构成）+ 一句「这次这条路给不了毛利的数」|
| 闸收紧 ⇒ 走 partial | 只有 `kpis` 那几个数（2~4 个）+ 说明 |

▎**投影那条路给的比 partial 多。收紧仍然是退步，只是退的东西换了。**
⇒ 裁定不变，⛔ 但理由必须更新 —— 拿一条已经失效的理由去支撑一个结论，
   下一个人照着它做判断时会踩空。

而「他要的指标没给数」这件事已由 `_metric_gap_note` 对**全部有 token 的指标**
做了投影。⇒ 剩下的唯一风险是**两者漂开**
（闸认的 token ≠ 投影认的 token ⇒ 出现「闸放行、投影也不说」的第三种缝）。

✅ **已做**：`test_metric_gate_and_projection_share_one_source.py`
钉住「同一个 token 对象 + 同一个字段」，并**显式断言闸仍是那个宽判据** ——
那条断言守的是**裁定本身**（有人来收紧时它会红，逼他解释为什么拒答更好）。

### ⚠️ 判据自己也量错过一次（留痕）

第一版用 `ast.Attribute` 数 `spec.requested_metrics`，当场红在
`_metric_gap_note` 上 —— 它写的是 `getattr(spec, "requested_metrics", ())`，
**字符串形式**，AST 上是 `Call` 的常量实参。
▎**AST 判据也会量错对象**：比字符串精确，但「精确地量了错的那个结构」一样不成立。
⛔ 修判据，⛔ 不把生产代码改成属性访问去迁就它。

## ② 产出被驳回时，手边有数却一个不给 —— 🔴 **需要 owner 裁定**

```python
# ⚠️ 只在能算出「为什么」时才走这条路: 说不出理由的数字贴在拒答旁边就是顶替。
gap_labels = missing_capability_labels(spec.unsupported_requirements)
if gap_labels:
    partial_text = partial_coverage_answer(...)
```

**实测（`_rejected_but_kpis_in_hand`）**：撞上兜底的 3 条

```
kpis=4  unsupported=[]  ← 最近30天营收为什么下滑
kpis=3  unsupported=[]  ← 模拟·徐汇美罗城店最近30天为什么毛利低
kpis=2  unsupported=[]  ← 最近30天哪个时段毛利最高
```

⇒ **3/3 手边都有数，老板一个都没拿到。**

⛔ **本轮不改**：那条纪律是 owner 写的，推翻它要 owner 拍板
（给数 = 可能被读成「顶替」；不给 = 老板空手而归）。
✅ 已登记进守望 `rejected-with-kpis-in-hand`，每天自己报一次。

### 🔴 这条读数第一版是**反的**，靠阴性对照救回来

第一版读最终响应 dict 的 `res["kpis"]`，读出「撞上兜底的 3 条 kpis 全是 0」
—— 差点写成「那条纪律没有代价」。
**而阴性对照红了**：正常出数的 2 条 `kpis` **也是 0** ⇒ 我读错了字段。
▎会读出「全 0」的仪器必须带阳性/阴性对照 —— 这次它真的开火了。
⇒ 改成在**拒答现场**用 `sys._getframe(1).f_locals` 取 `tiered_result.kpis`。

## ③ CHANNEL_MIX 算不出毛利 —— ⛔ **裁定：本轮不做**，理由不是「太难」

### 数据侧可行

`fact_pos_transaction` 有 `order_type` / `channel_origin` / `platform_fee_amount`
（**渠道是存的**）。成本在 `agg_restaurant_product_cost.food_cost`。

### 但连接是**跨模块跨库**的

读 `resolve_gross_margin` 自己的注释：

```
fact_pos_item → dim_product (POS 侧, 按 name)
              → product_types (cretas 侧 Java 库, 按归一化名匹配)
              → agg_restaurant_product_cost (product_source_pk = product_types.id)
```

⇒ 「按渠道加毛利」**不是加一个 GROUP BY**，而是把渠道穿进这条跨模块链。
⛔ 也**不能自己写第二份成本 SQL** —— 那是形态 D（同一个毛利口径两份）。

### 🔴 ⛔ 不做的真正理由（三条，都可检验）

1. **没有真实需求证据** —— 普查结论是「确实没有真人」，
   这个需求来自我自己构造的评测题库。
2. **验收不出可信的数** —— MOCK_REST 只有 **10 道菜 / 7 张成本卡**，
   而真实租户成本卡覆盖率 22%~61%。按渠道再摊一层会把覆盖率问题放大，
   ▎而「干净样本让每一道闸都绿」。
3. **当前行为已经诚实** —— 老板问渠道毛利，现在会被告知
   「**这次这条路给不了毛利的数**，下面是它能算的那些」。
   ⇒ 缺的是**能力**，⛔ 不是在说假话。

### ⚠️ 顺带挖出一个数据问题（登记，本卡不修）

`agg_restaurant_product_cost.product_id` **全是 0**（7 行里 1 个不同值），
真正的键是 `product_source_pk`（varchar，如 `mp_dish_002`）。
⇒ 我因为「两侧都是 bigint」选了 `product_id` 去连，读出**覆盖率 0.0%** ——
▎**类型匹配 ≠ 语义匹配。**
而那个 0% 是靠**阳性对照**（成本卡有行、两侧交集为 0）才认出来是仪器错。

## ④ 我在这一轮里连续猜错了四次列名/键

```
t.transaction_id            不存在（主键是 id）
c.product_source_pk = i.product_id   varchar = bigint
c.unit_cost                 不存在（真名 food_cost）
c.product_id                存在但全是 0（废弃占位列）
```

▎每次一个来回。⇒ 判据：**问「这几列对不对」之前，先问「这张表有哪些列」。**
⚠️ 还踩了一次「自愈的仪器坏在同一个事务里」：诊断查询写在 `except` 里、
还在失败的那个 `conn.transaction()` 内 ⇒ `InFailedSQLTransactionError`。
▎**诊断查询必须在失败的那个事务之外。**
