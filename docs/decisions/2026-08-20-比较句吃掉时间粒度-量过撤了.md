# 比较句吃掉时间粒度：**量过、试过、撤了**

**日期**: 2026-08-20
**结论**: ⛔ **不改**。缺陷是真的，但「保留 `time` 维度」这个修法实测**让老板拿到的更少**。
**口径**: prod **MOCK_REST 评测题库**，A/B 各 3 轮、同窗口、两侧探针 md5 逐字相同。
⛔ 非真实流量。

---

## 一、缺陷是真的

`restaurant_intent._build_spec` 里：

```python
if comparison and "time" in dimensions:
    dimensions = tuple(v for v in dimensions if v != "time")
```

`comparison` 来自 `_detect_comparison`（一张词表）。它命中就把 LLM 给的 `time` 维度整段剥掉。

📏 基线实测（arm A，3 轮**零抖动**）：

| 问句 | LLM 给的 `dimensions` | 答案 md5 / 长度 |
|---|---|---|
| 本月和上个月**每天**的营收**趋势**怎么样 | `['date']` | `fe3f7e231e` / 1306 |
| 这个月和上个月的营收**走势**对比 | `['date']` | `fe3f7e231e` / 1306 |
| 本月和上个月**按周**看营收 | `['date']` | `fe3f7e231e` / 1306 |
| 本月和上个月营收差多少（**无粒度词**） | `[]` | `fe3f7e231e` / 1306 |

▎**四条 md5 逐字相同。** 老板说的「每天 / 走势 / 按周」一个字都没起作用。

机制（变异时逐字复现）：

```
[restaurant-intent] contract-repair resolver RESTAURANT_OPS_TREND_ANALYSIS
                    -> RESTAURANT_OPS_SALES_SUMMARY metrics=('revenue',) dimensions=()
```

维度被剥空 ⇒ contract-repair 的能力闸 `if repair_candidate and dimensions:`
**因输入为空整段跳过** ⇒ `TREND_ANALYSIS` 被无阻拦改写成 `SALES_SUMMARY`。

---

## 二、修法试过了 —— 三条**全部变差**

改法是仓里现成的形状（抄 `llm_asked_store_grain`）：加一个
`_TIME_GRAIN_TOKENS`（每天/按周/走势…）放在**解锁侧**，命中就保留 LLM 的 `time`，
安全阀仍是 `_resolver_serves_dimensions`。单测 11 条全绿、变异 6 红 5 绿。

**然后跑 prod A/B（3 轮 × 两侧）**：

| | 基线 A | 改后 B |
|---|---|---|
| 路由 | `SALES_SUMMARY` `dims=()` | `TREND_ANALYSIS` `dims=('time',)` |
| 长度 | 1306 字 | 440~478 字 |
| 有没有同期对比数字 | ✅「与上个月同期（2026-07-01 至 2026-07-19）相比，营收低 **¥73,443.90**（0.5%），订单数减少 252 单（0.7%）」 | ❌ **没有** |
| 有没有按天/按周的表 | ❌ 没有 | ❌ **也没有**（表是按**月**的，只有一行） |
| 正文里那句 | —— | 「这个窗口里可比的完整月只有 1 个，**比不出最高/最低月**」 |

▎**两侧都没给出「每天/按周」，而改后还把唯一那个可用的数字丢了。**

3 条问句 × 3 轮 = 9/9 全部如此（0/3 轮相同，两侧各自 3 轮内零抖动）。

---

## 三、真正的约束不在这道否决上

`TREND_ANALYSIS` 把窗口按**月**分桶、再剔掉首尾残月。
「本月 + 上个月」是一个 2 个月的相对窗，两头都是残月 ⇒ 可比月恒为 1 ⇒
「比不出最高/最低月」。给它 `time` 维度**变不出**日/周粒度。

⚠️ 这与本仓 2026-08-19 记过的那条同源：
「两条各自正确的剔残月规则叠加后把比较集缩到 1 个元素」。

### 解冻条件（满足任一即可回来重做）

1. `TREND_ANALYSIS` 能按用户要求的粒度分桶（日 / 周），而不是恒按月；**且**
2. 它在跨残月时仍给出同期对比（现在是「本次不计算环比」直接放弃）。

到那时再加 `_TIME_GRAIN_TOKENS` 那一段（改动本身很小，本卡第二节写着形状）。

---

## 四、这一轮真正学到的（⛔ 比改动本身重要）

▎**「A 和 B 不一样 ⇒ 修好了」是错的。**

这三条**确实**变得不一样了（md5 0/3 轮相同），而且是往「更贴题」的方向变的
（`TREND_ANALYSIS` 听起来正是老板问的「趋势」）。
差一点就写成「修好了」—— **是逐字读正文才看出来它变差了**。

⇒ 加进验收步骤：**A/B 报差异之后，必须逐字读至少一条正文**，
   并回答一句「老板这次拿到的**有用的东西**是变多了还是变少了」。
   ⛔ 只报 md5 / kind / code / 长度不够。

⚠️ 同族前科：2026-08-18「量『追问接得住』量成了『两轮答案不一样』——而拒答也不一样」。

## 五、这一轮留下的东西（⛔ 不是白跑）

1. 这张卡本身：缺陷、修法、为什么不行、什么时候回来。
2. `restaurant_intent.py` 那一段上方的注释，逐字写着「不要照着再做一遍」。
3. 棘轮 `MAX_LEXICAL_VETOES` **保持把它算在内**（3，含这一条）——
   ⛔ 不因为「试过了」就把它从靶子里拿掉。
4. `test_generic_answer.py` 那条源码顺序断言的锚点从**整行**改成**前缀**：
   它守的行为没变，只是原来那种整行锚点在行尾多一个条件时就失配。
   这一处**保留**（严格更稳），⛔ 不随改动一起撤回。
