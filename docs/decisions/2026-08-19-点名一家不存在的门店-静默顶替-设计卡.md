## 一 · 老板看到的（prod 原文，⛔ 不是复述）

问：**「北京三里屯店卖得怎么样」**（MOCK_REST 没有这家店）

```
最近30天（2026-07-21 至 2026-08-19）覆盖 30 天、10 家门店，共 58,472 单。
总营收 ¥21,042,226.51 … 表现最强的是模拟·徐汇美罗城店 …
```

▎**一个字都没提「北京三里屯店」不存在。** 他拿到的是一个看着像答案、
▎实际答的是**别的事**的数字 —— 而且是全店合计，量级完全不同。

这正是 `restaurant_intent.py:5684` 那段注释**预言过**的事：

> 判据是「用户说没说门店」, 不是「门店范围定没定」: 没说门店时补「全部」是
> **补全**(他问的就是全店, 只是没说出口); 说了「东城店」而租户没这家店时补
> 「全部」是**换了个问题回答**, 他会拿到一个看着像答案、实际答的是别的事的数字。

⇒ **注释是对的，判据写在了下游，而上游用的是相反的那一条。**

### 上游是谁

`_semantic_spec_from_t3` 里有两个块会在 guard 之前就把 `store_scope` 定成 `all`：

```python
L6808  「模型自己给了 store 维度 → 门店范围是全部门店而不是缺项」
           … and not store_names …            ← 判据
L6852  「缺项都有安全默认值 → 补默认而不反问」
           … and not store_names …            ← 同一条判据的第二份
```

`store_names = _validated_llm_store_names(...)` 对**三种**模型输出都返回空
（它自己的 docstring 写着这一点）：

    ① 模型自己归一好了      → 被 `_verbatim_entity` 挡掉        → 空
    ② 模型回声老板的字      → `not in available`               → 空
    ③ 模型一家都没提名                                        → 空

▎**`not store_names` 分不开「他没说门店」（③）和「他说了一家我们没有的店」（②）。**
▎而这两件事该走相反的路。

## 三 · 修法（两半，⛔ 缺一半都不算修）

### 半 A · 上游**停止抢先**，⛔ 不在上游做第二份核对

```python
# 判据：老板**点名了**一家门店（LLM 的 store/stores，或他自己措辞里的门店提及）。
# ⛔ 这里**不判**「它在不在名单里」—— 那是 `_apply_store_scope_guard:5689` 的活，
#    它拿的是 `_load_store_options(pool, factory_id, code=...)` 的权威名单。
#    上游再判一次就是形态 D（同一个东西两份，它一定会漂）。
#    上游要做的只有一件事：**别把这一格提前定死，让 guard 有机会跑。**
and not named_store_mentioned
```

⚠️ 代价是**明确的**：老板点名的店**确实存在**时，上游也不再补默认，
多走一段到 guard —— 而 guard 对存在的门店会走 `store_scope='single'`
那条正路（阴性对照钉着）。⇒ 净效果只是把判定权还给唯一的权威。

### 半 B · 反问要说清**是哪家店没有**

半 A 只做完的话，老板拿到的是通用的
「这项分析要看哪一组门店？」—— 他不会知道自己那家店不存在，
只会觉得系统没听懂。**那是白问，不是少一步。**（与 Q08 的分界线正好相反：
Q08 答完那一问**就能拿到答案**，所以是「多一步」；这里答完仍然不知道真相。）

⇒ `L5689` 那支的 `clarification_question` 换成：

```
**门店名单里没有「北京三里屯店」**，所以没法单独给它的数 ——
也不会拿全部门店的合计顶替。

· 是刚开的店吗？先把它加进门店档案，加完这里就能单独看它。
· 还是我认错了字？在营的门店有：…

{STORE_SCOPE_CLARIFICATION_QUESTION}   ← ⛔ 常量必须**留在结尾**
```

#### 🔴 为什么常量必须留在结尾（这是本卡最容易踩的一格）

`restaurant_pending_clarifications` 只有 **两列**：
`original_query` / `clarification_question` —— **没有 `missing_slot`**。
延续轮认「上一轮问的是哪个槽」靠 `_slots_of_clarification` 对常量做
**字符串相等**。问句一旦变成动态文案：

    · 4 个按钮（全部门店 / 三家真店）**认不出来**
    · 老板的回答被拼成「北京三里屯店卖得怎么样 全部门店」重走一轮
      ⇒ 又检测到假店 ⇒ **又反问** —— 一个循环

⇒ 把常量放在结尾，边界转换点从 `==` 放宽成 `== or endswith("\n\n" + 常量)`。

⚠️ 那是**唯一**的边界转换点（它自己的 docstring 写着：改动前有 8 处各自比字符串，
合成追问会同时匹配不上全部 8 处并**静默穿过**），所以放宽只需改一处 ——
⛔ 但 `_slot_of_clarification`（单数版）是同一条判据的第二份，**一起改**，
否则就是形态 D 现场制造一份漂移。

### P2 的原始设计（保留，供追溯）

按「猜/查/算」的核心分工：

    「这几个字是不是一个门店名」 = **猜** ⇒ 该由 LLM 做
    「它在不在本租户名单里」     = **查** ⇒ 该由代码做

现在的契约让模型**一次做完两件事**（只在能对上名单时才填 `store`），
信息就在那一步丢了。⇒ 加一个**回声字段**（老板原话里的门店名，
⛔ 不要求它在名单里），代码再去查名单。

⚠️ P2 是 prompt + 契约改动，要独立设计卡 + prod A/B，⛔ 不在本卡里顺手做。
