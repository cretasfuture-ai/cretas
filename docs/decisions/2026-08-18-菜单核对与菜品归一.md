**日期**: 2026-08-18
**租户**: MOCK_REST（prod `smartbi_prod_db`，只读）
**分支**: `codex/claude-dish-catalogue`

---

## 0. 先说结论：owner 交待的落点和实测出来的落点不是同一处

owner 的 ② 写的是「把 `_catalogue_says_not_a_dish` 接到 `restaurant_intent.py`
那三个 dish 调用点上」。**实测下来，那三个调用点不是 prod 症状的成因**，
而且照那句话直接接会把一句诚实拒答换成一张不相干的排行表。

真因在**另一层**，而且是同一个形态（B：机制在、没接上）的更彻底的版本：

> `_catalogue_says_not_a_dish` **早就接在抽取器里**（`restaurant_ops_router:1470`），
> 但 `dish_catalogue_scope` **只包住 `parse_restaurant_query`**，
> 执行期（`tiered_answer`）在作用域外跑 ——
> 于是那道闸在**唯一一次结果能到达老板面前的调用**上恒 fail-open。

### 实测（探针 `_dishcat_scope.py`，prod MOCK_REST）

同一句问句，抽取器被调 11~14 次，每次记「当时目录条数」：

```
'香辣蟹煲卖得怎么样'  目录=10  ->  None      ← 在 parse 里, 目录在, 正确否决
'香辣蟹煲卖得怎么样'  目录=10  ->  None
 …(共 7 次, 全是 目录=10 -> None)…
'香辣蟹煲卖得怎么样'  目录=None ->  '香辣蟹煲'  ← 在执行里, 目录不在, 放行
```

**只有最后那一次的结果到得了老板面前。**

## 2. 三个选项

### 选项 A：照 owner 的字面做 —— 在三个 `llm_dish` 调用点上否决并摘掉槽位

**代价（实测否掉的）**：
`_dishcat_plan.py` 3 轮 × 7 问句，**形状 3/3 完全稳定**：

| 类 | `dish_slot` | 目录否决 | `ranking_direction` |
|---|---|---|---|
| 「那最差的呢」/「最差的那道菜…」/「最好的那道菜…」 | **None** | — | **worst / best** |
| 「香辣蟹煲…」/「佛跳墙…」 | 菜名 | **True** | None |
| 「米饭…」/「藤椒鸡…」 | 菜名 | False | None |

⇒ 排行类问句的 `dish_slot` **本来就是空的**（LLM 正确编译成了排行方向），
   目录否决在那一类上**一次都不会触发**；
⇒ 它唯一会触发的是「点名了一道菜单里没有的菜」，
   而那一类**今天已经拿到一句诚实的定向拒答**。摘掉槽位 = 拿全菜榜顶替他点名的那道菜，
   **正是 owner 自己写的「⛔ 绝不静默丢掉」**。

### 选项 B：一律反问「菜单里没查到「X」，是不是新菜？」

**代价**：「那最差的呢」也被反问。老板本来能拿到排行表，现在拿到一句
「菜单里没查到「最差」，是不是新菜？」——
**这正是反目标第一条说的那种提示：排在最前面的那个命中，他去查会一无所获**
（他去菜单里找「最差」这道新菜，找不到，也不该找）。北极星直接失败。

### 选项 C（**采纳**）：把作用域接上，让既有那道闸在执行期真的生效；槽位那条兜底路单独补一次核对

三处，各自守各自的：

| # | 改哪 | 守什么 | 目录不可用时 |
|---|---|---|---|
| ① | `tiered_answer` 绑定 `dish_catalogue_scope` | 抽取器那道既有的闸在执行期真的生效 | 逐字同今天 |
| ② | router 里 **spec 槽位兜底**那一行补目录核对 | 三个 `llm_dish` 汇流之后的唯一消费点 | 逐字同今天 |
| ③ | 「没有找到名为「X」的菜品」按目录分成两句 | 分开「菜单里没有」和「菜单里有、这段没卖」 | 逐字同今天 |

**为什么 ② 落在 router 而不是 owner 说的三个 `llm_dish` 调用点**：
三个调用点全部汇进 `_build_spec(llm_dish=…)` → `spec.dish_slot` →
`restaurant_intent_service` 的 `dish_mention` → router 的那一行兜底。
**一处接线覆盖三个来源，⛔ 不写三份判据**（形态 D：同一个东西有三份，它一定会漂）。
而且只有在 router 那一格，`resolved_ranking_direction` 与目录**同时**在手边。

## 3. 裁定理由

按 owner 的取舍顺序 **能不能决定 > 数字准 > 覆盖全**：

| 问句 | 今天 | 选项 A | 选项 B | **选项 C** |
|---|---|---|---|---|
| 那最差的呢 | 拒答 ✗ | 拒答 ✗（槽位本就空，闸不触发） | 反问 ✗ | **排行表 ✅** |
| 香辣蟹煲卖得怎么样 | 诚实拒答 ✅（措辞欠三件事） | 全菜榜顶替 ✗ | 反问 ✅ | **诚实拒答 + 三件事 ✅** |
| 米饭卖得怎么样 | 正常 ✅ | 正常 ✅ | 正常 ✅ | **逐字不变 ✅** |

**「摘不摘槽位」的判据是 `resolved_ranking_direction`，⛔ 不是词。**
它读的是 **LLM 自己编译出来的计划**：计划本身就是一个排行时，
一个菜名槽位是自相矛盾的多余约束；计划是点名一道菜时，那个名字**就是题目**，
摘掉它就没题了。

⛔ 这不是「用规则判用户是什么意思」——
判的是「**摘掉这个槽位之后，这个计划还成不成立**」，读的是结构不是措辞。

## 5. ③ 菜品侧归一 —— 实测：唯一匹配那一支**本来就做完了**

owner 交待「照抄门店那半」。实测（`_dishcat_gap2.py`，prod MOCK_REST）：

```
'木耳这个月卖得怎么样'  dish_slot='木耳'  → 抬头「凉拌木耳」本月销量 25,700 份 ✅
'花菜这个月卖得怎么样'  dish_slot='花菜'  → 抬头「干锅花菜」本月销量 31,779 份 ✅
'牛肉这个月卖得怎么样'  dish_slot='牛肉'  → 抬头「水煮牛肉」本月销量 31,730 份 ✅
```

**唯一匹配直接归一、抬头用库里全名 —— 三条全中，已存在**
（`_match_dish_rows` 的子串匹配 + 抬头取 `dish_name`）。

⇒ owner 预判的「MOCK_REST 上量不出归一的收益」得到证实，
   而**原因比预想的更彻底：不是收益小，是这一支本来就不缺**。
   ⛔ 不为了让读数好看去构造样本。

③ 剩下真正缺的两件，都是**措辞**不是机制：

1. **多条命中的确认式反问是黑话**
   今天：`「X」匹配到多道菜品：A、B。请指定其中一道后再查询。`
   门店那半：`你说的「X」，我这边有 N 家对得上：A、B。你要看哪一家？`
   ⇒ 照门店的形状改，并把候选放进 `suggested_followups` 让他点。
   ⚠️ 这一支 MOCK_REST 上不可达（见 §4），只有单测。

2. **零条命中时「走原路」在菜品侧是错的**
   门店那半零条走原路（fail-open）是对的：门店名对不上，问句还能按全店回答。
   菜品侧不行 —— 他点名了一道菜，拿别的菜的榜单顶替就是替他改题。
   ⇒ **菜品侧零条 = 定向拒答**，这是有意的偏离，理由如上。
   照 owner 的要求把措辞补成「缺什么 / 怎么拿到 / 他要干什么」三件事。

## 7. 我自己的仪器犯过的两个错（登记，⛔ 不是自谦）

1. **探针的 `dish=` 列读的是 `spec.dish` —— 那个属性不存在。**
   于是每一行都读成 `None`，看起来像「LLM 从来不填菜名槽位」。
   真正的字段是 `dish_slot`。⚠️ 这是形态 A：**我量的这个数，不是我想知道的那个数**。
   救回来的是另一个读数：答案里明明印着菜名，而槽位说 None —— 两个读数对不上才去查的。
   已修（`_dishcat_probe.py`），⛔ 没有加 `.get(k, None)` 兜底（那会把「我不知道」翻译成「是 None」）。

2. **变异对照的「变异到达了吗」那一栏，第一次跑时整栏是死的。**
   探针少了第二条 `sys.path`（`services` 在 `smartbi/` 下面），一 import 就崩，
   崩了之后 `.get(key)` 每一格都返回 `None`，而 `None != None` 为假
   ⇒ **五条变异全报「没到达」**。那不是读数，是仪器死了。
   已加阳性对照：探针读不到任何一格就直接 `rc=2`，⛔ 不让它继续报数。
