## 方法：判据用结构，⛔ 不用关键词表

关键词永远补不全（本仓明确裁定），而且写一张「提示词表」会撞词表棘轮闸。
`census_unconditional_callouts.py` 三个维度**全部来自 AST**：

**轴一「点名型」** —— f-string 里存在一个插值，它
(a) **没有数值 format_spec**（`.1f` / `,.2f` 是**报数**不是**点名**），且
(b) 值能追溯到**数据行**（`r["store_name"]` / `r.get(...)` / `row.name`，含
「先赋给局部变量再插值」一跳）。⇒ 纯参数插值（`{noun}` / `{title}`）被过滤掉。

**轴二「纯常量」** —— 🔴 补丁：实例一（`_advice_line`）的**原形**是
「一句无条件常量」，没有任何插值 ⇒ 它是 `ast.Constant` 不是 `ast.JoinedStr`，
**轴一完全看不见它**。五条 🔴 里有四条是靠轴二找到的。

**守卫强度** —— 沿 parent 链上溯收集所有 `if` 的 test：

| 档 | 判据 |
|---|---|
| `THRESHOLD` | 某个 test 里有 `< > <= >=` 且一侧是数值常量或模块级常量名 |
| `EXISTENCE` | 只有真值判断 / `is None` / `==` / `in`（`len(x) > 0` 归这里） |
| `NONE` | 一个 `if` 都没有 |

读数：

```
候选总数 1932
  轴 named   313   NONE=85   EXISTENCE=205   THRESHOLD=23
  轴 const  1619   NONE=407  EXISTENCE=1023  THRESHOLD=189
```

### 🟡 边界模糊 —— 有依据但没阈值

#### 🟡-1 `_staffing_store_lead_sentence`（`restaurant_ops_router.py:9361`）

prod 原文：

```
按门店看：缺口最大的是**模拟·静安嘉里中心店**的**晚市**，
预测客流 351 人、建议配 35 人、现有 8 人，还差 27 人，置信度 72.8%。
```

而同一份答案的明细表里，**缺口 27 的门店有 6 家**（静安嘉里中心 / 长宁龙之梦 /
徐汇美罗城 / 陆家嘴正大 / 杨浦五角场 / 打浦桥日月光），差别只在预测客流
351 vs 346 vs 344 vs 342 vs 341 vs 339。

⇒ 「缺口最大的是 X」是**并列第一里按排序取的第一个**。老板照它只去补静安，
会发现另外 5 家一模一样。**依据是对的（确实并列最大），缺的是「领先第二名
多少才值得单独点名」。**
⇒ 建议：并列时说「有 6 家晚市缺口都是 27 人」，⛔ 不点单独一家。

#### 🟡-2 `resolve_gross_margin` 的「需要关注的低毛利菜品」（`restaurant_ops_router.py:5561`）

选法是 `sorted(revenue>=1000, key=margin_rate)[:3]`（第 5381 行）——
**bottom-3，没有「多低才算低」的下界**。prod 实测：

| 菜品 | 毛利率 | 与主菜平均 67.8% 的差 |
|---|---|---|
| 水煮牛肉 | 58.6% | −9.2pp |
| 鲈鱼 | 62.6% | −5.2pp |
| **藤椒鸡** | **66.7%** | **−1.1pp** |

⇒ 藤椒鸡低于平均 1.1pp 就被印成「需要关注的低毛利菜品」。
⚠️ 而 MOCK_REST 只有 5 道菜有成本卡 ⇒ 这张「低毛利榜」是 5 里挑 3，
**60% 的菜都在榜上**。老板去查藤椒鸡大概率一无所获。
⇒ 建议：挂一个「低于平均多少 pp 才上榜」的下界，并允许**这一档为空**
（空的时候说「没有明显偏低的」，⛔ 不是硬凑 3 道）。

#### 🟡-3 `_compute_margin_dragger` 的「最拖整体毛利的菜品」（`restaurant_ops_router.py:2334`）

判据本身是对的（`拖累 = 营收占比 × 毛利率差`，恒等式，且 `min_revenue=1000`
挡掉了小额噪声）。**但拖累的量级没有下界** —— 平数据上它照样会点名一道
拖累 ≈ 0 的菜。

📏 这次实测**站得住**：水煮牛肉 占主菜已覆盖营收 24.6% × (58.6% − 67.8%)
= **−2.26pp**，是真材料。
⇒ 归 🟡 不是因为这次错了，是因为**没有任何条件保证下次不错**。
⇒ 建议：拖累绝对值低于某个 pp 时改说「没有哪道菜明显拖累整体毛利」。

唯一在禁区外的是 `canonical/entity_resolution/shortlist.py`。**我判断它不该现在改**，
三个选项和代价如下：

| 选项 | 做法 | 代价 / 为什么不选 |
|---|---|---|
| A. 抬高 `SIM_FLOOR` | 0.55 → 0.80 | ⛔ **会打死正确命中**：模块 docstring 记着正确候选 top-1 落在 0.608~0.796，抬到 0.80 一条都不剩。这是「修了假阳、把真阳一起杀了」 |
| B. 换成**相对**判据 | top-1 必须显著高于**该租户候选池自身的两两相似度基线**（同名模板的那部分被减掉） | 需要先量基线的分布（每个租户一次，可缓存）。⚠️ 这是**新机制**，要配阴性对照语料，不是一次 edit 能做完的 |
| C. 只改措辞 | 「有 4 家对得上」→「我没认出这家店，最像的几家是…，都不是的话请打全名」 | 便宜、立刻降低伤害（不再断言「对得上」），但**没有修掉误发本身** |

**裁定：留卡，本轮不改。** 理由是 A 有害、B 是新机制（该走 brainstorming +
写 plan，不该塞进一次普查）、C 虽然便宜但那句话在 `restaurant_intent.py`
（禁区）里，而 `shortlist.py` 这一侧只出 verdict、不出文案。
⇒ 真正该动的第一步是 **B 的基线测量**，那是下一条线的任务。

⚠️ 如果只能做一件事，做 C 的一半：把 `decide_from_scores` 的 `detail` 里
已经有的「top1 0.771 与次优只差 0.028」透传到文案上，让老板看得见
**产品有多不确定**。那不需要新机制。
