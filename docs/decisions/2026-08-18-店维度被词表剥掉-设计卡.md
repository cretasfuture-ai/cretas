**日期**: 2026-08-18
**租户/口径**: MOCK_REST，prod（47.100.235.168:8083，`smartbi_prod_db`），3 轮
**探针**: `smartbi.scripts._lossmaking` / `._lossmaking_llm_raw` / `._store_dim_override`

---

## 现象（老板会看到的）

| 问句 | 老板问的 | 老板拿到的 | 本次修不修 |
|---|---|---|---|
| 有几家店是亏钱的 | 店 | **菜品毛利分析**「5 道有成本卡的菜都还赚钱」 | ✅ 修 |
| 多少家店在亏钱 | 店 | 同上 | ✅ 修 |
| 所有门店最近30天的毛利是多少 | 店 | 同上 | ⚠️ **不修**，见下方「降级登记」 |
| 有没有店是亏钱的（对照） | 店 | ✅「10 家门店中没有毛利为负的门店」 | 本来就对 |

3 轮零抖动，24 次调用。

⚠️ **交接件说这句「在 prod 上仍拒答」—— 已过期。** 上一棒的
`_mentions_backed_by_catalogue`（`restaurant_intent_service.py:2061-2066`）
把假店名 `store_slot='有几家店'` 在执行时丢掉了，拒答消失。
**但只修了一半** ⇒ 拒答挪成了**错答**。错答比拒答更贵：它看起来是完整答案。

## 根因（实测，不是读码）

`_lossmaking_llm_raw` 钩 `_build_spec` 拿到 LLM 的原始输出。**两句完全相同**：

```
code = RESTAURANT_OPS_STORE_MARGIN     llm_dimensions = ('store',)
llm_store = None                        llm_store_scope = 'all'
```

▎**LLM 两句都判对了，一模一样。差异 100% 在确定性代码里。**
⇒ 上一棒登记的「落点在模型侧」可以正式排除。

断点在 `restaurant_intent.py:2505-2510`：

```python
if (store_scope == "all"
        and "store" in dimension_list
        and not _asks_store_breakdown(effective_query)):   # ← 一张 19 条的词表
    dimension_list.remove("store")
```

`_STORE_BREAKDOWN_SCOPE_TOKENS` 里有「有没有店」，**没有**「有几家店」。
store 维度被剥掉后 `dimensions=()`，于是：

1. `_plan_requested_intents` 选出 `GROSS_MARGIN`（1379 那段同样读这张词表）
2. contract-repair 的能力闸 `if repair_candidate and dimensions:`（2601）
   因 `dimensions == ()` **整段被跳过**，无阻拦地把 STORE_MARGIN 改写成 GROSS_MARGIN
3. `GROSS_MARGIN` 的能力是 `{dish, time}` —— **它不服务 store**。
   闸如果跑了本来会拦下，是维度先被删掉让闸失去了输入。

## 关键读数：那段覆盖到底在保护什么

`_store_dim_override`，8 句 × 3 轮 = 24 次，逐句打 LLM 原始 `dimensions`：

| 组 | 问句 | LLM 给的 dims | 覆盖开火 | 结果 |
|---|---|---|---|---|
| A | 有几家店是亏钱的 | `('store',)` | 🔴 删 | 误伤 |
| A | 多少家店在亏钱 | `('store',)` | 🔴 删 | 误伤 |
| A | 有没有店是亏钱的 | `('store',)` | - | ✅ |
| A | 哪家店毛利最低 | `('store',)` | - | ✅ |
| B | 全部门店最近30天卖了多少钱 | `()` | - | ✅ |
| B | 所有门店最近30天的毛利是多少 | `('store',)` | 🔴 删 | 误伤 |
| B | 最近30天总营收是多少 | `()` | - | ✅ |

▎**开火 9 次（9/24），9 次全是误伤，0 次保护。**
▎**LLM 在纯汇总句上给的就是 `()`，9/9 轮一次都没多给 store。**

⚠️ 组 B 的「所有门店的毛利是多少」是我**预设它该被删**的那句 —— 实测它也是误伤：
问门店毛利答菜品毛利。所以「组 B 该删」这个预设本身是错的。

## 三个选项

### 选项 1 · 往词表里补「有几家店」「多少家店」

- **代价**：下一个措辞又炸（「几间店在亏」「亏损的店有多少家」「有多少门店不赚钱」）。
  这正是架构裁定要换掉的「猜」—— 而且 owner 已裁定 **不复活关键词路由**，
  往词表加词是同一件事的小号版本。
- **好处**：3 分钟，零回归。
- ⛔ **不采纳**。它把一个结构缺陷变成一条永远补不完的清单。

### 选项 2 · 整段删除，完全信任 LLM 的 dimensions

- **代价**：那段有它的历史（注释写着防「otherwise-correct all-store sales/margin
  plans fail the immutable resolver-capability check」）。
  若 LLM 给了某个 resolver 服务不了的 store 维度，下游会拒答 —— 把误伤换成拒答。
- **好处**：最干净。
- ⛔ **不采纳**。它拆掉了安全阀，而安全阀在我 24 次样本里恰好没被触发过
  ——「没触发过」不等于「不需要」（形态 B⁴：验收环境不含能让它红的输入）。

### 选项 3 · 按**来源**收窄：只覆盖代码自己派生的 store 维度 ✅ 采纳

```python
explicit_store_scope, explicit_store_mentions = _detect_store_scope(effective_query)
llm_asked_store_grain = bool(
    llm_dimensions is not None and "store" in tuple(llm_dimensions)
    and explicit_store_scope != "all"                       # ← 见「第二版」
    and _resolver_serves_dimensions(code, ("store",)))
if (store_scope == "all" and "store" in dimension_list
        and not _asks_store_breakdown(effective_query)
        and not llm_asked_store_grain):
    dimension_list.remove("store")
```

- **判据是「查」不是「猜」**：LLM 明确要了按店拆 → 代码去**能力表**核对它自己选的
  resolver 真能不能按店出。能 ⇒ 保留；不能 ⇒ 维持原行为（删，避免拒答）。
  这正是架构第 ④ 步「核对」的形状 —— 代码可以纠正自己 derive 的东西，
  ⛔ 不该用词表否决 LLM 的语义判断。
- **零回归面**：LLM 没给 store 的路径逐字不变；LLM 给了但 resolver 不服务的路径
  逐字不变。只有「LLM 给了 + resolver 真能出」这一格从「删」变成「留」。
- **代价（诚实登记）**：它把正确性押在 LLM 的 `dimensions` 上。
  若某天 LLM 在纯汇总句上开始乱给 store，误伤会从「答非所问」变成
  「多给了一张门店表」—— 后者不是错答，是信息更多，代价可接受。

### 选项 3 的裁定理由

owner 的取舍顺序：**能不能决定 > 数字准不准 > 覆盖得全不全**。
选项 1 让「有几家店亏钱」这一句能决定，下一句不能；
选项 3 让**整个「按店拆」这一类**能决定。

| # | 变异 | 该红的断言 | 守的是什么 |

### 🔴 加第三个 AND 条件之后，原来那两条阴性对照**全部失效了**

第二版把 `explicit_store_scope != "all"` 加进 AND 链之后重跑变异：

```
M2 无条件豁免    → 实际变红 0 条   （第一版是红的）
M3 拆掉安全阀    → 实际变红 0 条   （第一版是红的）
```

⛔ 这**不是**「变异没打进去」——驱动脚本三层都证过了：锚点恰好 1 次、
落盘成功、`compile()` 通过。按形态 C″ 的判据，排除了那一头之后剩下的就是：
▎**那两条断言当时真的在守空气。**

成因：两条阴性对照的问句都写着「**全部门店**…」，于是
`explicit_store_scope == "all"` 成立，AND 链**在轮到它们各自那一半之前就短路了**。

▎**AND 链里新增一条，会让原有对照被新条件短路。**
▎新条件越靠前、越容易成立，被它遮住的下游条件就越多。

判据（以后每次往判据里加 AND）：
**把已有的每一条变异重跑一遍** —— ⛔ 不是「新条件加一条新变异」就完事。
修法是让每条阴性对照的输入**只落在它要测的那一半上**（这里是把问句里的
「全部门店」去掉），并在用例里**钉一条前提断言**说明为什么不能有那个词。

第二版修完后四条变异全部红在自己那一条上，零波及。
