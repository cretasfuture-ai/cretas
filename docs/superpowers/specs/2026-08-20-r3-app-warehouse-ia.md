## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像

**仓管员 / warehouse_worker** — 技术素养低，年纪偏大（客户原话：「做仓管的他年纪都比较大
文化素质很低，你不能太依赖他们，最好的方法就是你告诉他这个东西你要收多少就行了」）。
典型场景：站在货堆旁边、单手拿手机、光线不好，要在 30 秒内判断
「这批货我现在该做什么」并完成一次入库或发货确认。

### 用户旅程（发货侧）

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 首页「发货任务 (3)」 | 点开 tab | 只看到与发货有关的数，⛔ 不夹杂今日入库/库存预警 |
| 2 | 任务卡：客户 + 品名 + 数量 | 点某一单 | 进入发货确认 |
| 3 | 计划数量 + 实发输入框 | 填实发 | 超过计划立刻拦（Rule 1） |
| 4a | 批次已分配 | 点「确认发货」 | 成功，库存扣减 |
| 4b | **有行未分配批次** | —— | 页面**当场说清**哪几行、并给出**手机上走得通**的下一步 |

### 摩擦点清单

| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| F1 | 同一件事三个词混用：发货(68) / 出货(57)。仓管员不确定「出货管理」和「确认发货」是不是同一条路 | **HIGH** | 内联 UX·信息密度 |
| F2 | 「发货任务」tab 下摆着「今日入库 / 库存预警」——当前步骤不需要的信息 | **HIGH** | 内联 UX·信息密度（每屏只暴露当前步骤需要的信息） |
| F3 | 未分配批次时给的出路是「请先在**网页端**…」——仓管员手上只有手机，这是 dead-end | **HIGH** | fool-proof **Rule 5**（dead-end 改导航） |
| F4 | 首页顶部「库存状态」三节点图（8 需关注 / 52 使用中 / 29 可用）——占满一屏首屏，且答不上「我现在该做什么」 | **MED** | 内联 UX·信息密度 |
| F5 | 「出货」「出库」字面接近但是**两个概念**，混一起会诱导误操作（把领料出库当成发货） | **MED** | fool-proof Rule 2（上下文必带身份） |

### 每个摩擦点的设计回应

- **F1 → 统一为「发货」**，全端一个词。
  ▎选 `发货` 而不是 `出货` 的理由是**外部已经这么叫**：后端错误文案就写着
  「发货行 51 未完成批次分配」，web-admin 的入口叫「销售 → 发货记录」。
  改 App 一处，比改后端 + web 两处便宜，也符合 Steve 的第 ⑤ 条「对齐 web 端」。
  ⛔ **不动「出库」** —— 见 F5。

- **F2 → 统计卡跟着 tab 走**：发货 tab 只显示「今日发货 / 待发货」，
  入库 tab 只显示「今日入库 / 待入库」。库存预警数从这个网格里拿掉——
  它下面本来就有一整个「库存预警」区块，这里是**同一个数说两遍**（形态 D）。

- **F3 → 把 dead-end 换成手机上走得通的下一步**：保留「哪几行没分配」这个原因
  （它是对的、且是事先说清的），加一个**原地刷新**按钮（≥44pt）。

  🔴 **订正（实现时改的）**：这条设计回应最初写的是「换成应用内的调拨入口
  （首页已有 `TransferList` 路由）」。**那是错的** —— 拦住用户的是
  **「批次没分配」**，不是**「库存不够」**，而调拨解决的是后者。
  给一个解决不了当前原因的出路，比不给更糟：他会按着走一圈，回来发现还是发不了。

  ⚠️ 一般形式：**Rule 5 要的是「有下一步」，但那个下一步必须对应当前这条原因。**
  「dead-end 改导航」不等于「随便给个能点的按钮」。

  ⇒ 当前原因真正对应的动作是：别人在网页端分配完之后，他**在原地点一下继续**，
  不必退出重进、重新找这一单。网页端那句话保留为说明——
  确实有些事只能在网页做，⛔ 不能假装手机上什么都能干。

- **F4 → 移除首页「库存状态」节点图**。⚠️ 只在**仓储首页**移除，
  ⛔ 不删组件本身（其它角色的首页还在用它）。

- **F5 → 「出库」保持原样，并在设计卡里写死这条边界**：
  `出库` = 批次离开仓库这个**库存动作**（领料出库 / 扫码出库 / FIFO 优先出库 / 出库数量）；
  `发货` = 对着销售订单**发给客户**。两者不是同义词，合并会让「领料出库」被读成「发货」。
  ⚠️ 这一条是**故意不做**的登记，不是遗漏。

## 本轮**不做**的部分（显式登记，不是遗漏）

**③ 的「够不够」真值判断** —— Steve 的原话是
「看有没有足够的批次在我们仓库里面（餐厅库、冷冻库、包材库），没有的话就一定要去调拨」。

⛔ **做不了，因为数据不在手上**：`OutboundTask` 只有
`{id, orderId, customer, product, quantity, unit, status, dispatchTime, urgent}`，
**没有任何可用库存字段**，`shipmentApiClient` 也不返回。
要真做，需要后端出一个「按发货单逐行给出各库区可用量」的接口。

⚠️ **绝不用现有字段凑一个「够不够」出来** —— 那就是本仓反复记的
「把『我不知道』翻译成一个具体数字」。本轮交付的是 F3（不够时**有路可走**），
真值判断留给后端接口那一版。
