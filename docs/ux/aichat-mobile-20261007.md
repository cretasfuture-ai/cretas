# AIChatScreen 手机对话优化（B1-B9）

## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像
操作员、出成率录入员、仓管、质检员 — 日常使用手机完成查询和受控登记，技术素养差异较大，常在嘈杂生产现场单手操作；输入以语音为主，遇到追问时只愿补充缺少的一项。

### 用户旅程

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 空对话、紧凑推荐卡、语音输入 | 点推荐或说话 | 问题送出，推荐卡不再占位 |
| 2 | “正在理解你的话…” | 等待 | 3 秒内知道请求仍在处理 |
| 3 | 追问/错误的人话说明 | 补充缺少字段或点完整问题 | 只补当前槽位，保留上下文 |
| 4 | 查询卡片或窄屏分行结果 | 阅读并决定下一步 | 375px 内可读，不需横向滚动 |
| 5 | 写操作预览确认卡 | 检查并确认/取消 | 未确认前不产生写入 |
| 6 | 完成消息、👍/👎、复制菜单 | 反馈、长按复制或开始新对话 | 状态清楚，操作有反馈 |

### 摩擦点清单

| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| F1 | 没有真实追问芯片或把假问题展示给用户 | MEDIUM | 餐饮准则 8 |
| F2 | 失败时显示原始技术错误，慢请求没有阶段提示 | HIGH | fool-proof Rule 4 / 餐饮准则 14-15 |
| F3 | 空值、未知英文键和多余小数让用户误判业务数据 | HIGH | fool-proof Rule 1 / 餐饮准则 6 |
| F4 | 宽表、过小字号和小反馈按钮在手机上不可读或误触 | HIGH | fool-proof Rule 2 / 餐饮准则 5、9、13 |
| F5 | 无法安全清空旧会话，未确认写卡可能被误丢 | HIGH | 餐饮准则 18；写操作确认闸 |
| F6 | 阅读旧消息时自动滚动夺走当前视线 | MEDIUM | 餐饮准则 19 |
| F7 | 无法复制现场消息，或通过 Expo Web 无效的原生弹窗打断 | MEDIUM | 餐饮准则 20；项目 noRawAlertAlert |
| F8 | 反馈只覆盖食品知识，且后端能力边界不清 | MEDIUM | 餐饮准则 16；真实契约核验 |
| F9 | 空屏推荐卡过高，把输入区推到屏外 | HIGH | fool-proof Rule 5 / 餐饮准则 17、21 |

### 每个摩擦点的设计回应

- F1 → `suggestedActions` 继续表示澄清/候选操作；仅在 SSE 明确返回 `followUps`/`nextQuestions`（每项含 `label` + `question`）时渲染后续问题芯片。当前后端未生成该字段，前端只保留契约入口，不造假芯片。
- F2 → 独立错误消息使用“发生了什么 + 怎么处理”文案；请求先显示“正在理解你的话…”，超过 3 秒显示处理中的骨架；30 秒超时说明没有执行写操作。
- F3 → `null/undefined` 显示“暂无数据”；列表只显示有中文标签的字段；数字统一去掉无意义尾零；未知状态码不猜测。
- F4 → 375px 下 LIST 结果使用纵向记录卡；正文至少 16px、表格文字至少 13px；颜色全部来自主题 token；反馈与芯片触摸区达到准则尺寸。
- F5 → 顶栏“新对话”会取消 AbortController；存在 ready 的写确认卡时先用 appAlert 说明并让用户确认丢弃。
- F6 → 记录滚动位置，仅当距离底部不超过 120px 时自动滚底；用户向上阅读时保持位置。
- F7 → 消息长按先显示应用内菜单，确认后复制；不使用 `Alert.alert`。
- F8 → 所有已完成回答都可通过现有 `food-kb/feedback/submit` 显式评分，客户端携带任意 `intentCode` 与 `sessionId`；自动 `log-query` 仅对 `FOOD_KNOWLEDGE` 或带知识库元数据的回答启用。错误、流式未完成和 READY/未完成确认卡不显示评分。该接口语义是答案质量反馈，另有 `/ai-intents/feedback` 负责意图识别正确性，二者不混用。
- F9 → 推荐卡仅在空消息时渲染，采用紧凑两列布局并限制高度，输入区始终留在安全区内。

## 后端能力核验

- B1：工厂 SSE 响应类型已有 `suggestedActions`，但它的语义是澄清/候选操作，不是“接下来可以问”。实现为后端明确提供的 `followUps`/`nextQuestions`（每项含 `label` + `question`）保留契约和渲染入口；当前源码未发现该字段，故不造假芯片，后端补字段后才显示。
- B8：实查 `food-kb/feedback/submit` 的 `intentCode` 为可选字符串，没有知识类枚举限制；因此现有反馈客户端可携带任意意图的 `intentCode` 与 `sessionId`，对所有完成回答开放 👍/👎。它记录回答反馈，另有 `/ai-intents/feedback` 记录意图识别正确性，两者语义不混用。

## 验证边界

真实挂载 AIChatScreen 的测试桩仅覆盖网络/大模型 IO，不伪造后端业务结果；写操作仍走预览→确认→执行。浏览器截图若使用 fixture，只证明布局与交互，不代表真实业务验收。
