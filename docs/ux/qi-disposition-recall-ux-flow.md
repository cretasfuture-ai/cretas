# 质检员 App：不良品处置 / 批次召回 —— UX Flow Analysis

**日期**: 2026-11-12
**背景**: #1598 (B14) 把网页「不良品处置 / 批次召回」入口改成按质检模块权限放行，但质检员 (`quality_inspector`)
不登网页、App 里没有这两页，B14 对质检员实际不可用。本次在 RN 质检员端补齐两页，入口与按钮全部按后端权限判。

## UX Flow Analysis

### 用户画像
现场质检员 — 技术素养低到中，熟悉拍照/扫码，不熟悉 ERP 概念（「处置动作」「审批级别」「出货范围」）
— 典型场景：批次质检不合格后，站在车间里用手机决定「放行 / 返工 / 报废」；发现已出货批次有问题时发起召回并逐家记录客户联系。

### 用户旅程

**不良品处置**

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 首页「不良品处置」大卡片（有质检权限才出现） | 点卡片 | 进入处置页 |
| 2 | 「待处置」列表：每张卡带 批次号 + 品名 + 不合格/有条件放行 + 合格数/不合格数 | 点一张卡 | 进入该批处置页 |
| 3 | 页头 批次号·品名；「系统建议：返工」+ 理由；处置方式大按钮（建议项预选） | 选处置方式 | 选中项高亮；非放行时出现原因选择 |
| 4 | 标准原因选项（选「其他」才出输入框）；提交按钮显示「提交：返工 — 批次号」 | 点提交 → 二次确认（带批次号+动作） | 提交成功页：已执行 / 已送审（写明谁审） |
| 5 | 「等待审批」列表（只读）；有审批权限的人才看到「批准 / 驳回」 | 质检员只能看进度 | 不会点到自己没有权限的审批 |

**批次召回**

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 首页「批次召回」大卡片（有质检权限才出现） | 点卡片 | 召回列表（进行中在前） |
| 2 | 每张卡：召回单号 + 批次号 + 品名 + 状态 | 点卡片 | 召回详情 |
| 3 | 详情：剩余库存、每家客户出货量/已退/待退、是否已联系；卡住结案的原因 | 「记录客户联系」/「登记退货」 | 弹框带客户名+出货单号，退货数量上限预先显示 |
| 4 | 所有阻塞清掉后「确认结案」才可点 | 点结案 → 确认 | 状态变「已结案」 |
| 5 | 列表右上「发起召回」（有质检写权限才出现） | 选批次 → 看预览（库存/出货客户）→ 选原因 → 确认 | 召回创建，跳到详情 |

### 摩擦点清单
| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| F1 | 入口按岗位名单写死会把有权限的人挡在外面，或给没权限的人一个点了就 403 的按钮 | HIGH | fool-proof Rule 5 / 任务口径 |
| F2 | 「审批」按钮对质检员默认无权限，显示出来会点了被拒 | HIGH | fool-proof Rule 5 |
| F3 | 处置列表只有记录 ID，不知道是哪个批次哪种产品 | HIGH | fool-proof Rule 2 |
| F4 | 6 种处置动作名词抽象，不知道选哪个 | MED | 内联 UX：信息密度 |
| F5 | 报废/返工的理由随手乱写 | MED | fool-proof Rule 3 |
| F6 | 退货数量填超出货量，提交才报错 | HIGH | fool-proof Rule 1 |
| F7 | 连点提交重复发起处置 / 召回 | HIGH | fool-proof Rule 4 |
| F8 | 网络失败白屏、错误文案是英文/技术报错 | MED | 4 位一体 / 内联 UX：错误恢复 |
| F9 | 结案条件不满足时按钮能点，点了才说不行 | MED | fool-proof Rule 1 |
| F10 | 列表空时不知道是「没有」还是「没加载出来」 | MED | fool-proof Rule 5 |

### 每个摩擦点的设计回应
- F1 → 首页卡片按登录响应 `modulePermissions.quality` 判（与网页 B14 同口径：有 quality 读权限即显示），RN 不写任何岗位名单。
- F2 → 「批准 / 驳回」只在 `approval_quality_disposition` 为读写时显示（与后端 `@RequirePermission("approval_quality_disposition:approve")` 同一个码）；没有时「等待审批」列表只读并写明「由有审批权限的人处理」。
- F3 → 每张卡 = 批次号 + 品名 + 结果标签 + 合格/不合格数；处置页页头同样带批次号与品名。
- F4 → 进页即调后端评估，预选「系统建议」并显示理由；每个动作一行大按钮带一句白话说明和「需要审批」标记。
- F5 → 原因用标准选项（选「其他」才出输入框），放行以外必须选原因，否则提交按钮禁用。
- F6 → 退货框打开即显示「出货 X，已退 Y，还能退 Z」，数量超出 Z 时提交禁用。
- F7 → 提交中按钮 loading + 禁用；二次确认框；提交成功后返回列表并刷新（不停在可再次提交的表单上）。
- F8 → 错误以「发生了什么 + 怎么办」原样展示后端 message，并给「重试」按钮；表单已选内容不清空。
- F9 → 结案按钮按后端 `canClose` 禁用，下面逐条列出阻塞原因。
- F10 → 加载中 ActivityIndicator；加载失败显示错误+重试；真正为空才显示「没有待处置的批次」并给「返回首页」。

## 追加：超时处置（食品 DAG 缺口 14，2026-11-12）

**背景**: 操作员领用超时的半成品/原料会被拦，提示「请通知质检员在网页「质量管理 → 质检放行 → 超时处置」处理」。
质检员被网页 `MOBILE_ONLY_ROLES` 挡住，App 上又没有这页，于是处置走不通。Steve 拍板在 App 上加。
行为照网页 `ProcessTimeoutEventsTab.vue`；接口 `ProcessTimeLimitController`。

### 用户画像
现场质检员：同上。典型场景是操作员在车间喊「这盆料超时领不了」，质检员拿手机复检，当场放行或判不合格。

### 用户旅程

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 首页「超时处置」卡片（能看超时清单的人才出现） | 点卡片 | 待处置清单 |
| 2 | 每张卡：批次号 + 工序 + 「已超时 X」+ 超时数量 | 点一张 | 进入处置页 |
| 3 | 页头：批次号、工序 / 时限、起算时刻、截止、已超时、数量 | 选「复检放行」或「判不合格」（无默认） | 下方写清这个选择的后果 |
| 4 | 常用结论按钮 + 结论输入框（必填） | 点常用结论或自己写 | 提交按钮亮起 |
| 5 | 确认框：「复检放行 — 批次号」+ 后果 | 确认 | 回到清单并刷新；这条消失，记录页签多一条 |

### 摩擦点清单
| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| T1 | 放行是食品安全决定，若有默认值会被顺手点确认 | HIGH | fool-proof Rule 1 |
| T2 | 不知道放行后多久内要用完 / 判不合格后料去哪 | HIGH | fool-proof Rule 1 |
| T3 | 结论随手写成「好」「可以」 | MED | fool-proof Rule 3 |
| T4 | 两个人同时处置同一条，后提交的人报错后卡在表单 | MED | fool-proof Rule 4 / 5 |
| T5 | 没有权限处置的人点进去才被拒 | MED | fool-proof Rule 5 |
| T6 | 不知道是哪一盆料 | HIGH | fool-proof Rule 2 |

### 每个摩擦点的设计回应
- T1 → 处置结果两个大按钮，进页时都不选；没选不能提交。
- T2 → 选中后立刻显示后果：放行写「放行后 X 内可以领用，过了还要再处置」（或「不再限时」）；判不合格写「超时的 N kg 从库存转出，不能再领用」或「整批标为不合格」。确认框里再写一遍。
- T3 → 按结果给常用结论（与网页同一份），一点就追加；结论必填，空的不能提交。
- T4 → 提交失败时原样显示后端原因并重新读取清单；这条已经不在清单里（别人处置过）就退回清单，不留在会再失败的表单上。
- T5 → 入口按后端读权限（quality / production 任一可读）出现；「复检放行 / 判不合格」只在 `quality:read_write` 时显示，否则显示只读说明。
- T6 → 卡片和页头都带批次号 + 工序 + 超时数量；批次号缺失时写「批次号缺失」，不编。
