# 管理端数字专员工作台统一

依据：用户要求将已上线的批发商工作台样式统一到管理端所有工厂、客户的工作台，并统一称“数字专员”。沿用11-14组件库及现有岗位形象；不增加独立班组菜单，不修改客户原有模块或岗位授权。

范围为七个角色工作台，以及独立菜单中的AI价值工作台、配送排线工作台。质检页内部的ReviewWorkbench抽屉不是独立工作台，保留原业务形态。

| 原入口 | 统一岗位 | 实际能力边界 |
|---|---|---|
| sales-owner | 销售数字专员 | 原订单/客户/跟进业务；自由问题只读，写操作仍走原确认 |
| purchaser | 采购数字专员 | 原供应商/采购/库存预警；保留普通工厂已接入的采购操作 |
| warehouse-keeper | 库存数字专员 | 原待收、库存和仓储入口 |
| finance-manager | 财务数字专员 | 原财务报表与有资格的审批；审批身份不等于页面写权限 |
| quality-manager | 质量追溯数字专员 | 原追溯/召回，冻结、通知、关闭各自沿用权限及预览确认 |
| production-manager | 生产数字专员 | 原需求分析、起产预览和确认 |
| quality-chief | 质检数字专员 | 原待检批次、综合核对与放行预览确认 |
| dashboard/ai-value | AI价值数字专员 | 真实企业AI价值汇总，只有只读统计；无企业上下文时不查询，不伪造对话能力 |
| scheduling/logistics/workbench | 排线数字专员 | 原三步配送排线流程，生成路线本身有持久化写入；不伪装LLM聊天或自动生成 |

## UX Flow Analysis

### 用户画像

销售、采购、仓管、财务、生产及质检人员，熟悉各自业务、对技术界面熟悉程度不同。用户从原有菜单进入自己的岗位，要求称谓、形象、查询方式一致，同时继续使用已掌握的业务操作。

### 用户旅程

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|---|---|---|---|
| 1 | 原岗位菜单与数字专员形象/职责 | 打开工作台 | 等待真实企业和账号就绪，不使用默认企业 |
| 2 | 统一对话、当前状态、真实报告 | 提问或点击澄清 | READ查询保留上下文，失败可重试，不能把拒绝显示成已完成 |
| 3 | 原岗位业务数据和操作入口 | 核对单据/批次并办理 | 原权限、预览、确认、幂等和数量限制继续生效 |
| 4 | 明确的平台/排线能力 | 查看汇总或按步骤排线 | 现有API与领域流程继续使用；没有接入的AI动作不编造 |
| 5 | 新企业或新账号的空白状态 | 切换身份 | 先清空旧结果/预览/计划，再读取新范围，旧请求不能覆盖新结果 |

### 摩擦点清单

| ID | 摩擦点 | 严重程度 | 规则 |
|---|---|---|---|
| F1 | 统一外观时误丢原有审批/冻结/起产/放行功能 | HIGH | 原业务复用、上下文和确认 |
| F2 | 自由聊天误发写操作或将权限拒绝当成成功 | HIGH | 边界防呆、执行状态真实性 |
| F3 | 未绑定企业回退F006或切换后保留旧计划/数据 | HIGH | 身份边界、上下文、防重复 |
| F4 | 仅因更换外观开放原不可见的菜单/跨域写权限 | HIGH | 岗位权限及服务端资格 |
| F5 | 全平台汇总/排线算法被包装成不存在的AI对话 | MEDIUM | 真实能力、错误和空状态说明 |

### 设计回应

- F1：统一Frame与Conversation包裹既有业务区；原显式预览/写请求与自由READ查询分流，普通工厂既有操作保留。
- F2：自由提问使用统一意图接口的READ模式，保留会话和澄清；写操作沿用原表单/服务端确认，不新增无上下文快捷写。
- F3：清除F006回退，按factoryId+actorId重置页面状态并拒绝过期响应；物流清内存不得复用跨企业计划或写全局恢复抑制键。
- F4：导航仍按原角色/模块和企业菜单配置过滤，Frame只显示已允许路径；各写按钮沿用本身的业务权限与资格，不用单一页面权限扩大跨域授权。
- F5：平台只显示已有企业AI价值统计；排线保留原导入/预览/生成/确认流程，仅统一外层岗位呈现。空范围给出明确下一步。

验证覆盖：九个真实工作台入口、称谓/头像、READ与native写分流、跨身份清空、无默认企业、原菜单和资格阴性对照、构建/发布及生产只读界面核对。QA样例清理由另一数据scope单独留证，不创建其他客户样例。
