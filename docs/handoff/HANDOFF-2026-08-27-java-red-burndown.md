# Java 存量红的根因分解（2026-08-27）

**起点**：#183 落地夜间棘轮基线，量出 **143 条存量红 / 11891 个测试**。
在那之前这个数是拿不到的 —— 基线文件从没提交进仓，棘轮走的是
`BASELINE_MISSING → return RC_OK`：**跑完 8000 个测试然后无条件返回 0**。

**本轮结果**：**143 → 116**。而更要紧的产出是下面这张分解表 ——
**143 个名字压成约 14 个根因**，其中最大的一块（38 条，27%）不是缺陷。

## ⛔ 先说三条会让人做错事的判断

### 1. 「143 条红」≠「143 个缺陷」

实测根因约 **14 个**。按名字逐条修，会把一个根因修 28 遍。

### 2. 「改夹具让它变绿」是这里最危险的动作

至少两族的真相是**生产代码后来收紧了规则**，而不是测试写错了：

- 销售订单商品查找加了**工厂隔离**（`findByIdAndFactoryId`）
- 销售订单商品必须是**成品或半成品**，空分类**失败关闭**

把桩改成绕过它们，等于把两道真闸关掉。⇒ 每一族动手前先问：
**这条规则是有意加的吗？生产数据满足吗？**

（第二条的生产读数：`product_types` 234 行里 **10 行 `product_category` 为空**。
若那道校验在编辑既有产品时也生效，那 10 个产品现在改不了 —— **待查，未证实**。）

### 3. 本机跑绿 ≠ CI 跑绿

**50 条只在 CI 红，本机一条都不复现**（见下）。反过来「只在本机红」是 **0 条** ——
本机是 CI 的严格子集。

**分布高度集中**：

```

其余 5 个类                     12
```

**已排除的**：

| 假设 | 怎么证伪的 |
|---|---|
| 测试隔离 / 全量上下文污染 | 本机**全量**跑（11888 个测试）里 ProcessSheet 24 个类 174 个测试**全绿** |

  在本机挂死 17 分钟零输出）。CI 上它会跑。它的 Spring 上下文可能改变后续测试的行为。

## 🔴 附带查出的两个潜伏问题（都不紧急，但会咬人）

### A. `getActualQuantity()` 改名没有破坏编译，只是悄悄改变了含义

```java
生产:  calculateActualQuantity()   // @Transient 计算方法（新名字，含出成率折算）
旧名:  getActualQuantity()          // Lombok 给持久化字段生成的 getter
```

改名后旧名字**仍然存在**，所以所有调用点照常编译，只是从「计算值」变成了「持久化字段」。

生产实测：`bom_recipe_items` **73 行里 55 行 `actual_quantity` 是 NULL**。
`NutritionLabelGenerateTool` 在 null 时回退到 `standardQuantity` ——
而目前**没有任何物料设了出成率**（`yield_rate` 全是 null 或 100），
所以**今天两者等价，没有实际错误**。

⚠️ 但一旦有人设了出成率（比如 58%），营养标签就会用标准用量而不是折算用量，
**原料低估最多 40%**。

同一处的 `ProductionPlanServiceImpl` docstring 还写着
「`bomItem.getActualQuantity()` (已含出成率)」—— **描述过期**，
而同文件实际调的是 `calculateActualQuantity()`。

### B. 一个测试能挂死整轮跑批，而三态判定接不到

`IntentParityTest` 在本机挂死 **17 分钟零输出**（`@SpringBootTest`，卡在上下文启动）。

- surefire **没有任何超时配置**（`forkedProcessTimeoutInSeconds` 缺失）
- workflow 有 `timeout-minutes: 120`

⇒ CI 上一旦挂死，job 会被 GitHub 直接杀掉。而 `continue-on-error: true`
**只兜得住「失败」，兜不住「job 被杀」** ⇒ 棘轮那一步根本不会执行 ——
**既拿不到 rc=1 也拿不到 rc=2**，只有一个笼统的超时。

那正是三态设计要防的状态，而它有个洞。修法：给 surefire 加
`forkedProcessTimeoutInSeconds`（取值要 > 全量约 50 分钟、< job 的 120 分钟），
让挂死落到 **rc=2「没量到」**而不是「job 被杀」。

## 方法学：这一轮里被证伪的三个判断

写在这里是因为**它们都长得很像对的**，而且都是跑一次就能否掉的。

| 我当时的判断 | 怎么错的 | 判据 |
|---|---|---|
| 「7 个在产批次的 BOM 被人改过」 | 那 8 条记录**共享同一个微秒级时间戳**，是我自己 8-26 那条迁移干的 | **时间戳挤在一起 = 批量操作，不是人工编辑** |
| 「38 条是测试隔离问题」 | 本机**全量**跑它们也全绿 | 假设要用**同样规模**的跑批去验，不能用子集 |
| 「ProcessSheet 是时区问题」 | 换成加拿大时区跑，仍然全绿 | **跑一次问它**，比从配置推便宜得多 |

还有两次是我自己的仪器坏了：

- 阳性对照断言 `PATHS.length > 2`，**它绿着而解析器是坏的**（读到 4 条重复的，
  那 3 条要紧的一条都没进来）⇒ **阳性对照要量决定成败的那一维，不是量条数**
- 改写脚本的守卫写成 `if 'findByIdAndFactoryId' in s`，**匹配到了另一个
  repository 的桩**，四个文件全被误判成「已有」跳过 ⇒ **守卫要带前缀**

## 并行八路：没有一路走捷径

给每一路的禁令是「⛔ 不许为了变绿而改断言」。交回来的东西证明它落地了：

- **用仓里已有的证据反驳断言** —— `FgCostPropagationTest` 那 5 条基于「入库量优先取
  `productWeight`」，而它**与同目录两条正在通过的测试直接矛盾**。比读源码猜意图硬。
- **把守护方向反过来** —— 餐饮那两条守的是**已被显式删除的机制**，改成阴性对照
  `doesNotContainKey(...)`，让被删的东西不能悄悄回来。
- **唯一碰生产代码的那一路方向是收紧** —— 加 `@PriceSensitive`（多遮）。
  ALLOWLIST 那 3 个逐字核实过是单位码 / 换算比例，钱字段仍然遮着。
- **登记成具名例外而不是删掉不变式** —— 3 个财务工具确实需要 `finance:read_write`，
  打破了「`LEGACY_INFERRED` ⇒ 空权限」这条笼统假设。
