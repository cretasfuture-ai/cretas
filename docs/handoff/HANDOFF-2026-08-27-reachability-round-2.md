## 2. 🔑 本轮真正学到的方法（下一棒请照做）

### 接线之前先量三件事，⛔ 不是「看起来有就接」

```
① 生产上有没有数据?        —— 表行数 / 端点实打
② 有没有别的可用路径?      —— web-admin 有没有同一个页面 / App 有没有
③ 有没有卡住的单子?        —— status 分布里有没有堆积的 PENDING
```

**这三条把两件长得一样的事分开了**：

- **报表**（#224）：后端 27 个端点、实打 21/22 有真数据、web 有但手机没有、
  唯一挂载点恒假 ⇒ **接**。
- **HR / 审批 / 付款 / 领料**（web-admin 83 条孤儿里最大的几簇）：
  单据都在流转、**零待批**、审批走 App ⇒ **不接**（重复入口）。

⚠️ 我一开始把 HR 当高价值目标，量完才发现单子全办结了。**没有②③这两问，
   就会去接一批没人在等的页面。**

### 每条判据都要有能让它红的对照

本轮 8 次变异对照，**全部先撤回修复跑一遍**再声称守住了。形状最漂亮的一次是 #207：
去掉那一行兜底，**5 条转红**，而保持绿的 3 条恰好是三条阴性对照。

## 3. 唯一真正悬着的：OTA 送达未确认

```
2026-08-27 21:47  推了两棵树
  1.0.4/production  ts=1787838297410
  1.0.3/production  ts=1787838466856   ← 现场设备真正在问的那棵
```

🔴 **现场设备装的 APK 报 `runtime=1.0.3`**（服务器全量 OTA_PULL 100% 是 1.0.3），
而仓库三处版本号都是 1.0.4。只推 1.0.4 树 = 零交集 = 九天静默故障重演。
⇒ 按迁移期做法**双推**，用 `OTA_RUNTIME_VERSION_OVERRIDE=1.0.3`。

**已验证（服务器侧）**：以 1.0.3 客户端请求 manifest → 200，
`id=4bf39ae9-…`、`createdAt=2026-08-27T13:49:46Z`，与设备当前 `c72f63b3` 不同。

**未验证（真判据）**：设备侧 `outcome=update` + `current` 变掉。

```bash
ssh root@47.100.235.168 "grep OTA_PULL /www/wwwroot/cretas/python-prod.log | tail -5"
```

⛔ **日志里 ip=127.0.0.1 那条 `outcome=update` 是探针，不是送达。**
   只认 `121.228.99.40`（现场那台）。上一轮就是把自己的出口 IP 数成了现场设备。

⚠️ App 是 `checkAutomatically: "NEVER"` + `AppState` 切前台才检查
（`services/otaUpdateService.ts:214`）⇒ 要等用户下次打开 App，催不动。

📌 现场那台**一直是 1.0.3 二进制**。OTA 只能救 JS 层；1.0.4 的原生改动要重装 APK。

## 5. 🔴 本轮反复咬人的四个形态（每条带当天长相）

### ① 仪器造出假读数 —— 四次

| 长相 | 差点得出的错结论 |
|---|---|
| 日志判使用量，**阳性对照没过**（同窗口 `/users` 也是 0） | 「报表端点没人用」——其实日志根本不记请求路径 |
| `grep 'apiClient\.'` 数取数调用 | 「DataExport 什么都不做」——它手拼 URL 打 `/reports/export/*` |
| `find -name "report*.ts"` 抓到 `future/` 那份 | 「报表 client 是未来的」——屏用的是在用的那份 |
| `git log -S` 查依赖漂移 | 仓库 8-23 压平过，`package.json` 只有 1 个 commit，**git 答不了** |

⇒ **每个读数先问「我量的是不是我想知道的那个」，并配一条阳性对照。**

### ② 挂账让红变得可接受，于是没人再问它为什么红（#207）

那 8 个单测**确实红着**，但红的原因是另一道后加的闸（`assertPinnedDraft`），
一条断言都没跑到被测行为 —— 而功能在此期间**整个方法消失了**。
▎**「已挂账的红」和「坏了的红」长得一模一样。**

### ③ 判断错了一次，是报错文案把我拽回来的（#207）

第一版我把消失的方法原样恢复、喂 `standardQuantity`。**是错的** ——
P7 之后那是推导值，喂它会被覆盖或双重换算。
是那批测试的报错（「包材必须选择所在包装层级的业务角色…」）逼出来的。
⇒ **先分清「丢了」还是「被取代了」，再决定恢复还是撤承诺。**

### ④ 闸正确地红了一次，而正确做法是先解释再调（#209）

删掉 34 条死注册后 `roleReachability` 可达屏 397→364，跌破下限。
它自己的注释写着「变小是真的删屏了？确认后把三个数一起调小」。
⇒ 写探针在**同一棵树**上前后各跑一次，把少掉的 33 个**逐条 diff 出来**再调。
⚠️ **397 与 364 不可比**：屏一个没删，是口径变准了。报数要带口径。
