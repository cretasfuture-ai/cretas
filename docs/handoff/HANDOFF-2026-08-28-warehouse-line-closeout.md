## 1. 🔴 最重要的一条：**结构核对不等于行为正确**

裁定 ① 我配完条件节点、核对过「节点在、边在、条件串对、执行器口径唯一生效」，
就报告「配好了」。**行为一跑就塌**：

```
提交一张 55 行、零差异的盘点(F006 ST-202608-6B907387)

  OA 实例   APPROVED, currentNodeIds = []       <- 条件节点工作正常
  盘点单    PENDING_APPROVAL, approvedBy=null   <- 永久卡死
```

那张单**没有任何前进路径**：审不了（OA 无可操作节点）、驳不了（直接驳回接口返 410
「盘点审批仅能在 OA 审批中心执行」）、应用不了（`apply` 要求 APPROVED）。

⇒ **是 Owner 要求「视觉验收 / 走 E2E」才把它照出来的。** 纯结构核对会让这一轮
带着一个「已完成」的假结论收工，而真实用户提交第一张零差异盘点就会撞上死单。

## 2. 那个缺陷本身（#250，已合并）

```java
if (instance.isPresent()) {
    stocktake.setStatus(PENDING_APPROVAL);   // ← 从不看实例是不是已经结束了
```

把盘点单同步成 APPROVED 的代码**只长在 `transitionNode` 的处理里**，需要有人点一次。
而 `start → condition → end` 这种流程让实例**创建即完成**，那个人永远不会出现。

⇒ **「机制在、没接上」**：引擎支持 condition 直连 end，消费方却假设
「有实例 == 还要等人审」。**配置只是把潜伏缺陷暴露出来，不是配置的错。**

**改法**：实例已进终态就照抄结论（APPROVED/REJECTED），`CANCELLED`/`TIMEOUT`
在创建时出现则 409 报配置错，⛔ 不能落到 PENDING 再卡死一次。

⚠️ **Lombok 坑**（已写进代码注释）：`status` 有 `@Builder.Default` 给 `RUNNING`，
但 Lombok 把字段初始化器**搬进 builder 并从字段移除** ⇒ `new ApprovalWorkflowInstance()`
拿到的是 **null**。所以按「只有明确终态才特殊处理」写，⛔ 不能用穷举 `else` 兜底 ——
否则 null 掉进「配置错误」分支，打红一批无关用例。**我第一版就是这么写的，被自己那条下界测试拦下。**

**变异对照**：退回修复 → 4 条里**恰好 2 条红**（编码新要求的那两条），
两条守下界的保持绿 ⇒ 红了是发现，不是仪器坏。

## 3. 🔴 我四次订正自己 —— 每一次的成因都值得记

| # | 我先说的 | 实际 | 成因 |
|---|---|---|---|
| 1 | `RELEASE_SELECTION=none` ⇒「这次不会部署」 | **部署成功了** | 只读了开头就下结论；`--phase deploy` 显式指定时照样部署。**差点因此多跑一次发布，而两个发布并发写同一个共享 jar 就是 5-30 那个事故** |
| 2 | 「① 配好了」 | 会让盘点单卡死 | 只做结构核对，没跑行为 |
| 3 | 「RN 的 `start:*` 脚本至今无效」 | **早已修好** | 照着 8-15 的注释推断「还坏着」，没看当前文件。⚠️ 动手前查了一眼才没做重复改动并报一个不存在的缺陷 |
| 4 | 「手机 App 连不上后端、装的是指向死地址的旧包」 | **App 完全正常** | **我自己把密码输成了 7 位**（UI dump 里是 `•••••••`）。在这个坏读数上盖了一整套自洽因果链（ENVFILE 断链 → 回退模拟器回环 → 死地址），**而且它还有 8-15 的文档佐证，这让它更像真的** |

### 第 4 条的教训单独写

**一个错误读数 + 一份真实但不相关的文档 = 一个非常有说服力的错误结论。**

那些佐证每一条都是真的：`139.196.165.140:10010` 确实不通、`.env.test` 里确实记着
「实测不可达」、APK 里确实有 `10.0.2.2:10010` 这个串。**它们只是与手机登录失败无关。**

⇒ 判据：**先确认自己的输入是对的，再去解释输出。** 我应该在第一次失败时就
dump 一次 UI 核对密码位数（后来正是这么做才发现的），而不是直奔架构层找原因。
