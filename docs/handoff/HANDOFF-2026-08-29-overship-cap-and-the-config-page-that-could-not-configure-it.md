## 3. 超发上限（#308）

### 洞在哪

创建发货单时有一道 **0% 硬闸**，但仓管在 `warehouseConfirmDelivery` 覆盖**实发数量**时
**只挡负数、没有任何上限**：

```java
if (actual.signum() < 0) { throw ... }   // 那条路径上只有这一句
```

实测走通过一次「订 2 发 5」：**库存真扣 5 件、货真的出门、订单被置为 COMPLETED**。
采购侧早有 `overReceiveRate` + 异常单两样，销售侧两样都没有。

### 判据：`实发 ≤ 计划 × (1 + 上限)`

⛔ **不是**「累计实发 ≤ 订单量 × (1+上限)」。后者要重推跨发货单（主单/子单/已取消/拆单）
的累计账，而那本账**创建期已经算过了**：创建闸保证 `Σ计划 ≤ 订单量`。两道一叠即得

```
Σ实发 ≤ Σ计划 × (1+上限) ≤ 订单量 × (1+上限)      有界, 且可证明
```

⇒ 本闸**刻意窄**，javadoc 里逐条登记了它**不**守什么。

### 默认 0.10，⛔ 绝不是 0

`0` 会重演采购侧 2026-08-25 那个缺陷：默认 `:0.00` 让「没人配过」和「限制 0%」
不可区分，生产上按 0% 把货堵在门口。10% 意味着正常确认（实发 == 计划）溢出 0%、
完全不受影响。

### 复用 `OverReceiveLimit` 而不是克隆

会漂的**不是算术**，是那条「`null` = 不限制 / `0` = 一件都不许多」的语义。
采购与销售各有自己的**梯子**，但**共用一个值对象**，各自有自己的 `source` 常量。

⚠️ 类名仍叫 `OverReceiveLimit` 是**显式登记的「故意不改」**：改名要动
`PurchaseServiceImpl` 这条在跑的金额路径。正确的名字是 `QuantityOverageLimit`。

## 4. 顺带修的既有裂缝：38 个 key 建不出来

`ThresholdKeys` 已声明 **15 个前缀**的 key，而 `ThresholdCategory` 枚举只有 **6 个值**
⇒ `parseCategory` 拒绝其余 9 类，**那 38 个 key 在 API / UI 上一行都创建不出来**，
永远只能走代码里的 hard-coded fallback。

⚠️ 它**不报错、不抛异常、不变红**。唯一症状是「管理员在界面上找不到这一项」。

⇒ 补齐枚举 + `ThresholdKeyCategoryCoverageTest` 钉住不复发。闸是**反向**的：
不要求每个枚举值都有 key，只要求不存在「声明了 key 却没有分类装它」。

⚠️ **加枚举值安全，删/改名不安全**：`category` 是 `@Enumerated(STRING)`，
库里出现枚举没有的字符串会让**任何** `findByFactoryId` 全表查询在反序列化时抛异常，
把整个阈值中心页面打挂 —— 不是只挂那一行。

## 5. 🔴 视觉验收当场抓出的缺陷（#315）

页面全部通过：菜单点得到、路由对、真渲染、15 个 tab、「销售」分类在。
**但那一行不在。**

```
GET /api/mobile/F006/canvas-thresholds?category=SALES  →  HTTP 200, 0 行
```

而库里那行明明在（`flyway_schema_history` 成功、`factory_thresholds` 有记录）。

### 量出来的影响面（生产只读实测）

| factory_id | 行数 | 后果 |
|---|---:|---|
| `*`（全局） | 1 | 🔴 **所有工厂都配不了它** |
| `F006` | 23 | 只有这一家看得到东西 |
| **`LIUSHANMEN`（真实客户）** | **0** | 🔴 **管理员看到 15 个空分类** |
| `MOCK_REST` | 0 | 同上 |

⇒ 我在 #308 的迁移注释里专门论证过「⛔ 不给具体工厂插 per-factory 行 ——
没有 per-factory 行正好表达跟随全局默认」。那个论证对**解析梯子**是对的，
对**这个 UI** 是错的：列表接口按路径 factoryId 严格过滤，全局行永远不返回。

⚠️ **症状不报错**：接口返回 200、返回空数组，在每一项判据上都长得像
「这个工厂没有配置」。没有人会去查它。

### 修法：返回**有效配置**，⛔ 不补 seed

补 per-factory 行只治标：**下一个新建的工厂照样全空**，而且会造出 `N×M` 份重复数据，
全局默认值再也推不下去。

⇒ 列表按**解析梯子**返回：per-factory 优先，缺失时带出全局行并标 `inherited=true`。
这条梯子与 `ThresholdResolverService` **同源** —— 否则「页面上显示的」和
「运行时用的」会漂成两个东西，**那比看不见更危险**。

⚠️ **继承行的 `id` 属于全局那一行，对它 PUT 会改掉所有工厂的默认值。**
前端据 `inherited` 改走 POST 建本厂 override，界面标「继承全局」。

### A/B 段：配置模块本身

菜单点得到（⛔ 不是敲 URL）→ 落对路由 → **真渲染**（正文 1258 字、非闪屏特征）→

继承行走 POST 建 override；本厂行走 PUT 更新。

### C 段：改了配置，行为真的跟着变

**设计成不会真发货**（三次尝试的数量都远超上限，全部被拒 ⇒ 零副作用）：

```
上限 10%  → 409  「最大可发 88盒 (含 10% 超发)」
上限 50%  → 409  「最大可发 120盒 (含 50% 超发)」    ← 数跟着配置变
上限 500% → 超发闸不再开火, 被下游【有名字的】闸挡住:
            「可用库存不足，无法发货」                ← 证明真的走过了超发闸
还原 0.10 ✓
```

⚠️ **C3 的第一版判据是恒真式**（「不是超发上限那条错误」+「状态不是 200」——
任何错误都满足），它在一次 401 上假绿过。改成必须命中一个**说得出名字的下游闸**。

## 7. ⚠️ 本轮的仪器错（六个，全部当场抓住）

| # | 症状 | 真因 |
|---|---|---|
| 1 | 点击超时 30s | 命中的是文本测量用的副本 `<span class="menu-title-copy">` |
| 2 | 元素 `visible` 却 0×0 | 点顶级菜单是**开关**，把已展开的收起来了 |
| 3 | 展开后又变 0×0 | **`fullPage` 截图**滚动重排，把子菜单收起来了 |
| 4 | 再次 0×0 | **`scrollIntoViewIfNeeded()` 自己**把子菜单关了 |
| 5 | 「行不在」 | 15 个 tab 面板都渲染了，`.first()` 命中隐藏面板 |
| 6 | confirm 一律 401 | token 存在 **`cretas_access_token`**，我找的是 `token`/`accessToken` |

### 两条值得单独记

**a) 「阈值接口不带 token 也返回 200」是假警报。**
我是在**已登录的浏览器上下文**里测的，`credentials:'include'` 把会话 cookie 带上了。
换**全新上下文**（无 cookie 无 header）重测：401。带 token：200（阳性对照有效）。
⇒ **没有鉴权洞**，差一点就报出去了。
▎**在被污染的上下文里量鉴权，读数不可判定。**

**b) `git commit --only <paths>` 不包含未列出的删除。**
改 Flyway 版本号时我没把被删的旧路径列进去，结果 **HEAD 里两个迁移文件都在**，
而工作树只有新的那个：

| | |
|---|---|
| 本地 `mvn`（从工作树编译） | **绿** |
| CI（从提交的树构建） | **红** |

症状长成「我改号了但撞号还在」，极易被误读成改号没生效。
判据：`git ls-tree -r HEAD \| grep <文件名>` 必须恰好一条。

## 11. ⚠️ 环境雷（不是我的，但下一棒会踩）

`pwsh -File scripts/check-worktree-junctions.ps1` 扫出 **3 个指向仓库工作区的 junction**，
都在**别的 session** 的 worktree 里：

```
cretas-bp-hardening/web-admin/node_modules
cretas-integration-warehouse-finance-sales-workflow-20260823/frontend/.../node_modules
cretas-integration-warehouse-finance-sales-workflow-20260823/web-admin/node_modules
```

⛔ **谁 `git worktree remove --force` 掉左边那个，右边 target 的 `node_modules`
就会被递归删空**（2026-08-09/10 已真实发生两次）。

本轮没有摘链 —— 那会让那两条 session 的构建失效，属于动别人的活工作区。
摘链命令：`pwsh -File scripts/check-worktree-junctions.ps1 -Fix`
（只删链接本身，不动 target）。

我自己的 7 个 worktree 已用 `scripts/safe-worktree-remove.sh` 清理，
并核实主仓 `web-admin/node_modules` 完好（251 个子目录）。
