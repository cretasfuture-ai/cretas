# 用户操作时间线

本功能将“用户做了什么”与“服务端处理结果”放在同一条可查询时间线。业务字段的实际变更仍以 `operation_logs` 和各业务审计表为准；客户端点击不能证明事务成功。

## 记录内容

| 来源 | 记录 | 真实性 |
| --- | --- | --- |
| `screen` | 页面进入和路由模板 | 客户端上报 |
| `click` | 控件稳定标识、组件、禁用状态 | 客户端上报 |
| `input` | 字段名、长度；不存输入值 | 客户端上报 |
| `block` | 客户端校验规则和字段名 | 客户端上报 |
| `api` | 路由模板、方法、HTTP 状态、业务成功状态、错误码、耗时 | 服务端观察 |

Web 在文档级捕获按钮、链接、表单变更和原生校验拦截；RN 在根视图捕获点击手势并过滤滑动，导航变化记页面。业务代码可调用 `logBusinessAction('purchase.submit', { entityId: 'PO-123', quantity: 12 })` 或 `logActivityBlock('quantity.required', 'quantity')` 加上稳定语义。`data-activity-action` 和 `testID` 优先于通用控件名；新增关键按钮时应给它们稳定标识。

请求的 `X-Client-Action-ID` 在点击后五秒内附带，用于辅助关联；一个点击可能引发多个请求，因此这只是关联线索。`X-Correlation-ID` 是单次请求标识。时间线位于 Web 管理端“系统操作日志”页，仅工厂超级管理员和权限管理员可查询，查询始终限制在已认证的工厂。

## 存储和边界

- `activity_events` 与 `operation_logs` 分表。前者是高频诊断数据，180 天后分批删除；后者承载业务审计，不受此清理任务影响。
- 事件时间按 UTC 存为 `TIMESTAMPTZ`，查询返回带 `Z` 的时间；管理页面按浏览器所在时区显示。
- 每次客户端上报最多 20 条（服务端同样硬限 20 条）、请求体最多 64 KiB，每个已认证用户每分钟最多 12 批；服务端使用有界队列与批量写入。队列满或写入失败会输出错误日志，不阻塞业务请求。180 天清理每分钟最多删除 5000 行，需按实际吞吐监控积压。限流计数在单个 Java 实例内，不能充当跨实例的全局容量配额。
- 无人类动作关联且结果相同的 GET 在一分钟内折叠；不同点击引发的 GET、写请求均不折叠。异步 API 的初始 HTTP 状态附带 `asyncStarted=true`，代表连接已建立，并非流的最终结果。上报端不发送表单值、请求体、凭据或异常消息；服务端再按细节字段白名单过滤。
- 客户端事件带按账号去重的 `eventId`，响应丢失后的重试不会重复插入。App 失败批次按工厂和用户隔离保存在普通 AsyncStorage，最多保留 24 小时，退出登录或换账号时清理；此处仍有业务标识和操作元数据，设备本地数据保护与业务账号治理需一并考虑。Web 使用短时内存队列和页面隐藏时 `keepalive` 发送；登出/换账号立即清理。404/410 停发，413 缩小批次，429 延迟重试。断网、进程被强制结束、采集器被拦截等情况仍可能丢失行为事件，不得把时间线当作零遗漏的法律审计。
- 未登录操作、未进入 Spring MVC 的认证拒绝、部分直接 `fetch` 或未经过统一 API 客户端的请求，没有点击到请求的自动关联；服务端已认证的 `/api/mobile/**` 请求仍有独立 API 行。关键业务流程上线前应检查“页面 → 点击/拦截 → API → 事务审计”的实际链路。

## 容量观察

2026-09-27 只读核验：生产 `cretas-factory-api-audit.jsonl` 的 09-21 至 09-25 每日 2707–4721 行，Java 主机根盘尚余约 31 GiB。这只代表现有 API 审计量，不等同新时间线吞吐。按新事件为其 3–5 倍估计，约 0.8–2.4 万行/日、180 天 150–430 万行；如每行连索引按 1 KiB 粗估，约 1.5–4.3 GiB。上线后应每日读取 `activity_events` 当日行数、`pg_total_relation_size('activity_events')` 与写入失败/队列丢弃日志；若连续两天超过 2.5 万行/日、表及索引超过 5 GiB，或清理积压增长，先收紧保留期或完善采样/配额再扩大采集。估算不是容量保证，尤其客户端上报限流只在单 JVM，服务端自动 API 行没有同一限流。

## 验收

迁移可以在隔离 PostgreSQL 中验证：`scripts/ci/run-with-test-postgres.sh bash scripts/ci/test-activity-events-migration.sh`。该脚本只创建一次性测试库，核对两类事件与索引，并在 `autoCommit=false` 下运行 JDBC 写入、去重、按厂查询和到期清理测试。生产发布后仍须核对实际 Spring/JPA 装配、迁移和写后回读；隔离测试不代替这一步。

1. 在测试环境以工厂账号进入页面、点击有稳定标识的按钮、触发一次成功和一次业务失败；以管理员按用户与时间查询事件，检查路由、状态、错误码和关联 ID。
2. 检查相应业务审计记录的实体 ID 与字段变更；不能以客户端 `click` 或 HTTP 200 代替写后回读。
3. 输入密码、手机号和自由文本，确认 `activity_events.detail` 没有输入值；跨工厂账号不能查询或上报到另一工厂。
4. 检查队列满、入库失败、上报 413/429 告警和清理任务的日志；观察实际事件量与数据库增长后调整容量。
