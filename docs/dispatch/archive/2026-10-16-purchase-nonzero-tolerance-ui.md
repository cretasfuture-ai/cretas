## 场景设计与真实 UI 结果

新建一张合成采购单：面粉10箱（10kg/箱）、食品袋10包（10个/包），原计划各100个基本单位。创建人提交，另一名授权账号从真实OA页面审批。仅临时在该测试厂配置30%采购超收容差；工厂库存设置前置与恢复使用既有配置API，不将其称为配置UI验收。

| 检查 | 实际结果 |
| --- | --- |
| 初始上限 | 页面显示30%；两行计划均为10，累计可收上限均13，本次输入框上限13。 |
| 累计余量 | 先从真实UI收货各5，上传合成凭证并确认，新增50kg和50个库存；采购单保持PARTIAL_RECEIVED。再次打开收货页，计划剩余各5，但本次可收上限均8，正确包含容差余量。 |
| 范围内输入 | 页面允许录入面粉7箱、食品袋8包；累计分别12和13，即超收20%及恰好30%。没有把待收计划量5误当输入上限。 |
| 超限输入 | 面粉输入8.001箱，失焦后页面约束为8；累计上限13，无收货写请求。 |
| 后端最终拒绝 | 临时在31%规则下从UI保存8.001箱+8包草稿并上传凭证，UI更新后打开确认窗口；将该厂规则收紧回30%，实际点击最终“确认收货入库”，POST confirm返回409。页面明确显示“已收5、本次8.001、累计13.001、下单10、最大可收13、30%”。 |
| 修正原草稿并放行 | 刷新真实页面，确认显示当前30%规则；将同一草稿改为7箱+8包，UI更新及最终确认均200，新增70kg和80个库存。最终累计面粉12箱=120kg、食品袋13包=130个，采购单COMPLETED、已全部到货，待收任务消失。 |

31%仅用于制造可合法保存、尚未入库的旧草稿；最终拒绝和最终放行都按当前30%执行。没有篡改组件状态、伪造响应或重放收货写API。上一切片已通过的零容差创建/更新/确认三处拒绝直接复用，本批只补非零累计计算、允许区间、精确边界及最终入库拒绝。

## 金额读回口径

现有系统以锁定的四位未税单价计算实收行，逐行未税金额先取分，再乘税率并取分；与现有 `PurchaseOrderItem.getLineAmountWithTax` 和 `PurchaseServiceImpl.taxInclusiveReceivedValue` 相同。本批两张应付分别265.00、373.99，合计638.99，供应商余额增加638.99；没有实际付款。

初始辅助断言按页面显示的两位含税单价估算639.00，读回差0.01。核对上述已存在的合同和逐行舍入口径后，使用锁定单价、实收量及税率独立计算并匹配两条应付；未修改产品计税逻辑。收货数量、边界拒绝及零副作用断言全部保留。此验收不裁定将现有逐行舍入改为固定含税单价计价。
