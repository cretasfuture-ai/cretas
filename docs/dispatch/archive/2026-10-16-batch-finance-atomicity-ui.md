## 问题与增量

批量审批/驳回原先直接调用同类带 `@Transactional` 的方法，绕过 Spring 代理；余额保存与调整状态保存可能成为独立提交，后者发生版本冲突时无法撤回前者。

本次对每个 ID 显式使用主事务管理器的 `TransactionTemplate(REQUIRES_NEW)`，将原单条处理完整包入独立事务；提交完成后才增加成功计数，提交失败在事务外捕获，其他 ID 继续。保留逐条结果、部分成功、四眼、租户和版本校验。事务组件缺失返回 503，避免无事务执行。UI 实测发现的乐观锁异常 SQL 泄漏同步修复：Spring/JPA 乐观锁及其嵌套原因统一显示中文刷新提示。

无 Entity、Repository、迁移或 Web 源码变更。原单条业务逻辑保持原样，未扩大到采购异常入口的多操作者重复决定。

## 真实 UI、Hibernate/PostgreSQL 与余额读回

复用既有测试环境。通过真实采购退货 UI 新建并完成四张各 5 kg / 25 元的测试单，生成四条由独立主管提交的 PENDING 应付调整；此时余额仍为 **1,033.99 元**。库存前置从 197 kg 变为 177 kg；批量财审阶段不应再改库存。

| 同一调整，一页批量审批、另一页批量驳回 | 驳回成功；审批在 `ar_ap_transactions` 更新提交时版本冲突。最终 REJECTED，余额仍 **983.99**，失败审批的余额写入随事务撤回 |
