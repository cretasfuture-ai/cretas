## 本次增量

- 采购退货按实际收货的库存基本单位计算余额，扣除有货退货的待完成及已完成数量；拒绝累计超退。无货退款不占物理容量，驳回单释放容量。
- 源采购单事务行锁串行化容量决策。表单每次打开生成稳定 UUID；同工厂、typed actor 和请求键的重试返回原单，内容不同返回明确 409；键级事务锁覆盖不同来源单的同键竞争。平台与工厂同数值用户 ID 分属不同 namespace。
- 来源采购单始终执行行级权限检查；余额查询的精确路由使用采购单归属。前端显示服务器的“剩余可退”，并防止异步表单校验期间双击产生两次提交。
- 沿用完成出货、单条应付调整审批的原事务与乐观锁。无 Entity、Repository、迁移、生产配置变更；采购异常入口源码与 base 相同。

## 真实 UI 与 PostgreSQL 读回

使用既有测试工厂、采购单和收货记录，没有新增采购、收货或附件环境。基线实际收货为面粉 120 kg、包材 130 个；既有退货后剩余可退为 90 kg、80 个。

| 场景 | 实测结果 |
| --- | --- |
| 表单填写 91 kg | 按钮禁用；捕获的真实表单请求改为 91 kg 后端仍返回 409，无新增单据 |
| 表单双击创建 10 kg，捕获的同请求并发重放 | UI 仅发送一次创建；重放返回同 ID，数据库只有一张 10 kg 草稿 |
| 同键改变内容 | 409，明确提示幂等键对应的退货内容不一致 |
| 剩余 80 kg 时，两真实页面同时各创建 50 kg | 一次 200、一次 409，只有一张新 50 kg 草稿；刷新后余额 30 kg，填写 31 kg 禁用 |
| 两张草稿提交、业务审批、财务审批 | 库存、库存调整、应付台账与供应商余额均未变化 |
| 两真实页面同时完成同一张 10 kg 退货 | 200/乐观锁 409；只扣 10 kg，只生成一条待审批 -50 元调整，余额不变 |
| 正常完成另一个 50 kg 退货 | 两张单均 COMPLETED，累计扣 60 kg，只新增两条待审批调整 -50/-250 元 |
| 独立审批人两真实页面同时审批 -50 元调整 | 200/乐观锁 409；余额只减 50 元至 1,283.99 |
| 再审批 -250 元调整 | 应付余额 1,033.99；UI 对账/应付页与数据库一致 |
| 完成后并发重放原创建请求 | 返回原 COMPLETED 单；单据数量、库存、库存调整、应付台账和余额不再变化 |

最终库存 UI 与数据库均为：面粉 **197 kg**、包材 **350 个**。本次有效单据仅两张，合计 60 kg / 300 元。临时采购及财务模块覆盖经 UI 清除并恢复基线；用户、角色数据范围、原采购/收货/异常/既有退货记录不变。既有工厂 **505 张表**计数及指纹全部一致。

同键重放及绕过前端的阴性请求属于捕获真实 UI 请求后的 API 补充验证；创建、争抢余额、提交审批、完成出货、单条财审和最终页面读回均经真实 UI。脚本定位与等待错误已按状态读回后续跑，没有盲目重发业务请求。
