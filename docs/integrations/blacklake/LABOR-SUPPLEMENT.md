# 黑湖人工资料补查与计算

本轮仅查询任务、报工，沿用现有工厂绑定、连接锁、分页和限流。原始返回含人员字段，只在本机 CurrentUser DPAPI 加密保存，不提交仓库或送给模型。

官方动态文档的[查询报工返回参数](https://blacklake.feishu.cn/docs/doccn4ngN8QPClafs1duryGaLed#Ha4gWP)将 `productionStaffId` 定义为生产人员 ID。报工人、审批人、创建人及任务分配人员不能替代该字段；生产人员登记仍不能证明完整班组名单。

| 数据 | 用法与边界 |
| --- | --- |
| productionStaffId | 工厂范围内使用本机密钥做 HMAC，生成去重标识；公开预览只显示登记人数，不提供原始 ID 和姓名。 |
| effectiveTime / sumEffectiveTime | 本次非零记录与报工起止秒数一致，任务累计值与其报工合计一致。读数仍逐项核对；有未知休息、加班、停机扣除规则或时段/累计数不一致时保持待核。只叫报工有效时长，不当作人时。 |
| estimatedSalary / sumOutputSalary | 仅用前者核对报工与任务工资范围是否相等；成本金额仍取任务累计工资，不叠加报工工资。 |
| taskOperators / outputObject | 分配列表与报工权限不是实际参与者出勤名单，不据此补人数。 |

每分钟采集现有查询的同时保留最小必要字段，不新增每分钟查询次数。第一次补查返回419任务、384报工、6个生产人员登记ID；全部报工已审批，168条为零有效时长；376个有报工任务的有效时长累计对齐，全部419个任务的工资对齐（无报工零工资任务单独识别）。这些是本次查询范围的登记记录，不是全厂实际人数。

补查同时发现一张此前工单本轮未返回，旧采集器因此停止替换整批数据。现在将其独立保存为 `unreturned_project` 来源核对记录，包含工单号、最后可见时间、旧轮次、负责人及核对动作；旧轮次完整内容仍在 SQLite，不推定删除。当前统计只用本轮真实返回的工单，未返回记录单独在页面提示；记录重新出现后关闭当前缺口，历史轮次不改写。其余工单继续受原分页、工厂、父子关联、重复和业务响应校验保护。

可用计算：工序已记录工资、单位成品人工费、登记人员去重计数、累计报工有效时长；任务工资及人员对应完整、工序金额对齐后，计算“按登记人员测算人均”。该测算明确标记班组代报限制，不替代真实班组人均。

公开预览的既有人事字段过滤保持不变，HMAC 人员标识也不传给网页。`GET /labor-summary` 在原有工厂和 FULL 成本授权后，绑定选中工单与不可变来源快照，在服务端完成跨工序去重及平均，只返回人数、金额和工序计数。网页切换产品/工单后重新取同范围结果；过期响应不覆盖新选择。

仍需车间主管/班组长确认实际班组名单及每段实际参与人数。零时长、同人重叠报工需要确认计时方式、代报或补录；工资不一致时另找财务。页面按所选产品/工单列出逐工单、逐工序的缺项、负责人、核对动作和补齐用途。确认真实人数前，不启用人时分摊。

后续确认资料的计算规则保持为：人均＝同范围人工费÷去重实际参与人数；每人时费用＝人工费÷实际人时；工序人时＝各时段时长×该段实际人数；分摊测算＝同一人工费×工序人时÷总人时，最后一个正权重工序接收分币尾差。已记录的计件工资仍按原工序展示，测算不修改工资或账目。
