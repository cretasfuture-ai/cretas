# F006 角色权限与 Web / App / 跨端全链 E2E

## 1. 目标与完成定义

本轮以 F006 专用测试租户验证六个必要角色能否完成完整业务链，并验证每个页面、行内操作、接口权限、控制台错误和跨端交接。测试完成不等于交付完成；只有缺陷修复、目标测试、离线合入本地 `main`、生产发布、进程启动时间晚于制品 mtime、线上复验均通过，才可标记 delivery complete。

业务链按现行财务红线固定为：

`采购下单/订单 OA 审批 → 仓储收货入库并生成未清应付 → 财务确认付款并核销指定应付 → 销售下单 → 生产计划/批次/逐道报工 → 质检 → 仓储发货 → 财务开票/收款`

交接中的“付款先于收货”属于已退役的采购付款申请链。2026-08-23 线上实测 `POST /payment-requests` 返回 410 `PAYMENT_REQUEST_LEGACY_WRITE_DISABLED`；现行后端只允许从收货生成的 `AP_INVOICE` 未清项调用 `/finance/payables/{id}/settlements`。不得为了保持旧顺序恢复会产生未分配付款的入口。预付单在当前模型下仍先完成采购订单审批，实际资金核销等待可审计未清应付生成。

每次角色切换必须先退出，再使用目标账号重新登录；禁止复用上一个角色的权限缓存。

## 2. 数据与写入边界

- 所有业务写入只允许 `factoryUser.factoryId === 'F006'`，首次写入前必须从实时登录响应证明租户。
- 测试业务键统一带 `E2E-RBAC-20260823-<runId>`，记录创建的订单、计划、批次、质检、入库、发货、发票和收款 ID。
- 收尾只删除或撤销本轮创建且可证明属于 F006 的记录；不清空 F006 历史数据，不触碰其他租户、共享字典或全局配置。
- 价格掩码与角色页面普查使用生产只读 harness，要求 `actualBusinessWrites = 0` 且 blocked mutation attempts = 0。
- 有写入的 F006 流程使用独立任务脚本或真实 UI，不扩大只读 harness 白名单。

## 3. 三套执行流程

### A. 纯 Web Admin

1. 角色登录与身份：验证 username、role、factoryId、菜单和首页。
2. 页面普查：逐个打开该角色菜单页、隐藏直达页和必要行内入口；记录 200、预期 403、非预期 403、404、5xx、错误 toast、console error、page error。
3. 采购：采购主管新建并提交采购订单；刷新列表和详情，验证订单 OA 审批结果及财务侧可读。
4. 仓储收货：仓储主管从采购来源任务收货，校验批次、数量、单位、质检门禁和库存增量；采购侧回读实收，并确认生成与本次收货绑定的 `AP_INVOICE` 未清应付。
5. 财务付款：财务主管只从该 `AP_INVOICE` 行发起付款核销；验证付款凭证、幂等键、allocation、未清金额、供应商余额和采购单关联，采购侧回读付款状态。旧付款申请页只允许查询历史记录，不得出现新建/提交/审批/确认付款动作。
6. 销售：销售主管创建并确认销售订单，校验客户、SKU、数量、单价、税额和生产交接。
7. 生产：生产主管创建计划、生成批次并完成逐道录入；刷新后核对任务、批次、消耗、产出和状态。
8. 质检：质检员处理目标批次，先执行价格掩码阴性验收，再提交真实质检结果并由上下游回读。
9. 发货：仓储主管按销售订单创建/确认发货，校验精确批次、扣库一次且订单状态同步。
10. 财务收尾：财务主管开票、登记收款并核对 AR、发票、收款和销售订单状态。

每个写步骤必须具备：提交前 F006 scope、精确请求/响应或 toast、刷新后持久化、详情页回读、下游模块回读、记录 ID、截图。

### B. 纯 App / Expo

1. 使用 Expo 启动 App，逐角色退出重登。
2. 覆盖角色首页、工作台、列表、详情、表单、扫码替代入口和错误态。
3. 生产侧执行报工/逐道录入；质检侧处理同一批次；仓储侧执行采购入库与销售发货。
4. 每个动作检查提交、持久化、刷新、详情回读和错误提示，不以页面能打开作为通过。
5. 当前机器无 ADB 与 Maestro；本轮可立即执行 Expo Web 的 App UI。真机/模拟器原生验收单列为 native gate，环境未具备时标记 blocked，不能冒充已通过。

### C. Web ↔ App 跨端

1. Web 采购/销售创建的业务记录，App 必须按精确业务键可见。
2. App 的报工、质检、入库和发货写入，Web 刷新后必须显示相同记录 ID、数量、时间和状态。
3. Web 订单 OA 审批或应付付款核销后，App 不得继续显示旧的可操作状态；App 完成仓储动作后，Web 库存、订单和财务状态必须一致。
4. 最终守恒：采购数量 = 收货数量 + 合法未收；生产投入/产出与批次状态一致；发货扣库一次；应付/应收、发票和收付款不重复。

## 5. 缺陷处理循环

1. 先分类为产品缺陷、测试脚本缺陷、数据前置缺陷或部署前置缺陷。
2. 产品缺陷先新增会红的聚焦断言，再做同因扫描；涉及角色访问范围必须同时检查模块矩阵、菜单 roles、`hideForFactoryTypes`、`ROLE_PATH_WHITELIST`，以及后端 `@RequirePermission` 与 `@RequireModule`。
3. 砍权限前运行 `scripts/check-menu-permission-drift.py` 预演，要求新增漂移 0；脚本的六类已知盲区必须人工补查。
4. Flyway 编号只在真正需要迁移时重新扫描目录；已知 `V20261030_18` 已占用，不预留、不猜号。
5. GitHub 停用期间，修复在独立 `codex/*` worktree 完成并通过目标门禁，再串行 no-ff 合入 `cretas-mainmerge` 本地 `main`。
6. 从 `cretas-deploy-offline` detached 到精确本地 main SHA，使用 `SKIP_GIT_CHECK=1` 发布。每次 Java 发布后必须验证进程启动时间晚于制品 mtime；短路误判时用 `FORCE_REDEPLOY=1`。

## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像
F006 仓管 — 低技术素养、以手机完成现场收货 — 打开 App 后应直接从“入库”进入待办，不应理解生产/库存模块边界或寻找被隐藏的库存 Tab。

### 用户旅程
| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 入库首页唯一主操作“待收货任务”，下方是降级的“生产成品入库”入口 | 点“生产成品入库” | 进入已有中转实收确认屏，不恢复库存 Tab |
| 2 | 精确产品名、计划单号、批次、生产报产量和目的仓 | 核对系统预填的实收数量 | 每条产出都有上下文，数量不得超过生产报产 |
| 3 | 每张待办卡只有一个“确认实收”按钮 | 填可选备注并确认 | 幂等提交一次，成功后该卡从待办消失 |
| 4 | 网络或业务错误 | 点“重试”或按明确提示处理 | 已填数量保留，不出现空白屏或技术错误码 |

### 摩擦点清单
| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| F1 | 中转实收屏只注册在已隐藏的库存 Tab，仓管无法到达 | HIGH | fool-proof Rule 5 |
| F2 | 若恢复库存 Tab，会把盘点、预警、温控等办公室信息重新压给现场仓管 | HIGH | 内联 UX 规则：信息密度 |
| F3 | 生产成品与采购收货混在同一批次列表会让仓管无法判断任务来源 | MED | fool-proof Rule 2 |
| F4 | 数量误填或重复点击可能造成错收、重复入库 | HIGH | fool-proof Rule 1 / Rule 4 |

### 每个摩擦点的设计回应
- F1 → 把既有 `WHTransitLedger` 同时注册到入库 Stack，并从入库首页提供可见入口。
- F2 → 保持 `SIMPLIFIED_WAREHOUSE_NAV=true`，库存 Tab 继续隐藏，只开放这一条现场动作。
- F3 → 入口明确命名“生产成品入库”，目标屏继续显示产品名、计划单号、批次和方向。
- F4 → 复用目标屏现有报产上限、等量校验、disabled 提交和后端幂等键，不新造写接口。
