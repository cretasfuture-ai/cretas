# 产线人数怎么配：详细配置方案（给老板看）

日期：2026-11-14 · 状态：方案，未实现（第 1 步「按产线配最少/最多人数、技能等级」已随本 PR 上线网页入口）

## 一句话

以前的「标准人数」只是每条线一个数，插单时拿来和当天排班的人数比。工厂里真实的情况更细：同一条线做不同产品要的人数不同，不同工序要的人不同，白班夜班不同，有些岗位必须有特定的人（比如必须有 1 名质检、1 名持证操作工）。这份方案把「人数」拆成五个维度：**产线、产品、工序、班次、岗位和技能**。每个维度说清五件事：工厂里的例子、数据怎么存、谁会用、不配置时怎么办、建厂对话里怎么配。最后给出先做哪个、后做哪个。

**总原则（Steve 定的方向）**：怎么比较、怎么提示由系统统一做（机制）。每个厂要什么人、要几个，由这个厂在建厂时自己配（策略）。**不配就不比较**，系统不会自己编一个默认人数去比。人不够**只提示、不拦**（11-10 裁定），以后哪个厂要拦，用工厂开关打开，默认关。

## 两份「最少人数」：standard_workers 和 min_workers

### 现状

| | `standard_workers`（插单最少人数） | `min_workers`（APS 内部） |
|---|---|---|
| 哪来的 | 2026-11-11 `V20261111_01` 新加，可空 | 2025-12 建表时就有，`DEFAULT 1` |
| 现有数据 | 网页「人数配置」写进去的才有值，没配是空 | 每条线都有值，绝大多数是默认的 1 |
| 能不能分出「没配」 | 能：空就是没配 | 不能：1 可能是默认值，也可能是真配的 1 |
| 网页怎么叫 | 「插单最少人数」；接口字段叫 `insertMinWorkers` | 网页不显示 |
| 谁写 | `PUT /scheduling/production-lines/{id}/staffing` 的 `insertMinWorkers`；旧接口创建/更新产线时的 `standardWorkers` | 旧接口创建产线时的 `minWorkers`（不传就写 1）、更新产线时的 `minWorkers` |

### 合并之前谁读哪一份（以代码为准，2026-11-14）

| 读的人 | 读哪一份 | 位置 |
|---|---|---|
| 紧急插单：生成时段的人数要求、确认时比较排班、workerStatus | **只读 `standard_workers`** | `UrgentInsertServiceImpl.generateInsertSlots`，经 `InsertSlot.requiredWorkers` 到 `checkWorkers` |
| 网页「产线产能与设备」人数配置 | `standard_workers`（显示和保存） | `web-admin/src/views/scheduling/line-capacity/index.vue` |
| APS 自适应排程模型特征 | `min_workers` | `APSAdaptiveSchedulingServiceImpl` 约 968 行（空时取 0.5） |
| 调度 AI 请求 / 特征 | `min_workers` | `SchedulingAIServiceImpl` 约 591、670、676 行（空时取 5） |

规矩：**合并之前，新功能一律读 `standard_workers`**，不得新增对 `min_workers` 的读取。

### 以后怎么合并（阶段 A，一个 PR，强制走 PR，因为动迁移和实体）

1. **先量现状**：在 prod 只读统计每个厂 `min_workers` 的分布，以及 `standard_workers` 非空的条数，把结果写进 PR 描述，作为前后对照。
2. **迁移**（一个 Flyway 脚本）：
   - `ALTER TABLE production_lines ALTER COLUMN min_workers DROP DEFAULT;`
   - `UPDATE production_lines SET min_workers = standard_workers;` 回填后，没配的线变空。
   - 保留 `standard_workers` 列一个版本，不删，方便回滚；在列注释里写明「已废弃，读 min_workers」。
3. **代码同一个 PR 里改**：
   - 插单和网页改读写 `min_workers`；实体去掉 `minWorkers = 1` 的默认值；创建产线不传就存空，不再写 1。
   - APS 两处读取保持今天的读数：读到空值时按 1 处理，就是迁移前绝大多数线的值。这样排程模型的输入不会因为合并而变化。要在测试里钉住「迁移前后同一条线的特征值相同」。
   - 网页和接口字段名保持「插单最少人数 / insertMinWorkers」，只换后面存的列，用户无感。
4. **验收**：迁移前后各数一次。判据：已配线数 = 迁移前 `standard_workers` 非空数；插单比较结果在同一批产线上不变（配了的照比，没配的照旧不比）；APS 特征值不变。
5. **下一个版本**确认无人读 `standard_workers` 后，再删掉这一列。

## 维度一：按产线

**工厂里的例子**：卤制一线是大锅线，最少要 4 个人才转得动：投料、看锅、出锅、装筐各 1 人。包装线是半自动的，2 个人就够，最多站 6 个人，再多就挤在一起了。

**数据结构**：已有（见上表），不用新建。

**谁会用**
- 插单：已经在用最少人数。
- APS 排程：排某条线时，当班人数少于最少人数，就把这条线标「人手不足」，产能按比例打折；多于最多人数的部分不算产能（站不下）。
- 开工检查：班组长点「开工」时，到岗人数少于最少人数，就提示「本线最少 4 人，现在到岗 3 人」。

**默认值 / 不配置**：不填就不比较。最多人数不填，就不设上限。

**建厂对话里怎么配**：助手问「每条线最少几个人才能开？最多能站几个人？」，老板答「卤制线最少 4 个，最多 8 个；包装线 2 到 6 个」，助手复述后写入。老板答不上来也可以跳过，事后到网页上补。

## 维度二：按产品（同一条线做不同产品，人数不同）

**工厂里的例子**：同是卤制一线，做整只猪蹄要 4 个人；做切片猪蹄要多 2 个人上切片台，就是 6 个人。做礼盒装要多 1 个人摆盒。

**数据结构草案**：新表 `line_product_staffing`

| 列 | 说明 |
|---|---|
| factory_id | 租户隔离 |
| production_line_id | 哪条线 |
| product_type_id | 哪个产品；**空 = 这条线所有产品通用** |
| min_workers / max_workers | 人数 |
| effective_from / effective_to | 生效区间，改了留历史（和产能配置 `line_capacity_configs` 同一个写法） |
| source | 工厂配置 / 对话建厂 |

**取值顺序**：先找「这条线 + 这个产品」，找不到再用「这条线通用」，再找不到就不比较。和网页上「每小时产能」配置的取值顺序完全一样，老板只要学一种规矩。

**谁会用**
- 插单：插的是哪个产品，就用那个产品的人数去比。这是最直接的收益，因为插单本来就知道产品。
- APS 排程：排到哪个产品，就用哪个产品的人数判断这一班能不能开。
- 开工检查：按生产计划上的产品取人数。

**默认值 / 不配置**：退回到产线通用值；产线也没配，就不比较。

**建厂对话里怎么配**：助手在录完产品清单后追问「有没有哪个产品比别的要多几个人？」。只记老板说出来的例外，别的产品都用产线通用值。不要求逐个产品填。

## 维度三：按工序

**工厂里的例子**：一个卤猪蹄的工艺是：解冻 → 清洗 → 卤制 → 冷却 → 切片 → 包装。卤制只要 1 人看锅，切片要 3 人，包装要 2 人。各工序同时开工的话，这条线一共要 6 人。工序之间错开的话，同一时刻最多要 3 人。

**数据结构草案**：产品工艺里已经有每道工序的字段 `ProductType.processingStages`，格式是 JSON，每道工序已经带 `requiredSkillLevel`（技能等级）。在同一个 JSON 里每道工序再加 `minWorkers`，不建新表。

```json
[{"stageType": "SLICING", "orderIndex": 5, "requiredSkillLevel": 3, "minWorkers": 3, "estimatedMinutes": 30}]
```

**谁会用**
- APS 排程：这是工序级排程的前提，用来判断某道工序这一时段有没有人。排程是工序级时才有意义。
- 开工检查：报工开某道工序时，比较这道工序的到岗人数。
- 插单：用不到这么细。插单仍然看产品或产线总人数，避免插单页一次冒出几十条提示。

**默认值 / 不配置**：工序没填人数，就用产品或产线的总人数，工序级不比较。

**建厂对话里怎么配**：录工艺流程时顺带问「这一步要几个人？」，可以跳过。只要一道工序填了人数，助手就会提醒「其他工序也填一下吗？不填就不按工序比较」。

## 维度四：按班次

**工厂里的例子**：白班卤制线开满 6 人；夜班只做冷却和包装，3 人就够。周末不开切片，人数也不同。

**数据结构草案**：在维度一或维度二的人数表上加一列 `shift_code`，**空 = 所有班次通用**。班次编码沿用排班模块已有的班次定义，不另起一套。

**取值顺序**：先「产品 + 班次」，再「产品通用」，再「产线 + 班次」，再「产线通用」，都没有就不比较。网页上要把这条取值顺序写给用户看，并在比较结果里写明「这次用的是哪一条配置」。

**谁会用**
- 插单：插单时段落在哪个班次，就用哪个班次的人数。夜班插单不会被白班的人数误报「人不够」。
- APS 排程：按班次排的时候用。
- 开工检查：按当前班次比较。

**默认值 / 不配置**：用不分班次的值。

**建厂对话里怎么配**：只在老板说过「有夜班」或「分几个班」之后才追问「夜班人数和白班不一样吗？」。不分班次的工厂完全不会被问到。

## 维度五：按岗位和技能（例如必须有 1 名质检、1 名持证操作工）

**工厂里的例子**：卤制一线开工必须有 1 名质检员在岗，因为 CCP 温度点要有人签字；必须有 1 名持叉车证（或压力容器操作证）的人，没有就不能开锅；切片工序的人技能等级要 3 级以上，新手切不匀。

**这和前面四个维度不一样**：前面四个只管「几个人」，这一个管「要什么人」。总人数够了，但没有质检，仍然是不满足。

**数据结构草案**：新表 `line_staffing_requirements`，一条线（可细到产品、工序）可以有多条要求：

| 列 | 说明 |
|---|---|
| factory_id / production_line_id | 必填 |
| product_type_id / stage_type / shift_code | 可空，空 = 通用（取值顺序同上） |
| requirement_type | `ROLE` 岗位 / `SKILL` 技能 / `CERT` 证书 |
| requirement_key | 例：岗位 `quality_inspector`；技能 `切片`；证书 `压力容器操作证` |
| min_level | 技能时用，例：3 |
| min_count | 至少几人，例：1 |
| severity | `HINT` 只提示（默认）/ `BLOCK` 拦住（要工厂开关打开才生效） |

人员这边已有的字段：`users.position`（岗位）、`users.skill_levels`（JSON，例如 `{"切片": 3, "质检": 2}`）。**证书目前没有地方存**，要新增「人员证书」（证书名、编号、有效期），过期就不算。

**谁会用**
- 开工检查：最主要的使用方。开工那一刻对照到岗名单，缺质检、缺持证人就提示。工厂把这条设为「拦」的话，就不让开工（同「缺料开工拦截」，是工厂级开关，默认关）。
- 插单：点名派人时提示「这批人里没有质检员」。不点名的时候，只核对当天班上有没有这类人。
- APS 排程：排人时优先满足硬要求，比如先把质检排进去。

**默认值 / 不配置**：没有要求就不检查。证书过期的人不算满足要求。

**建厂对话里怎么配**：助手问「开线时有没有必须在场的人？比如质检、持证的操作工？」，老板说「卤制线要 1 个质检、1 个有压力容器证的」，助手生成两条要求，**默认只提示**，并问一句「人不在时要不要拦住不让开工？」。老板说要拦才设成拦。

## 推荐分期顺序

| 期 | 做什么 | 为什么排在这 | 动不动库 |
|---|---|---|---|
| **A（下一步）** | ① 合并 `min_workers` 和 `standard_workers` 两列（迁移：`min_workers` 去掉默认值、改为可空，用 `standard_workers` 回填；APS 读到空值时沿用今天的读数）② 开工检查接上产线最少人数（只提示）③ 建厂对话加「每条线几个人」 | 收掉「两个最少人数」这个隐患；开工检查是班组长每天看得到的地方 | 一次迁移 |
| **B** | 按产品配人数（维度二），插单按产品取 | 插单本来就知道产品，收益立刻能看到；写法照抄产能配置，风险低 | 新表 |
| **C** | 岗位和技能要求（维度五）：先做岗位和技能等级（人员字段已有），只提示 | 「必须有质检」是食品厂的硬需求，和 CCP 签字直接相关 | 新表 |
| **D** | 人员证书 + 证书类要求 + 工厂开关「缺人拦开工」 | 证书要新录数据，等 C 跑顺了再做 | 新表 |
| **E** | 按班次（维度四） | 现在的工厂多数是单班；有夜班的厂提出来再做 | 加列 |
| **F** | 按工序（维度三），并接入 APS 工序级排程 | 依赖 APS 先做到工序级；单独做工序人数用处不大 | 改 JSON |

**每一期都保持**：不配就不比较；人不够默认只提示；比较结果里写明「这次用的是哪一条配置、来自建厂对话还是工厂配置」；跨厂一律按 factory_id 隔离。
