## UX Flow Analysis

### 用户画像

首道报工操作员通常在车间手机上完成领料，可能戴手套、时间紧、对 FIFO/FEFO 术语不熟，但需要清楚知道“本次总共投多少、系统从哪几批扣、哪里还没填完”。

### 用户旅程

| 步骤 | 用户看到 | 用户操作 | 系统反馈 |
|---|---|---|---|
| 1 | 已选一个批次，并在报工页填了本次投入量 | 展开领料批次 | 显示当前批次可领量；若本批不足，立即解释需要多批次 |
| 2 | 同一张决策卡，主操作为“按效期优先自动分配”，次操作为“手动选择批次” | 选择自动 | 系统只为同一原料调用现有 FEFO 推荐，按推荐顺序分摊本次总投入量 |
| 3A | 自动结果卡 | 核对每批数量，必要时切到手动修改 | 显示目标量、已分配批次数、是否足量；批次身份仍逐条保留 |
| 3B | 手动引导 | 继续勾选 2–5 个批次并逐批填写 | 首批原投入量保留，所有输入位于外层可滚动编辑区 |
| 4 | 逐批身份、剩余量、输入与合计 | 修正空值或超量 | 任一空值、非正数、单批超量或自动分配缺口都阻塞确认并指出修法 |
| 5 | 所有批次数量合法 | 确定选择并提交报工 | `materialBatchRefs` 仍逐批提交；后端继续按批次再次校验库存 |

### 摩擦点与设计回应

| 摩擦点 | 严重程度 | 设计回应 |
|---|---|---|
| 操作员知道本批不够，却要自己心算并反复勾选/拆数 | HIGH | 在本批不足时优先给出一键 FEFO 自动分配，按每批剩余量依次填满直至目标量 |
| “自动合并批次”容易被理解为抹掉追溯身份 | HIGH | 全部文案使用“自动分配用量”；列表、编辑区和 payload 始终保留每个批次 ID 与数量 |
| 自动接口失败、单位不一致或库存不足可能形成死胡同 | HIGH | 原地保留错误/缺口说明和“改为手动选择批次”整行选项；已有选择和输入不清空 |
| 自动结果仍可能因并发领料过期 | MED | 明示“按当前可用量生成，提交时再次校验”；不绕过既有逐批超量和服务端校验 |
| 手动路径被自动操作遮蔽 | MED | 同一汇总窗口保留可见的次选项，自动结果也在原窗口内随时切回手动编辑；不把两个动作散落成页面按钮 |

## 交互与数据契约

1. 仅当普通单批模式、投入量为正且大于当前批次 `remainingQuantity` 时展示决策卡；不打断本批足够的原单批流程。
2. 自动路径调用现有 `getFefoBatches(materialTypeId, targetQty, factoryId)`；只接受同一 `materialTypeId` 且批次 `quantityUnit` 与报工投入单位一致的返回。单位不一致时 fail closed，不做换算猜测。
3. 分配算法按 FEFO 返回顺序依次使用 `min(批次剩余量, 尚缺目标量)`；只选择数量大于 0 的批次。数字格式不制造无意义尾零。
4. 自动结果不足目标量时保留已生成的逐批数量，但 `canConfirm()` 与父层验证都保持阻塞，并显示尚缺数量；切到手动后由操作员重新选择/调整。
5. 自动结果中的任一选择或数量被人工修改后即进入手动模式，所有逐批空值、非正数、超量校验继续生效。
6. 自动与手动最终都只生成现有 `MaterialBatchRef[]`；不新增“合并批次”实体、字段或提交 API。

## 验收判据

- 真实组件测试覆盖：不足单批出现双路径；自动成功分成 2–5 批并精确合计目标量；手动路径保留首批已填量并可逐批编辑。
- 失败恢复覆盖：FEFO 接口失败、返回单位不一致、总可用量不足时都显示具体原因且手动入口可达。
- 变异对照：删除自动分配顺序/上限逻辑会使纯函数断言红；删除不足阻塞会使组件确认状态断言红；删除手动选项会使双路径断言红。
- 既有 `MaterialBatchPicker` 目标测试、TypeScript gate 与 `git diff --check` 通过。
