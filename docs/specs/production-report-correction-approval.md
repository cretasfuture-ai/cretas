# 报工核对修正与审批（冻结规格）

## 状态机、字段、权限与停止条件

- 状态：无修正 → `PENDING_APPROVAL`（草稿，不改变当前有效报工，阻止结单）→ `APPROVED_APPLIED`（同一事务应用允许字段并保留原值）或 `REJECTED`（原值不变）。每次批准形成永久审计记录，不覆盖既有审计。
- 可改字段：实际产出、良品数量、不良品数量、人员数量、总工时、报工备注。不得改原料/半成品投入、批次来源、库存流水、成本、工序/批次/计划状态。
- 权限：具备“报工修正”权限的文员或生产管理人员可发起；普通报工员不可发起。审批人只由 OA 已发布工作流节点配置决定；代码不写角色。未配置 `PRODUCTION_REPORT_CORRECTION_APPROVAL` 时提示“请先配置报工修正审批流程”并拒绝创建草稿。
- OA 复用：复用现有 workflow instance 创建、待办、节点流转和 domain action；只增加一个业务类型及报工修正 domain adapter，不创建第二套审批。
- 盘点：按计划/批次/成品关联显示已批准修正的 before/after、原因和审批状态；只提示重点核对，不创建盘盈盘亏或库存流水。
- 停止条件：租户不一致、审批前值被应用、允许范围外字段可改、产生投入/库存/成本 mutation、任务/批次/计划回退、重复应用、硬编码审批角色或无配置默认通过。

## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像

- 报工员：在手机端提交现场结果，不负责审批或事后重录整道工序。
- 文员/生产管理人员：在 Web 核对原值，只修错误结果字段并说明原因。
- OA 审批人：由工作流配置决定，在待办中看清 before/after 后批准或驳回。
- 盘点人员：看见醒目提示后重点核对实物，仍通过正式盘点提交差异。

### 用户旅程

| 阶段 | 入口与动作 | 必见反馈 | 异常停止 |
|---|---|---|---|
| 核对 | 生产管理 → 报工核对，点“核对修正” | 原始值自动带出，仅允许字段可编辑 | 已结单、无权限或已有待审批时不允许提交 |
| 提交 | 填新值与必填原因，提交审批 | “待审批”，当前有效值仍显示原值 | 未配置流程时明确提示先配置 |
| 审批 | OA 待办查看差异，批准/驳回 | 批准后“报工数据已修正”；驳回显示原因 | 非配置审批人无权操作 |
| 结单 | 待审批时尝试结单；批准后重试 | 待审批明确阻断并指出工序；批准后可继续 | 不得绕过草稿直接结单 |
| 盘点 | 打开相关批次/成品盘点 | 醒目提示、差异、原因、审批状态 | 提示不得自动改变库存 |

### 摩擦点清单

1. 从空白重录会迫使员工凭记忆还原整道报工。
2. 审批前若混用草稿值，会污染结单、成本和库存判断。
3. 只改数字不留标记，后续盘点无法识别重点批次。
4. 隐藏或模糊的工作流缺失会被误解为已提交成功。

### 每个摩擦点的设计回应

1. 修正弹窗只读展示原值，并以原值预填新值；输入库存字段完全不出现。
2. 页面并列显示“当前有效值”和“待审批修正”，结单按钮返回带工序信息的阻断提示。
3. 报工行、批次核对和盘点页统一使用“待审批/报工数据已修正”标签，可展开 before/after 与原因。
4. 未配置流程使用阻断型错误“请先配置报工修正审批流程”，不显示成功 Toast，不创建草稿。
