# F006 仓管 App 首页与收发货任务体验

## 目标与验收

- 底部固定为四个入口：`首页 / 入库 / 发货 / 我的`，登录后先到首页。
- 首页只提供两个大入口：`入库` 与 `发货`；进入后落到对应业务首页。
- 入库管理以采购收货任务为真值，不再用已生成物料批次冒充待收货任务。
- 入库筛选固定为 `全部 / 待收货 / 部分入库 / 已收货`；全部按该顺序排列，同状态内优先显示交期更早的任务。
- 删除餐饮待验收入口、采购卡片的“财审通过”措辞与“明细行”统计。
- 每张收货/发货卡片显示“共 N 项”，所有数量必须紧邻真实单位；多单位订单不得把不同单位相加。
- 扫码入库为完整宽度、至少 56dp 高的明显操作。

## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像

- F006 仓管主管/仓管员，主要在收货区与发货区使用手机。
- 可能戴手套、单手操作，现场噪声大，不能依赖细小文字或隐含状态。
- 核心判断是“现在收/发哪一单、几项、多少、什么单位”，不需要在 App 查看办公室统计。

### 用户旅程

| 阶段 | 用户动作 | 系统反馈 | 下一步 |
|---|---|---|---|
| 登录 | 用仓管账号登录 | 进入四导航的首页 | 选择入库或发货 |
| 首页 | 点击大号入库/发货卡片 | 切换到相应底部导航首页 | 查看待办 |
| 入库 | 查看待收货、部分入库、已收货 | 显示真实采购任务数、供应商、项数与带单位数量 | 点任务或扫码 |
| 收货 | 核对每项应收/已收/待收 | 数量与单位成对呈现，多单位不合计 | 开始收货并提交 |
| 发货 | 查看待确认发货单 | 显示客户、销售单、项数和每项带单位计划数量 | 确认并发货 |
| 返回 | 完成操作返回列表 | 列表自动刷新，收货完毕的采购单进入「已收货」 | 继续下一单或退出换角色 |

### 摩擦点清单

1. 原来只有三个导航，没有首页作为稳定起点。
2. 入库页读取物料批次，导致“待入库 0 单”与真实采购待收货任务不一致。
3. 餐饮待验收与工厂仓管场景无关，增加误触。
4. 原筛选是批次质检生命周期，不是仓管的收货生命周期。
5. “财审通过”是收货可见的前置条件，不是仓管下一步，重复占位。
6. 数量缺单位，且不同单位直接相加会制造错误合计。
7. 发货卡片把多项货品压成一行，收货与发货的核对方式不一致。
8. 扫码入库按钮偏小，现场单手/戴手套不友好。
9. 采购单收货完毕后显示「已完成」，没有说清已完成的是收货动作。

### 设计响应

- 首页只保留两个大号 `TouchableRipple` 业务入口，底部“我的”始终保留用于退出换角色。
- 入库页直接查询采购单四类状态并显式显示加载失败，禁止把权限/网络错误伪装成空列表。
- `APPROVED` 与 `FINANCE_APPROVED` 对仓管统一显示“待收货”；`PARTIAL_RECEIVED` 显示“部分入库”。
- 单位统一时才展示三列总量；多单位订单显示“多单位，按明细核对”，并逐项展示应收/已收/待收及单位。
- 收货与发货卡片都显示“共 N 项”和最多三行物料/产品明细，超出时明确提示剩余项数。
- 采购单的 `COMPLETED` 仅作为内部状态值；采购列表、仓储入库筛选和卡片统一显示「已收货」。
- 所有主要触控目标不小于 44dp；扫码入口高度 56dp；错误态给出原因和重试动作。
